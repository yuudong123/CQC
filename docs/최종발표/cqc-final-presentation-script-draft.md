## 발표 시간 가이드

**15분 발표는 아래 선택 쪽을 요약해 말하고 품질 라이브 3분을 포함하는 동선이다.** 자료의 41쪽은 유지하며, 전체 대본을 모두 읽는 동선과 구분한다. 실제 시간은 리허설 전 추정치다.

| 구간 | 이동할 쪽 | 시간 |
|---|---|---|
| 문제·데이터 선정·MVP | 1·2·4~9 (3쪽 목차는 넘김) | 3분 |
| 데이터 | 10·12·13·16 | 1.5분 |
| 모델 선택 | 19·20·23·30 | 2.5분 |
| 시스템 | 31~34 | 2분 |
| 품질 라이브 | 35 → 서버 관제, 거래·물류 옵션 제외 | 3분 |
| 결과·한계·마무리 | 36~41 | 3분 |

상세 연구 **11·14·15·17·18·21·22·24~29쪽은 질문 대응·참고용**으로 두고 선택 동선에서는 건너뛴다. 라이브 3분은 처리 중 사과, 재검사·검수 사진, 처리량과 이력 확인을 압축해서 보여준다.

41쪽의 전체 해설 대본은 약 **22~27분**이고, 10-08 시연 대본은 별도 **8~10분**이다. 두 대본을 그대로 이어 읽으면 겹치는 설명까지 포함해 **30~37분**이므로 15분 발표로 계산하지 않는다. 15분 동선에서는 선택 쪽과 품질 라이브만 사용한다.

## 01쪽. CQC 사과 품질 판정

안녕하세요. CQC는 같은 사과의 여러 각도 사진을 함께 보고 품종과 외관 등급을 판정하는 프로젝트입니다. 저희가 구현한 MVP는 판정 결과를 정상 선별 또는 재검사로 나누고, 검사 이력과 현재 상태를 관제 화면에서 확인하는 흐름입니다. 오늘은 데이터와 실험을 어떻게 바꿔 모델을 선택했는지, 실제 서버에서 어디까지 연결하고 확인했는지 말씀드리겠습니다. 거래와 배송은 뒤에서 별도의 가상 확장 시연으로 소개합니다.

## 02~03쪽. 목차

발표는 여섯 부분으로 나눴습니다. 문제와 데이터를 고른 이유, 데이터 분석, 모델 실험과 선정, 선별 정책과 시스템, 시연과 결과, 마지막으로 한계와 확장 방향 순서로 말씀드리겠습니다. 3쪽은 말없이 넘깁니다.

## 04쪽. 문제 정의

사과를 하나씩 보며 등급을 판단하는 작업은 같은 판단을 계속 반복해야 합니다. 작업자나 촬영 환경이 달라지면 판단 기준도 흔들릴 수 있고, 애매한 사과는 다시 확인해야 합니다. 저희는 이 반복 업무를 품종·외관 판정과 재검사 기준으로 정리하고, 결과를 기록하는 흐름을 만들었습니다. 판정 결과를 거래와 배송에 이어 쓰는 것은 향후 확장 목표입니다.

## 05쪽. 왜 AI Hub 사과 품질 데이터인가

데이터를 고를 때 기준은 "실제 선별 공정과 같은 구조인가"였습니다. 성주 월항농협의 참외 AI 선별은 한 알을 돌리면서 24장을 찍고 26가지 외관 상태를 확인해 등급을 정하고, 그 결과를 농가가 확인할 수 있게 남깁니다. 도입 뒤 하루 처리량은 80톤에서 120~160톤으로 늘었고 작업 인력은 절반 이상 줄었습니다.

AI Hub 농산물 품질 이미지의 사과 데이터도 같은 사과를 여러 카메라 위치와 회전 각도로 찍었고, 같은 사과의 사진이 group_no로 묶여 있습니다. 특·상·보통 등급과 부사·양광 품종 라벨, 촬영 각도와 크기·무게 정보도 함께 있습니다. "한 개체를 여러 각도로 보고, 등급을 정하고, 기록한다"는 현장 구조를 그대로 데이터로 검증할 수 있어서 이 데이터를 골랐습니다.

## 06쪽. 데이터 선정 기준과 확인 결과

고르기 전에 원본을 직접 확인했습니다. 사과 179개, 사진 25,024장이 group_no로 연결되고, 부사·양광과 특·상·보통의 여섯 조합이 모두 있습니다. 손상·짝 누락·라벨 불일치가 0건이라 한 달 일정 안에 바로 학습을 시작할 수 있었습니다. 공개 데이터이고 AI Hub가 기준모델 F1 0.89를 공개해서, 저희 외관 승인 기준을 그보다 높은 Macro F1 0.90으로 정했습니다.

한계도 알고 골랐습니다. 독립된 표본은 사진 수가 아니라 사과 179개이고, 상처 같은 결점 라벨과 실측 당도가 없고, 촬영 환경이 하나뿐입니다. 그래서 결점 판정은 하지 않고, 당도는 가상값으로 시연하며, 현장 일반화는 별도 검증 과제로 남겼습니다.

## 07쪽. 업무 흐름 변화

기존에는 사람이 외관을 보고 선별 위치를 정했습니다. 제안한 흐름에서는 AI가 품종과 외관 등급, 신뢰도를 반환하고 Backend가 선별 목적지를 결정합니다. 신뢰도가 기준보다 낮거나 오류가 있으면 재검사로 분리합니다. 이번 MVP에서는 이 결과를 관제와 이력에 연결했습니다. 출품·입찰·배송은 그다음 단계의 가상 시연입니다.

## 08쪽. 목표 서비스 흐름

입력은 사과 한 개를 여러 각도에서 촬영한 사진 12장입니다. AI 판정에 가상 당도 구간을 더해 선별 목적지를 정하고, 관제 화면에서 검사 상태와 이력을 확인합니다. 여기까지가 품질 MVP입니다. 오른쪽의 출품·입찰·결제·배차는 브라우저의 가상 흐름으로 보여줍니다. 실제 결제나 실제 판매·배송 연동이 완료됐다는 의미는 아닙니다.

## 09쪽. MVP 정의

MVP의 단위는 사진 한 장이 아니라 사과 한 개입니다. 부사·양광 두 품종과 특·상·보통 세 외관 등급을 판정하고, 비실측 가상 당도를 14 Brix 미만과 이상으로 나눕니다. 정상 목적지는 이 세 기준을 조합한 12개이고, 재검사 목적지 하나를 더해 총 13개입니다.

10월 5일 기준으로 Simulator 자동 입력부터 AI 판정, DB 저장, 서버 관제까지 연결돼 있습니다. 다만 현재 운영은 순차 한 개, 2초마다 한 묶음으로 초당 0.5건입니다. 처음 목표인 초당 2건과 외관 Macro F1 0.90에는 미달하며, 정상 100건과 장애 5종의 최종 수용시험도 남아 있습니다.

## 10쪽. 데이터와 판정 단위

원본은 이미지와 JSON 25,024쌍이지만 실제 사과는 179개입니다. 같은 사과를 여러 번 촬영했기 때문에 사진 수와 독립된 사과 수를 구분해야 합니다. 같은 사과를 나타내는 ID인 group_no로 사진을 묶고, 학습·검증·시험도 사과 단위로 나눴습니다. 화면의 가상 당도는 모델이 측정한 당도가 아니라 시연용 생성값입니다.

## 11쪽. 데이터·모델 의사결정 과정

처음에는 원본 연결과 사과 단위 분할을 확인하고, 모델 구조와 사진 장수를 비교했습니다. 첫 후보는 개발 평가가 좋았지만 Test에서 상 등급 오류가 집중됐습니다. 그래서 학습 설정뿐 아니라 평가 시점을 고르는 방식도 바꿨습니다. 그 뒤 각도 재선택, 가상 당도 결합, 종합등급 모델을 비교하고 v2 이미지 모델을 유지했습니다. 지금부터는 각 선택의 이유를 순서대로 보여드리겠습니다.

## 12쪽. 표본 규모와 등급 분포

한 사과에 사진이 8장부터 184장까지 있으므로 사진이 많은 사과가 독립 표본 수를 늘려 주지는 않습니다. 등급별 사과 수도 특 48개, 상 75개, 보통 56개로 다릅니다. 그래서 전체 정답률과 함께 Macro F1을 사용했습니다. F1은 정답을 얼마나 잘 찾고 예측을 얼마나 정확하게 했는지 함께 보는 점수이고, Macro F1은 각 등급의 점수를 같은 비중으로 평균한 값입니다.

## 13쪽. 등급 정답과 대표 샘플

정답은 AI Hub 데이터에 붙은 특·상·보통 라벨입니다. 착색이나 크기, 결점의 세부 수치 기준은 공개되지 않아, 화면에는 등급별 실제 사진과 모델 예측을 예시로 놓았습니다. 이 확률은 모델이 낸 예측값이지 등급의 객관적인 근거나 품질 보증은 아닙니다.

부사 상 대표 사과는 v1이 특으로 틀렸지만 v2는 상으로 맞힌 사례입니다. 한편 상처를 따로 구분하는 결점 라벨은 없습니다. 상처 난 사과가 재검사로 잘 빠지는지도 아직 검증하지 못했습니다.

## 14쪽. 라벨 연결과 매니페스트

처음에는 JSON의 번호만으로 사진과 라벨을 연결할 수 있을 것 같았습니다. 실제로 확인하니 번호와 사진 번호 조합에 중복이 있어 연결 키로 쓸 수 없었습니다. 그래서 같은 ZIP 안의 파일명으로 PNG와 JSON을 연결하고, 사과 묶음은 group_no로 따로 관리했습니다. 매니페스트는 어떤 원본 파일에서 사진과 라벨을 읽어야 하는지 기록한 목록입니다.

## 15쪽. 무결성·중복 검사

25,024쌍을 모두 읽어 사진과 라벨의 짝, 해상도, 파일 손상과 내용 중복을 검사했습니다. 손상이나 짝 누락, 해상도 불일치는 0건이었습니다. 이미지 내용이 완전히 같은 파일은 5쌍 있었고, 모두 같은 사과 안에 있었습니다. 같은 사진인데 촬영 각도 라벨이 다른 사례도 발견해 원본과 점검 기록을 함께 보존했습니다.

## 16쪽. 사과 단위 분할

같은 사과의 앞면을 학습하고 뒷면을 시험하면 이미 본 사과의 특징이 평가에 섞일 수 있습니다. 이를 막으려고 같은 group_no의 사진은 전부 같은 세트에 넣었습니다. Train 125개, Validation 27개, Test 27개로 고정했고 사과 ID의 교차는 0건입니다.

개발용 152개에는 검증 사과를 다섯 번 바꿔 비교하는 5-fold 교차검증을 적용했습니다. 원본 Training과 Validation의 출처 차이를 보는 source 검증도 별도로 했습니다. 이후에 나오는 CV와 source는 이 두 개발 평가를 뜻합니다.

## 17쪽. 대표 프레임과 누락 뷰 처리

화면의 12장은 같은 사과에서 규칙으로 고른 대표 사진입니다. 촬영 방향과 각도를 정렬한 뒤 균등 간격으로 뽑아 4·8·12·16·40장 조건을 만들었습니다. 사진은 224×224 RGB로 맞췄습니다. 사진이 8장뿐인 사과는 빈 자리 네 개를 채우되, 계산할 때 빈 자리의 특징을 제외했습니다. 사진이 부족하다는 이유로 다른 사과와 섞거나 평가에서 임의로 빼지 않았습니다.

## 18쪽. 공유·분리 모델 비교

두 구조 모두 사진마다 특징을 추출하고, 유효한 사진들의 특징을 평균해 사과 한 개를 판단합니다. 공유 구조는 품종과 외관이 같은 특징 추출기를 쓰고, 분리 구조는 각각 별도의 특징 추출기를 씁니다. 같은 특징을 공유하는 편이 나은지 직접 비교한 것입니다. PyTorch로 다각도 입력과 마스킹을 구현했고, 작은 데이터와 CPU 실행을 고려해 ImageNet 사전학습 MobileNetV3 Small을 사용했습니다.

## 19쪽. 구조·입력 장수 50회 비교

공유·분리 두 구조, 다섯 가지 사진 장수, 다섯 fold를 조합해 50회 학습했습니다. 당시 fold별 최고 시점 점수에서는 분리 12장이 외관 Macro F1 0.9809로 가장 높았습니다. 그래서 첫 후보를 분리 12장으로 정했습니다. 사진을 40장으로 늘렸을 때는 성능이 오히려 낮아졌습니다.

다만 이 그래프는 모델 개발 평가입니다. 전체 후보를 목표 서버 CPU에서 같은 조건으로 비교한 완료 증거는 아닙니다. 그 처리시간 비교 범위는 추가 확인이 남아 있습니다.

## 20쪽. v1 Test 오류 분석

첫 후보를 개발 사과 152개로 학습하고 Test 27개에서 평가하니 외관 Macro F1은 0.7778이었습니다. 오류 여섯 개가 모두 상 등급에 집중됐습니다. 상을 특으로 본 경우가 네 개, 보통으로 본 경우가 두 개입니다. 오답 네 개는 신뢰도도 96% 이상이었습니다. 이 사례를 통해 신뢰도가 높다는 이유만으로 판정이 맞다고 볼 수 없고, 등급 경계와 학습 안정성도 확인해야 한다는 점을 알았습니다.

## 21쪽. Epoch 선정 방식 재검토

Epoch는 전체 학습 데이터를 한 번 학습하는 단위입니다. v1은 각 fold에서 가장 좋은 epoch를 찾은 뒤 그 중앙값인 19를 최종 학습 길이로 골랐습니다. 그런데 모든 fold를 같은 19 epoch에서 비교하면 외관 F1 평균이 0.6735였습니다. 서로 다른 유리한 시점의 점수를 모은 것과 한 시점에서 비교한 결과가 달랐던 것입니다. v2부터는 같은 epoch의 평균, 가장 낮은 fold, source 검증을 함께 보도록 바꿨습니다.

## 22쪽. v2 학습 안정화 실험

v2는 분리 구조와 12장 입력을 유지하면서 학습률을 낮추고 규제를 강화했습니다. 쉬운 표본보다 어려운 표본의 영향을 키우는 Focal 손실과, 등급 간 거리를 반영하는 순서형 손실도 비교했습니다. 이미지 단독과 가상 당도 결합까지 총 48회 실행했습니다. 좋은 평균만 보지 않고 최저 fold와 source 중 더 낮은 점수도 반영해, 특정 검증 구성에서 크게 흔들리는 후보를 걸렀습니다.

## 23쪽. v2 선정 결과

선정한 설정은 이미지 단독, 분리 12장, 어려운 표본의 영향을 키우는 Focal 손실, 4 epoch입니다. 개발 5-fold의 외관 Macro F1은 0.8844, source는 0.7932였습니다. 이 설정으로 학습한 모델은 기존 Test 27개를 다시 평가했을 때 모두 맞혔습니다.

여기서 1.0000은 독립된 최종 승인 점수가 아닙니다. v1 오류를 분석했던 같은 Test를 재사용한 회귀 비교, 즉 기존 사례에서 결과가 어떻게 달라졌는지 확인한 값입니다. 현재 모델도 미검증 후보 상태이며, 기능 동결 뒤 평가와 모델 카드 정리가 남아 있습니다.

## 24쪽. 각도 재선택·증강 실험

대표 사진 12장에만 의존하는지 확인하려고 매 epoch마다 같은 사과에서 다른 각도를 고르는 실험도 했습니다. 두 fold는 완료했고 세 번째 fold는 일부 진행한 뒤 추가 학습을 중단했습니다. 그래서 이 결과를 완료된 비교나 성능 개선으로 보고하지 않고, 부분 실행 기록으로 남겼습니다. 밝기와 대비 변화는 후속 후보입니다. 현재 적용 모델은 기존 v2입니다.

## 25쪽. 가상 당도 생성

당도 센서가 없으므로 시연용 가상 당도를 만들었습니다. 사진의 붉은 정도와 면적, 각도별 색상 균일도에 사과별 고정 잡음을 더했습니다. 같은 사과에는 다시 실행해도 같은 값이 나옵니다. 179개 값의 범위는 10.7부터 17.9이고 평균은 14.11입니다. 이 값은 실제 사과의 당도나 사진으로 당도를 측정한 결과가 아닙니다. 보조 입력 비교와 선별 동선을 시험하기 위한 값입니다.

## 26쪽. 가상 당도 결합 모델 비교

이미지에 가상 당도를 더하면 기존 외관 등급을 더 잘 맞힐지 비교했습니다. 이미지 단독은 CV 0.8844, source 0.7932였고, 결합 모델은 각각 0.8592, 0.7675로 낮아졌습니다. 입력을 하나 더 넣는 것만으로 성능이 좋아지지는 않았습니다. 그래서 외관은 이미지 모델로 판단하고, 가상 당도는 다음 단계의 선별 기준에서 따로 쓰기로 했습니다.

## 27쪽. 검토한 종합등급 정책

다음 두 쪽은 현재 선별 정책을 결정하기 전에 검토한 별도 실험입니다. 외관 60%, 가상 당도 40%로 종합 점수를 만들고, 높은 당도가 낮은 외관을 과하게 보완하지 못하도록 최소 조건을 뒀습니다. 이 규칙으로 만든 종합등급을 신경망이 학습하도록 해 봤습니다. 종합등급은 AI Hub의 새 정답이나 실제 상품 가치가 아니라 저희가 정한 가상 정책의 정답입니다.

## 28쪽. 정책 모델 실험과 한계

v3는 이미지와 가상 당도로 그 정책 기반 종합등급을 예측했습니다. source F1은 0.6238, 공통 시점의 5-fold 평균은 0.6283이었고 최저 fold는 0.3592였습니다. 검증 구성에 따른 편차가 커서 운영 모델로 선택하지 않았습니다. 기존 Test 비교도 재사용 진단이고 v2와 v3의 학습 사과 수가 달라, 완전히 같은 조건의 독립 비교로 보지는 않습니다. 현재는 v2 외관 판정을 사용합니다.

## 29쪽. 입고 시연과 모델 적용

모델을 고른 다음 실제 입력을 재생할 사진 묶음을 만들었습니다. 기록된 선택 규칙에 따라 사진 13,720장을 제외하고, 남은 11,304장으로 12장 완성 묶음 869개와 잔여 묶음 127개를 구성했습니다. Simulator가 이를 보내고 v2가 판정하는 흐름입니다.

여기서 원본 사과 132개를 다시 사용하므로 새로운 독립 정확도 시험은 아닙니다. 제외 사진과 겹치지 않는 시연 입력으로 HTTP와 선별·저장 흐름을 확인하는 데 사용했습니다. 화면의 합성 이미지 HTTP 측정도 실제 사진 운영 처리량과 별개의 시험입니다.

## 30쪽. 후보 비교와 현재 선정 근거

선정 과정을 정리하면, 먼저 분리 12장으로 구조를 고정하고 v1의 상 등급 오류를 보고 v2의 학습 설정과 손실을 선택했습니다. 가상 당도 결합은 성능이 낮아졌고, 종합등급 v3는 fold 편차가 커서 채택하지 않았습니다. 신뢰도 보정은 예측 확률을 조정한 것이며 분류 정확도 개선과 구분합니다.

적용 후보는 v2지만 개발 외관 F1 0.8844는 목표 0.90에 미달합니다. 기존 Test의 1.0000도 재사용 회귀입니다. 서버에서 선정 모델을 측정한 근거는 있고, 전체 후보의 목표 CPU 비교와 최종 승인은 남아 있습니다.

## 31쪽. 최종 선별 정책

현재 운영 정책은 종합등급을 다시 학습한 v3가 아니라 v2의 품종·외관 결과와 가상 당도 구간의 조합입니다. Backend가 신뢰도와 오류, 제한시간을 확인한 뒤 정상 목적지 12개 또는 재검사 목적지 하나를 선택합니다. 품종 신뢰도 기준은 0.50, 외관은 0.60입니다. 물리 선별기나 PLC를 연결한 것은 아니고, 가상 제어 결과와 목적지를 확인하는 범위입니다.

## 32쪽. 시스템 프로세스

왼쪽은 현재 품질 MVP의 처리 흐름입니다. Simulator가 사진과 가상 당도를 보내면 AI 판정 후 선별 목적지를 정하고, 이력과 상태를 관제에 표시합니다. 오른쪽은 출품부터 배송까지의 확장 흐름입니다. 점선은 가상 시연의 연결을 뜻합니다. 공통 화면에서 이어 보여줄 수 있어도 실제 QC 기록이 판매 물량과 실배송으로 연결됐다는 의미는 아닙니다.

## 33쪽. 소프트웨어 아키텍처

품질 관제는 Next.js 웹이 QC Backend를 조회하는 구조입니다. Backend는 Inference에 사진을 보내고 결과로 선별 정책을 적용하며, 검사 이력은 MySQL에 저장합니다. 웹은 1초마다 상태를 조회합니다.

물류 API와 MongoDB 코드는 별도의 확장 구성으로 있습니다. 현재 발표의 거래·배송 화면은 기본 브라우저 가상 모드입니다. 서버 관제에서 자동 경매를 켜더라도 QC 이력을 참고해 가상 상태에 복사하는 것이며, 실제 물류 API나 MongoDB 연동을 증명하는 동선은 아닙니다.

## 34쪽. 실행·배포 아키텍처

서버컴의 Docker Compose는 품질 네 개와 물류 세 개, 총 일곱 컨테이너를 구성합니다. 모델 파일은 Inference 이미지에 넣고 DB와 Simulator 위치, 로그는 볼륨에 보관합니다. dev에 올리면 Jenkins가 Python·웹 시험을 먼저 돌리고, 통과한 버전만 빌드해 배포합니다. 배포 뒤 상태 확인에 실패하면 직전 이미지로 자동 복구하고, 서버에서 실패를 일부러 주입해 이 동작을 확인했습니다.

오류 로그는 서비스별 현재 파일 하나와 백업 다섯 개로 순환합니다. Simulator는 재시작해도 재생 위치를 이어 갑니다.

## 35쪽. 최종 시연 구성

시연에서는 사과 12장 입력, 품종·외관 판정, 재검사 분기, 이력·통계 순서로 품질 MVP를 보여드립니다. 사진에는 처리 중인 사과와 최근 결과, 재검사·오류 목록, 처리량 그래프가 있습니다. 라인 속도는 준비 단계에서 2초·순차 한 개로 확인합니다.

그다음 별도 브라우저 예시에서 거래·배송 가상 흐름을 짧게 보여드립니다. 공용 서버 장애 주입은 기본 동선에 넣지 않습니다. 메뉴에 있는 장애 여섯 종류와 최종 수용시험의 필수 장애 다섯 종류도 구분합니다.

> 진행자 메모: 실제 화면 조작은 10-08 시연 대본을 따른다. 서버 연결이 안 되면 10-05 저장 캡처와 사전 준비한 브라우저 예시로 전환하고, 현재 실서버 실행 증거처럼 설명하지 않는다.

## 36쪽. 구현 범위와 남은 검증

모델, Backend, 웹은 실제 서버에서 연결돼 있습니다. 모델은 보정한 v2를 서비스하고, Backend는 판정과 12+1 선별, 검사 이력, 검수 사진, 라인 속도 기한까지 구현했고 통합시험 2단계 27개와 3단계 DB·보존·조회·복구 시험을 통과했습니다. 화면은 처리 중 사과 12장과 검수 이미지, 처리량 추이를 실제 데이터로 보여주고, 일곱 가지 화면 크기에서 스크롤 없이 보이는 것과 서버 화면을 3시간 25분 띄워 둬도 메모리가 늘지 않는 것을 확인했습니다. 배포는 시험 통과 후 배포, 실패 시 복구, 위치 복구와 로그 순환을 서버에서 확인했습니다.

다만 기능이 연결된 것과 최종 수용을 통과한 것은 구분합니다. 정상 100건과 장애 다섯 종류는 10월 12일 수용시험에서 판정하고, 13일 기능 동결 뒤 최종 Test 1회와 모델 카드를 확정합니다.

## 37쪽. 측정 조건별 결과

결과마다 언제, 어떤 입력으로, 어느 구간을 쟀는지 함께 적었습니다. 9월 30일 실제 사진 12장으로 잰 추론 서버 내부 시간은 p95 309밀리초입니다. p95는 요청의 95%가 그 시간 안에 끝난다는 뜻입니다. 10월 5일 운영 이력 200건으로 보면 2초 간격에서 초당 0.50건을 처리합니다. 처음 목표였던 초당 2건에는 미달이라 그대로 공개합니다.

추론 제한시간을 고정 500밀리초에서 라인 속도와 같게 바꾼 뒤에는, 하루 4.1%이던 시간 초과가 적용 후 535건 동안 0건이었습니다. 그 사이 배포가 두 번 있었는데도 0이었습니다. 신뢰도 보정은 개발 표본에서 재검사를 23.7%에서 16.4%로 줄였고, 운영 이력의 재검사는 9.5%였습니다. 표본과 조건이 달라 두 비율을 직접 비교하지는 않습니다.

관제 화면은 10월 6일 서버에 3시간 25분 띄워 두고 30초마다 메모리를 쟀습니다. 30분마다 정리한 뒤의 메모리가 6.8에서 8.7MB 사이로 늘지 않았고, 그사이 재배포 네 번과 탭 숨김 두 번에도 새로고침 없이 스스로 복구했습니다.

## 38쪽. 문제 해결 사례

문제를 만나면 먼저 재고, 원인을 나누고, 고친 뒤 다시 쟀습니다. 재검사가 많았던 문제는 모델을 다시 학습하지 않고 신뢰도 보정만으로 줄였습니다. 추론이 느렸을 때는 병목이 모델이 아니라 사진 해제라는 걸 찾아 병렬로 바꿨습니다. 설정은 초당 2건인데 실제는 0.63건이던 문제는 처리 주기보다 긴 2초 간격으로 맞췄습니다.

입력 간격을 바꾼 뒤에도 500밀리초 제한시간은 그대로 남아 있었습니다. 하루치 이력을 10분 단위로 나눠 보니 조용한 시간엔 0%, 빌드 중엔 8.8%였고, 근거가 사라진 숫자라는 걸 확인해 제한시간을 라인 속도와 같게 바꿨습니다. 처리 중 사과가 화면에 잘 안 뜨던 문제는 사진 한 장이 1.66메가바이트라는 걸 재서 축소본으로 바꾸고 조회 주기를 맞춰, 들어온 사과를 모두 보여주게 했습니다. 계약 변경으로 Jenkins 웹 시험이 실패했을 때는 배포가 멈췄지만, 실패 시 기존 버전을 유지하는 설계 덕분에 서비스는 끊기지 않았습니다.

## 39쪽. 이슈 기반 협업과 AI 에이전트

저희 팀은 네 명이 데이터·모델, 화면, Backend, 배포를 나눠 맡고, 각자 AI 코딩 에이전트와 함께 작업했습니다. 처음에는 작업 결과와 요청을 디스코드 메시지로 정리했는데, 메시지가 흘러가면서 누가 맡았고 끝났는지 추적하기 어려웠습니다. 필수 요구사항인 처리 중 사과 표시가 담당 없이 남아 있다가 서버 화면에서야 드러난 일도 있었고, 에이전트가 지시 없이 PR을 올려 되돌린 일도 있었습니다.

그래서 10월 1일부터 Git Issue로 바꿨습니다. 제목에 담당 파트와 WBS 번호를 쓰고 파트·종류·우선순위 라벨을 붙입니다. 담당 에이전트는 착수 댓글로 계획을 남기고, 사람이 확인한 뒤에만 작업합니다. 이슈 본문은 요청일 뿐 명령으로 실행하지 않고, 에이전트는 직접 푸시하거나 이슈를 닫지 않습니다. 결과는 수치와 다른 파트 영향까지 댓글로 남기고, 사람이 PR을 병합하면 이슈가 닫힙니다.

첫 이틀 동안 이슈 16건을 만들어 12건을 닫았고, 멘토링 피드백은 다음 날 아침 이슈 6건으로 나눠 그중 3건을 약 한 시간 만에 병합까지 끝냈습니다. 사람과 에이전트가 같은 이슈를 보고 움직이니 동기화 비용이 크게 줄었습니다.
