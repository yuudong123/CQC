## 발표 시간 가이드

**15분 발표는 아래 선택 쪽을 요약해 말하고 품질 라이브 3분을 포함하는 동선이다.** 자료의 41쪽은 유지하며, 전체 대본을 모두 읽는 동선과 구분한다. 실제 시간은 리허설 전 추정치다.

| 구간 | 이동할 쪽 | 시간 |
|---|---|---|
| 문제·데이터 선정·MVP | 1·2·4~9 (3쪽 목차는 넘김) | 3분 |
| 데이터 | 10·12·13·16 | 1.5분 |
| 모델 선택 | 19·20·23·30 | 2.5분 |
| 시스템 | 31~34 | 2분 |
| 품질 라이브 | 35 → 서버 관제, 거래·물류 옵션 제외 | 3분 |
| 결과·한계·마무리 | 36~41 | 3분 |

상세 연구 **11·14·15·17·18·21·22·24~29쪽은 질문 대응·참고용**으로 두고 선택 동선에서는 건너뛴다. 라이브 3분은 처리 중 사과, 재검사·검수 사진, 처리량과 이력 확인을 압축해서 보여준다.

41쪽의 전체 해설 대본은 약 **22~27분**이고, 10-08 시연 대본은 별도 **8~10분**이다. 두 대본을 그대로 이어 읽으면 겹치는 설명까지 포함해 **30~37분**이므로 15분 발표로 계산하지 않는다. 15분 동선에서는 선택 쪽과 품질 라이브만 사용한다.

## 01쪽. CQC 사과 품질 판정

안녕하세요. CQC는 같은 사과의 여러 각도 사진을 함께 보고 품종과 외관 등급을 판정하는 프로젝트입니다. 저희가 구현한 MVP는 판정 결과를 정상 선별과 재검사로 나누고, 검사 이력과 현재 상태를 관제 화면에서 확인하는 흐름입니다. 소규모 농가 한 곳이 자기 농장의 선별 라인을 앉아서 지켜보는 상황을 생각하고 만들었습니다. 오늘은 데이터와 실험을 거쳐 모델을 고른 과정, 그리고 실제 서버에서 연결하고 확인한 결과를 말씀드리겠습니다. 거래와 배송은 뒤에서 가상 확장 시연으로 소개합니다.

## 02~03쪽. 목차

발표는 여섯 부분입니다. 문제와 데이터를 고른 이유, 데이터 분석, 모델 실험과 선정, 선별 정책과 시스템, 시연과 결과, 마지막으로 확장 방향 순서로 말씀드리겠습니다. 3쪽은 말없이 넘깁니다.

## 04쪽. 문제 정의

사과를 하나씩 보며 등급을 정하는 작업은 같은 판단의 반복입니다. 작업자나 촬영 환경에 따라 기준이 흔들리고, 애매한 사과는 다시 확인해야 합니다. 저희는 이 반복 업무를 품종·외관 판정과 재검사 기준으로 정리하고, 결과를 기록하는 흐름을 만들었습니다. 판정 결과를 거래와 배송에 이어 쓰는 것은 확장 목표입니다.

## 05쪽. 왜 AI Hub 사과 품질 데이터인가

데이터를 고를 때 기준은 "실제 선별 공정과 같은 구조인가"였습니다. 성주 월항농협의 참외 AI 선별은 한 알을 돌리면서 24장을 찍고 26가지 외관 상태를 확인해 등급을 정하고, 그 결과를 농가가 볼 수 있게 남깁니다. 도입 뒤 하루 처리량은 80톤에서 120~160톤으로 늘었고 작업 인력은 절반 이상 줄었습니다.

AI Hub 농산물 품질 이미지의 사과 데이터도 같은 사과를 여러 카메라 위치와 회전 각도로 찍었고, 같은 사과의 사진이 group_no로 묶여 있습니다. 특·상·보통 등급과 부사·양광 품종 라벨, 촬영 각도와 크기·무게 정보도 있습니다. "한 개체를 여러 각도로 보고, 등급을 정하고, 기록한다"는 현장 구조를 그대로 검증할 수 있어서 이 데이터를 골랐습니다.

## 06쪽. 데이터 선정 기준과 확인 결과

고르기 전에 원본을 직접 확인했습니다. 사과 179개, 사진 25,024장이 group_no로 연결되고, 부사·양광과 특·상·보통의 여섯 조합이 모두 있습니다. 손상·짝 누락·라벨 불일치가 0건이라 한 달 일정 안에 바로 학습을 시작할 수 있었습니다. AI Hub가 공개한 기준모델 F1이 0.89라서, 외관 승인 기준을 Macro F1 0.90으로 정했습니다.

알고 고른 한계도 있습니다. 독립 표본은 사과 179개이고, 상처 같은 결점 라벨과 실측 당도가 없고, 촬영 환경이 하나입니다. 그래서 결점 판정은 범위에서 빼고, 당도는 가상값으로 시연하며, 현장 일반화는 별도 검증 과제로 남겼습니다.

## 07쪽. 업무 흐름 변화

기존에는 사람이 외관을 보고 선별 위치를 정했습니다. 제안한 흐름에서는 AI가 품종과 외관 등급, 신뢰도를 반환하고 Backend가 선별 목적지를 결정합니다. 신뢰도가 기준에 못 미치거나 오류가 나면 재검사로 분리합니다. 이번 MVP는 이 결과를 관제와 이력까지 연결했습니다. 출품·입찰·배송은 다음 단계의 가상 시연입니다.

## 08쪽. 목표 서비스 흐름

입력은 사과 한 개를 여러 각도에서 촬영한 사진 12장입니다. AI 판정에 가상 당도 구간을 더해 선별 목적지를 정하고, 관제 화면에서 검사 상태와 이력을 확인합니다. 여기까지가 품질 MVP입니다. 오른쪽의 출품·입찰·결제·배차는 브라우저에서 돌아가는 가상 흐름입니다.

## 09쪽. MVP 정의

MVP의 판정 단위는 사과 한 개입니다. 부사·양광 두 품종과 특·상·보통 세 외관 등급을 판정하고, 가상 당도를 14 Brix 미만과 이상으로 나눕니다. 정상 목적지는 이 세 기준을 조합한 12개이고, 재검사 목적지 하나를 더해 총 13개입니다.

지금 Simulator 자동 입력부터 AI 판정, DB 저장, 서버 관제까지 연결돼 있습니다. 운영은 순차 한 개, 2초마다 한 묶음으로 초당 0.5건입니다. 처음 목표였던 초당 2건과 외관 Macro F1 0.90에는 미달했고, 정상 100건과 장애 5종의 최종 수용시험은 10월 12일에 진행합니다.

## 10쪽. 데이터와 판정 단위

원본은 이미지와 JSON 25,024쌍이고, 실제 사과는 179개입니다. 같은 사과를 여러 번 촬영했기 때문에 사진 수와 사과 수를 나눠서 봐야 합니다. 같은 사과를 나타내는 ID인 group_no로 사진을 묶고, 학습·검증·시험도 사과 단위로 나눴습니다. 화면의 가상 당도는 시연용으로 생성한 값입니다.

## 11쪽. 데이터·모델 의사결정 과정

먼저 원본 연결과 사과 단위 분할을 확인하고, 모델 구조와 사진 장수를 비교했습니다. 첫 후보는 개발 평가가 좋았지만 Test에서 상 등급 오류가 몰렸습니다. 그래서 학습 설정과 평가 시점을 고르는 방식을 함께 바꿨습니다. 그 뒤 각도 재선택, 가상 당도 결합, 종합등급 모델을 비교하고 v2 이미지 모델을 유지했습니다. 각 선택의 이유를 순서대로 보여드리겠습니다.

## 12쪽. 표본 규모와 등급 분포

한 사과에 사진이 8장부터 184장까지 있어서, 사진이 많다고 독립 표본이 늘어나지는 않습니다. 등급별 사과 수도 특 48개, 상 75개, 보통 56개로 다릅니다. 그래서 정답률과 함께 Macro F1을 썼습니다. F1은 정답을 얼마나 잘 찾고 예측을 얼마나 정확하게 했는지 함께 보는 점수이고, Macro F1은 등급별 점수를 같은 비중으로 평균한 값입니다.

## 13쪽. 등급 정답과 대표 샘플

정답은 AI Hub 데이터의 특·상·보통 라벨입니다. 착색이나 크기, 결점의 세부 수치 기준은 공개되지 않아서, 화면에는 등급별 실제 사진과 모델 예측 확률을 예시로 놓았습니다.

부사 상 대표 사과는 v1이 특으로 틀렸고 v2가 상으로 맞힌 사례입니다. 상처를 구분하는 결점 라벨은 없어서, 상처 난 사과의 재검사 분기는 확장 과제로 남겼습니다.

## 14쪽. 라벨 연결과 매니페스트

처음에는 JSON의 번호로 사진과 라벨을 연결하려 했습니다. 확인해 보니 번호와 사진 번호 조합에 중복이 있었습니다. 그래서 같은 ZIP 안의 파일명으로 PNG와 JSON을 연결하고, 사과 묶음은 group_no로 따로 관리했습니다. 매니페스트는 어떤 원본 파일에서 사진과 라벨을 읽을지 기록한 목록입니다.

## 15쪽. 무결성·중복 검사

25,024쌍을 모두 읽어 사진과 라벨의 짝, 해상도, 파일 손상과 내용 중복을 검사했습니다. 손상이나 짝 누락, 해상도 불일치는 0건이었습니다. 내용이 완전히 같은 파일은 5쌍이었고, 모두 같은 사과 안에 있었습니다. 같은 사진에 서로 다른 촬영 각도 라벨이 붙은 사례도 찾아 원본과 점검 기록을 함께 보존했습니다.

## 16쪽. 사과 단위 분할

같은 사과의 앞면을 학습하고 뒷면을 시험하면 이미 본 사과의 특징이 평가에 섞입니다. 그래서 같은 group_no의 사진은 전부 같은 세트에 넣었습니다. Train 125개, Validation 27개, Test 27개로 고정했고 사과 ID 교차는 0건입니다.

개발용 152개에는 검증 사과를 다섯 번 바꿔 비교하는 5-fold 교차검증을 적용했습니다. 원본 Training과 Validation의 출처 차이를 보는 source 검증도 따로 했습니다. 이후의 CV와 source는 이 두 개발 평가입니다.

## 17쪽. 대표 프레임과 누락 뷰 처리

화면의 12장은 같은 사과에서 규칙으로 고른 대표 사진입니다. 촬영 방향과 각도를 정렬한 뒤 균등 간격으로 뽑아 4·8·12·16·40장 조건을 만들었고, 사진은 224×224 RGB로 맞췄습니다. 사진이 8장뿐인 사과는 빈 자리 네 개를 채우고, 계산할 때 빈 자리의 특징을 제외했습니다.

## 18쪽. 공유·분리 모델 비교

두 구조 모두 사진마다 특징을 뽑고, 유효한 사진들의 특징을 평균해 사과 한 개를 판단합니다. 공유 구조는 품종과 외관이 특징 추출기 하나를 함께 쓰고, 분리 구조는 각자 따로 씁니다. 어느 쪽이 나은지 직접 비교했습니다. PyTorch로 다각도 입력과 마스킹을 구현했고, 작은 데이터와 CPU 실행에 맞춰 ImageNet 사전학습 MobileNetV3 Small을 썼습니다.

## 19쪽. 구조·입력 장수 50회 비교

두 구조, 다섯 가지 사진 장수, 다섯 fold를 조합해 50회 학습했습니다. fold별 최고 시점 점수에서 분리 12장이 외관 Macro F1 0.9809로 가장 높아 첫 후보로 정했습니다. 40장으로 늘리면 성능이 크게 떨어졌습니다. 이 비교는 개발 PC에서 했고, 선정 모델은 서버에서 따로 측정했습니다.

## 20쪽. v1 Test 오류 분석

첫 후보를 개발 사과 152개로 학습하고 Test 27개에서 평가하니 외관 Macro F1이 0.7778이었습니다. 오류 여섯 개가 모두 상 등급이었고, 상을 특으로 본 경우가 네 개, 보통으로 본 경우가 두 개입니다. 오답 네 개는 신뢰도가 96% 이상이었습니다. 여기서 신뢰도와 함께 등급 경계와 학습 안정성을 봐야 한다는 걸 배웠습니다.

## 21쪽. Epoch 선정 방식 재검토

Epoch는 전체 학습 데이터를 한 번 도는 단위입니다. v1은 fold마다 가장 좋은 epoch를 찾고 그 중앙값인 19를 최종 학습 길이로 골랐습니다. 모든 fold를 같은 19 epoch에서 비교하면 외관 F1 평균은 0.6735였습니다. 그래서 v2부터는 같은 epoch의 평균, 가장 낮은 fold, source 검증을 함께 봤습니다.

## 22쪽. v2 학습 안정화 실험

v2는 분리 구조와 12장 입력을 유지하고, 학습률을 낮추고 규제를 강화했습니다. 어려운 표본의 영향을 키우는 Focal 손실과 등급 간 거리를 반영하는 순서형 손실도 비교했습니다. 이미지 단독과 가상 당도 결합까지 모두 48회 실행했습니다. 평균과 함께 최저 fold와 source 중 낮은 점수를 반영해, 검증 구성에 따라 크게 흔들리는 후보를 걸렀습니다.

## 23쪽. v2 선정 결과

선정한 설정은 이미지 단독, 분리 12장, Focal 손실, 4 epoch입니다. 개발 5-fold의 외관 Macro F1은 0.8844, source는 0.7932입니다.

기존 Test 27개는 v1 오류 분석에 쓴 같은 세트를 다시 돌린 회귀 확인이고, 여기서는 모두 맞혔습니다. 독립 승인 평가는 기능 동결 뒤 최종 Test와 모델 카드로 진행합니다.

## 24쪽. 각도 재선택·증강 실험

대표 사진 12장에만 의존하는지 보려고, 매 epoch마다 같은 사과에서 다른 각도를 고르는 실험을 했습니다. 두 fold를 마치고 세 번째 fold 중간에 학습을 멈췄고, 부분 실행 기록으로 남겼습니다. 밝기와 대비 변화는 후속 후보이고, 적용 모델은 v2입니다.

## 25쪽. 가상 당도 생성

당도 센서가 없어서 시연용 가상 당도를 만들었습니다. 사진의 붉은 정도와 면적, 각도별 색상 균일도에 사과별 고정 잡음을 더했고, 같은 사과는 다시 실행해도 같은 값이 나옵니다. 179개 값의 범위는 10.7부터 17.9, 평균은 14.11입니다. 이 값으로 보조 입력 비교와 선별 동선을 시험했습니다.

## 26쪽. 가상 당도 결합 모델 비교

이미지에 가상 당도를 더하면 외관 등급을 더 잘 맞히는지 비교했습니다. 이미지 단독은 CV 0.8844, source 0.7932였고, 결합 모델은 0.8592, 0.7675로 낮았습니다. 그래서 외관은 이미지 모델로 판단하고, 가상 당도는 선별 기준에서 따로 쓰기로 했습니다.

## 27쪽. 검토한 종합등급 정책

다음 두 쪽은 선별 정책을 정하기 전에 검토한 실험입니다. 외관 60%, 가상 당도 40%로 종합 점수를 만들고, 높은 당도가 낮은 외관을 과하게 메우지 못하도록 최소 조건을 뒀습니다. 이 규칙으로 만든 종합등급을 신경망이 학습하게 했습니다. 이 종합등급은 저희가 정한 가상 정책의 정답입니다.

## 28쪽. 정책 모델 실험과 한계

v3는 이미지와 가상 당도로 그 종합등급을 예측했습니다. source F1은 0.6238, 공통 시점의 5-fold 평균은 0.6283, 최저 fold는 0.3592였습니다. 검증 구성에 따른 편차가 커서 운영 모델로 쓰지 않았고, 지금은 v2 외관 판정을 씁니다.

## 29쪽. 입고 시연과 모델 적용

모델을 고른 다음 실제 입력을 재생할 사진 묶음을 만들었습니다. 기록된 선택 규칙에 따라 사진 13,720장을 빼고, 남은 11,304장으로 12장 완성 묶음 869개와 잔여 묶음 127개를 구성했습니다. Simulator가 이 묶음을 보내고 v2가 판정합니다. 이 묶음은 원본 사과 132개를 다시 쓰기 때문에 정확도 시험에는 쓰지 않고, HTTP와 선별·저장 흐름을 확인하는 데 썼습니다.

## 30쪽. 후보 비교와 현재 선정 근거

정리하면, 분리 12장으로 구조를 고정하고, v1의 상 등급 오류를 보고 v2의 학습 설정과 손실을 골랐습니다. 가상 당도 결합은 성능이 낮아졌고, 종합등급 v3는 fold 편차가 커서 채택하지 않았습니다. 신뢰도 보정으로 예측 확률을 다듬어 재검사를 줄였습니다.

적용 모델은 v2이고 개발 외관 F1은 0.8844로 목표 0.90에 미달합니다. 서버에서 선정 모델의 처리 시간을 쟀고, 최종 승인 평가는 동결 뒤에 진행합니다.

## 31쪽. 최종 선별 정책

운영 정책은 v2의 품종·외관 결과와 가상 당도 구간의 조합입니다. Backend가 신뢰도와 오류, 제한시간을 확인한 뒤 정상 목적지 12개 중 하나 또는 재검사 목적지를 고릅니다. 품종 신뢰도 기준은 0.50, 외관은 0.60입니다. 선별 장치는 가상 제어로 연결했습니다.

이 조합에서 외관은 보통인데 당도가 14 이상인 칸, 부사 6번과 양광 12번이 시장에서 말하는 "못난이 사과"입니다. 모양 때문에 제값을 못 받던 사과를 맛 기준으로 따로 모아 팔 수 있습니다. 한 대형마트는 이런 상생 과일 매출이 전년 같은 기간 대비 180% 넘게 늘었고, 쿠팡은 못난이 농산물을 8천 톤 넘게 직매입했습니다. 실측 당도를 연결하면 이 칸이 바로 상품이 됩니다.

## 32쪽. 시스템 프로세스

왼쪽은 품질 MVP의 처리 흐름입니다. Simulator가 사진과 가상 당도를 보내면 AI가 판정하고 선별 목적지를 정한 뒤, 이력과 상태를 관제에 표시합니다. 오른쪽은 출품부터 배송까지의 확장 흐름이고, 점선은 가상 시연의 연결입니다.

## 33쪽. 소프트웨어 아키텍처

품질 관제는 Next.js 웹이 QC Backend를 1초마다 조회하는 구조입니다. Backend는 Inference에 사진을 보내 결과를 받고 선별 정책을 적용하며, 검사 이력은 MySQL에 저장합니다.

물류 API와 MongoDB는 확장 구성으로 따로 있고, 거래·배송 화면은 브라우저 가상 모드로 돌아갑니다. 서버 관제에서 자동 경매를 켜면 QC 이력을 브라우저의 가상 상태로 가져와 씁니다.

## 34쪽. 실행·배포 아키텍처

서버컴의 Docker Compose는 품질 네 개와 물류 세 개, 모두 일곱 컨테이너입니다. 모델 파일은 Inference 이미지에 넣고 DB와 Simulator 위치, 로그는 볼륨에 둡니다. dev에 올리면 Jenkins가 Python·웹 시험을 먼저 돌리고, 통과한 버전만 빌드해 배포합니다. 배포 뒤 상태 확인에 실패하면 직전 이미지로 자동 복구하고, 서버에서 실패를 일부러 넣어 이 동작을 확인했습니다.

오류 로그는 서비스별 현재 파일 하나와 백업 다섯 개로 순환합니다. Simulator는 재시작해도 재생 위치를 이어 갑니다.

## 35쪽. 최종 시연 구성

시연은 사과 12장 입력, 품종·외관 판정, 재검사 분기, 이력·통계 순서로 품질 MVP를 보여드립니다. 화면은 농장 한 곳 전용 관제 화면입니다. 모니터를 계속 보고 있지 않아도 지나가며 한눈에 보이도록 오늘 저장 검사와 재검사율을 크게 두고, 손이 가야 하는 재검사·오류 사과를 좌상단에 놓았습니다. 시스템 상태는 색으로 표시하고, 처리 중 사과는 정상 작동 확인용으로 우하단에 작게 두었습니다. 라인 속도는 2초·순차 한 개입니다.

이어서 브라우저 예시로 거래·배송 가상 흐름을 짧게 보여드립니다. 장애 시연은 공용 서버와 분리된 환경에서 합니다.

> 진행자 메모: 실제 화면 조작은 10-08 시연 대본을 따른다. 서버 연결이 안 되면 10-05 저장 캡처와 사전 준비한 브라우저 예시로 전환한다고 먼저 말한다.

## 36쪽. 구현 범위와 남은 검증

모델, Backend, 웹, 배포가 실제 서버에서 연결돼 있습니다. 모델은 보정한 v2를 서비스합니다. Backend는 판정과 12+1 선별, 검사 이력, 검수 사진, 라인 속도 기한을 구현했고 통합시험(BE-10)을 DB 장애·보존·CSV·화면 연동까지 마쳤습니다. 화면은 처리 중 사과 12장과 검수 이미지, 처리량 추이를 실제 데이터로 보여주고, 서버 화면을 3시간 25분 띄워 둬도 메모리가 늘지 않았습니다. 배포는 시험 통과 후 배포, 실패 시 복구, 위치 복구와 로그 순환을 서버에서 확인했고, 수용시험 자동화 스크립트도 준비했습니다.

남은 일정은 10월 12일 정상 100건·장애 5종 수용시험, 13일 기능 동결, 그 뒤 최종 Test 1회와 모델 카드입니다.

## 37쪽. 측정 조건별 결과

결과마다 날짜, 입력, 구간을 함께 적었습니다. 9월 30일 실제 사진 12장으로 잰 추론 서버 내부 시간은 p95 309밀리초입니다. p95는 요청의 95%가 그 시간 안에 끝난다는 뜻입니다. 10월 5일 운영 이력 200건 기준으로 2초 간격에서 초당 0.50건을 처리합니다. 처음 목표였던 초당 2건에는 미달입니다.

추론 제한시간을 고정 500밀리초에서 라인 속도와 같게 바꾸자, 하루 4.1%이던 시간 초과가 적용 후 535건 동안 0건이 됐고, 그 사이 배포 두 번에도 0이었습니다. 신뢰도 보정은 개발 표본의 재검사를 23.7%에서 16.4%로 줄였고, 운영 이력의 재검사는 9.5%였습니다.

관제 화면은 10월 6일 서버에 3시간 25분 띄워 두고 30초마다 메모리를 쟀습니다. 30분마다 정리한 뒤의 메모리가 6.8에서 8.7MB 사이를 유지했고, 그사이 재배포 네 번과 탭 숨김 두 번에도 새로고침 없이 스스로 복구했습니다.

## 38쪽. 문제 해결 사례

문제를 만나면 먼저 재고, 원인을 나누고, 고친 뒤 다시 쟀습니다. 재검사가 많았던 문제는 모델을 다시 학습하지 않고 신뢰도 보정으로 줄였습니다. 추론이 느렸을 때는 병목이 사진 해제라는 걸 찾아 병렬로 바꿨습니다. 설정은 초당 2건인데 실제는 0.63건이던 문제는 처리 주기에 맞춰 2초 간격으로 바꿨습니다.

입력 간격을 바꾼 뒤에도 500밀리초 제한시간이 남아 있었습니다. 하루치 이력을 10분 단위로 나눠 보니 조용한 시간엔 0%, 빌드 중엔 8.8%였고, 근거가 사라진 숫자라는 걸 확인해 제한시간을 라인 속도와 같게 바꿨습니다. 처리 중 사과가 화면에 잘 안 뜨던 문제는 사진 한 장이 1.66메가바이트라는 걸 재서 축소본으로 바꾸고 조회 주기를 맞춰, 들어온 사과를 모두 보여주게 했습니다. 계약 변경으로 Jenkins 웹 시험이 실패했을 때는 배포가 멈췄고, 실패 시 기존 버전을 유지하는 설계 덕분에 서비스는 계속 돌았습니다.

## 39쪽. 이슈 기반 협업과 AI 에이전트

저희 팀은 네 명이 데이터·모델, 화면, Backend, 배포를 나눠 맡고, 각자 AI 코딩 에이전트와 함께 작업했습니다. 처음에는 결과와 요청을 디스코드 메시지로 주고받았는데, 메시지가 흘러가면서 누가 맡았고 끝났는지 추적하기 어려웠습니다. 필수 요구사항인 처리 중 사과 표시가 담당 없이 남아 있다가 서버 화면에서야 드러난 일도 있었고, 에이전트가 지시 없이 PR을 올려 되돌린 일도 있었습니다.

그래서 10월 1일부터 Git Issue로 바꿨습니다. 제목에 담당 파트와 WBS 번호를 쓰고 파트·종류·우선순위 라벨을 붙입니다. 담당 에이전트는 착수 댓글로 계획을 남기고, 사람이 확인한 뒤에 작업합니다. 이슈 본문은 요청으로 다루고, 푸시와 이슈 종료는 사람이 합니다. 결과는 수치와 다른 파트 영향까지 댓글로 남기고, 사람이 PR을 병합하면 이슈가 닫힙니다.

첫 이틀 동안 이슈 16건을 만들어 12건을 닫았고, 멘토링 피드백은 다음 날 아침 이슈 6건으로 나눠 그중 3건을 약 한 시간 만에 병합했습니다. 사람과 에이전트가 같은 이슈를 보고 움직이니 동기화 비용이 크게 줄었습니다.
