### 1. 신뢰도 보정으로 재검사 줄이기

- **상황:** 모델은 대부분 맞히는데 신뢰도가 낮게 나와 기준(0.50) 미만 재검사가 많았다. 개발 데이터(OOF) 기준 재검사 23.7%.
- **원인:** 모델 출력 확률이 실제 정답률과 맞지 않았다. 품질 신뢰도 보정 오차(ECE) 0.259.
- **해결:** 온도 보정. 품질 T=0.391, 품종 T=0.384로 확률을 다시 계산했다. 예측 라벨은 그대로이고 신뢰도만 실제 정답률에 맞춘다. 가중치 파일(`model.pt`)은 바꾸지 않고 설정 파일(`model.json`)만 바꿨다(체크섬 동일).
- **임계값:** 보정 후 품종 0.50, 품질 0.60으로 다시 골랐다.
- **결과:**

| 항목 | 보정 전 | 보정 후 |
|---|---:|---:|
| 품질 ECE | 0.259 | 0.081 |
| 개발 데이터 재검사율 | 23.7% | 16.4% |
| 자동 처리 건 품질 정확도 | 92.2% | 92.9% |
| 시연 36묶음 재검사율 | 13.9% | 8.3% |

- **발표 포인트:** 모델을 다시 학습하지 않고, 확률을 실제 정답률에 맞추는 것만으로 재검사를 3분의 1 줄였다. 자동 처리 정확도는 떨어지지 않았다.
- 근거: [DM-08](../wbs/[DM-08]%20신뢰도·병렬%20처리%20기준.md), [보정 결과](../wbs/results/v2-calibration-oof-20260930.json)

### 2. 비교 기준값 버그

- **상황:** 보정 보고서의 "현재 임계값 기준" 행은 보정 전 모델 상태를 보여줘야 한다.
- **원인:** 이 기준값을 보정 전 확률이 아니라 보정 후 확률로 계산하고 있었다. 보정 전후 비교가 성립하지 않았다.
- **해결:** 기준값을 온도 1.0(보정 전)으로 계산하도록 고치고, 같은 실수를 막는 회귀 시험을 추가했다.
- **발표 포인트:** 결과가 좋아 보여도 나빠 보여도 비교 기준부터 검증했다.

### 3. 느린 곳은 모델이 아니라 사진 해제

- **상황:** 추론 한 건 시간을 줄여야 했다.
- **발견:** Inference 응답에 `Server-Timing` 헤더를 넣어 사진 해제·모델·전체 시간을 나눠 봤다. 클라우드 2 vCPU에서는 PNG 12장 해제가 모델 계산보다 3~4배 오래 걸렸다.
- **해결:** 12장을 병렬로 해제한다. 동시 요청 수는 늘리지 않는다(2로 올리면 같은 CPU를 나눠 써서 p95 528ms로 오히려 느려짐).
- **결과 (서버컴, 실제 시연 사진 36묶음):** 해제 p95 149ms, 모델 p95 161ms, 전체 p95 309ms, 500ms 초과 0건.
- **측정 중 문제:** Jenkins 자동 재배포가 측정 도중 두 번 일어나 연결이 끊겼다. 3분간 상태가 안정된 것을 확인한 뒤 다시 쟀고, 스크립트가 실패 요청을 기록하게 바꿨다.
- **발표 포인트:** 감으로 모델을 바꾸기 전에 단계별 시간을 먼저 쟀고, 병목이 모델이 아니었다.
- 근거: [서버컴 서버 내부 지연](../wbs/results/server-real-photos-20260930.json)

### 4. 실제 Backend에 붙여 보니 나온 결함 4건

- **상황:** 화면은 예시 데이터로 다 동작했지만 실제 Backend·DB·모델과 붙인 적은 없었다.
- **방법:** 웹을 실제 Backend에 연결해 500ms 간격으로 3,600건을 넣고(31.5분), MySQL과 Inference를 일부러 멈췄다.
- **확인된 정상 동작:** 브라우저 메모리 안정(heap 중앙값 22~23MB, DOM 노드 2,074개 고정), DB 50초 중단 시 "마지막 수신 시각·기존 화면 유지" 경고 후 재시작 2초 뒤 자동 복구, 장애 이미지 100장 상한 유지.
- **발견한 결함:**
  1. DB가 멈추면 선별도 멈춘다(7~8초 뒤 HTTP 500). 요구사항은 "DB가 죽어도 선별은 계속"
  2. 현재 처리량이 실제보다 낮게(0.0) 표시된다
  3. Inference 연결 실패가 "시간 초과"로 기록된다
  4. Inference 상태가 항상 "알 수 없음"
- **작은 표시 수정:** 신뢰도가 `66.10390000000001%`처럼 보여 소수 첫째 자리로 고쳤다.
- **후속 (10-02):** DB 중단 시 선별 지속(LKG, PR #37·#52), 현재 처리량 표시(최근 10초 평균, #49), Inference 상태 표시(#37)는 해결했다. Inference 연결 실패가 시간 초과로 기록되는 건(QA KI-3)은 추적 중이다.
- **발표 포인트:** 예시 데이터로 통과한 기능도 실제 장애를 일으켜 보고 나서야 결함이 드러났다.
- 근거: [FE-08](../wbs/FE-08.md), [연속 관제 기록](../wbs/results/fe-long-run-real-backend-20260930.json), [협업 요청](../wbs/협업공지/파트별-협업-요청.md)

### 5. 결정되지 않은 범위를 시연 가능하게 만들기

- **상황:** 물류(출품·경매·배차)를 MVP에 넣을지 목요일(10-01)에 결정한다. 그 전에 시연은 가능해야 했다.
- **해결:** 물류 서버 없이 브라우저 안에서 같은 규칙으로 도는 가상 물류로 바꿨다. 실제 API 모드는 설정 하나(`NEXT_PUBLIC_LOGISTICS_MODE=live`)로 되돌릴 수 있다.
- **발표 포인트:** 결정을 기다리며 멈추지 않고, 어느 쪽으로 결정돼도 버릴 코드가 없게 만들었다.

### 6. "배포 성공"인데 입력이 0건

- **상황:** Simulator를 배포했고 Jenkins도 성공했는데 오늘 검사가 0건이었다.
- **발견:** 관제 상태(snapshot)에서 Simulator `stopped`, `running=false`를 확인했다. 기본값이 정지라 누군가 켜야 입력이 시작됐다. health는 프로세스가 살아 있는지만 봤다.
- **해결:** 기동 시 데이터와 재생 위치를 검증한 뒤 자동 재생한다. health는 "재생 중이고 최근 30초 안에 검사 전송이 성공했는지"를 보고, Jenkins 배포 검증도 같은 조건을 쓴다.
- **발표 포인트:** "컨테이너가 떠 있다"와 "서비스가 일을 하고 있다"는 다르다. 배포 성공 기준을 실제 동작으로 바꿨다.
- 근거: [Simulator 배포 문서](../wbs/reference/MO/simulator-deployment.md)

### 7. 부분 성능과 전체 성능은 다르다

- **상황:** 추론 서버 안에서는 한 건 271ms라 초당 3.7건이 가능해 보였다. 목표는 초당 2건.
- **발견:** Simulator를 실제로 돌린 뒤 운영 이력 200건의 요청 간격을 분석했다. 실제 처리량은 **초당 0.63건**이었다. 한 건 왕복이 약 1.4초다.
- **원인:** 모델 계산은 150ms뿐이다. 나머지는 13.8MB 사진 묶음을 Simulator→Backend→Inference로 두 번 넘기고 두 번 해석하며 DB에 저장하는 시간이다. 입력 간격(500ms)이 처리 주기보다 짧아 요청이 계속 밀렸다.
- **해결:** 입력 간격을 처리 주기 p90(1.8초)보다 긴 2000ms로 맞췄다. 설정한 속도와 실제 속도가 같아지고 요청이 쌓이지 않는다.
- **결과:** 시연 처리량 초당 0.5건. 초당 2건 목표는 현재 구조의 서버컴에서 미달로 기록했다.
- **재측정 (10-01, 배포 후):** 152건 연속에서 초당 0.50건, 시작 간격 p50 2.003초·p90 2.111초, 시간 초과 0건. 설정한 속도와 실제 속도가 같아졌다.
- **발표 포인트:** 부품별 벤치마크(초당 3.7건)만 보고 통과라고 하지 않고, 전체 흐름을 재서 실제 한계(0.63건)를 찾았다. 목표 미달도 숫자 그대로 밝힌다.
- 근거: [DM-08 운영 경로 처리량](../wbs/[DM-08]%20신뢰도·병렬%20처리%20기준.md), [Simulator 처리량](../wbs/results/server-simulator-throughput-20260930.json)

### 8. 이슈 기반 협업과 AI 에이전트 동기화

- **상황:** 4명이 데이터·모델(DM), 화면(FE), Backend(BE), 배포(MO)를 나눠 맡고, 각자 AI 코딩 에이전트와 작업한다. 작업 결과와 파트 간 요청은 디스코드 메시지로 정리했다.
- **문제:**
  - 메시지가 흘러가서 누가 맡았는지, 끝났는지 다시 찾기 어려웠다.
  - 필수 요구사항 FR-20(처리 중 사과 표시)은 담당 이슈 없이 남아 있다가, 10-01 서버 관제 화면에서 "처리 중 사과"가 비어 있는 걸 보고서야 드러났다(snapshot `jobs: []` 고정).
  - 에이전트마다 대화 맥락이 달라서, 다른 파트가 무엇을 바꿨는지 사람이 매번 옮겨 줘야 했다.
- **해결 (Issue #39, 10-01 채택):**
  - **제목:** `[담당][WBS] 한 줄 요약` (예: `[BE][FR-20] 처리 중 사과를 관제 snapshot jobs로 전송`)
  - **라벨 3종:** 파트 `DM` `FE` `BE` `MO` / 종류 `요청` `버그` `결과` `결정` / 우선순위 `P1`~`P3`. 에이전트는 라벨로 자기 이슈를 찾는다.
  - **양식 4종:** 작업 요청, 버그, 작업 결과(디스코드 정리 대체: 한 일·수치·다른 파트 영향·남은 일), 결정 요청.
  - **에이전트 댓글:** `**[FE 에이전트] 착수**`(계획) → `**[FE 에이전트] 결과**`(바꾼 것·테스트·PR 번호).
  - **종료:** 코드 변경은 PR 본문 `Closes #번호`로 병합 시 자동 종료. 측정·확인 이슈는 요청자가 결과를 보고 닫는다.
  - **에이전트 작업 지침:** 모든 작업·커밋·푸시·PR 전에 열린 이슈와 새 댓글을 먼저 확인한다.

### 10. 멘토링 피드백을 하루 만에 화면에 반영

- **상황:** 10-01 멘토링에서 "처리 현황 시각화의 가독성이 떨어지고 빈 공간이 많다", "정상 판정은 실시간으로 볼 필요가 적다", "낙찰 → 결제 → 배송 흐름이 보여야 한다"는 의견을 받았다.
- **원인:** 30초·1초 막대는 최대 4건/초 기준이라 운영 속도 0.5건/초에서 거의 비어 보였다. 서버가 처리 중 검사를 보내지 않아(#53) 처리 중 사과 패널도 비어 있었다.
- **해결 (#54·#58, PR #60·#61):**
  - 처리 중 사과 패널은 처리 중 이미지 전용 자리로 둔다. 빈 공간을 메우려고 완료된 판정 카드를 넣었다가, 의미가 섞여 뺐다(#61). 실제 처리 중 이미지는 #53으로 채운다.
  - 최근 판정 표를 **재검사·오류 사과** 목록으로 바꿨다. 사유(품종·품질 신뢰도 미달, 추론 시간 초과 등)와 기준 미달 신뢰도를 강조한다. 설비 쪽 오류는 시스템 상태 패널의 "설비·연동 오류"로 역할을 나눴다.
  - 처리 현황 막대를 **Chart.js 선그래프**로 바꿨다. 최근 5분 처리량(20초 이동평균)에 설정한 라인 속도를 점선으로 겹쳐, 선이 점선 아래로 내려가면 라인이 속도를 못 따라간다는 게 보인다. 재검사·오류 시점은 점으로 찍는다.
  - 자동 경매 시연에 결제 완료(가상) 단계를 넣었다.
- **결과:** 피드백 다음 날 오전에 병합. 서버 관제 화면에서 처리량 선이 설정 속도 0.5건/초를 따라가는 것을 확인했다.
- **발표 포인트:** 시각화의 기준을 "데이터가 있다"가 아니라 "운영자가 지금 무엇을 해야 하는지"로 바꿨다.
- 근거: [QA-WEB-03·05](../wbs/reference/ALL/qa-test-cases.md), PR #60

### 11. 처리 중 사과 사진이 뜨기 전에 사라짐

- **상황:** 10-02 오전, 처리 중 사과 12장을 관제 화면에 보내는 기능(#53, PR #62)을 서버에 배포했다.
- **발견:** 12장 중 상당수가 화면에 뜨기 전에 `410 IMAGE_EXPIRED`가 됐다(샘플 4회 만료 0·2·6·11장). 사진 1장을 직접 받아 보니 원본 PNG **약 1.66MB**였다.
- **원인:** 사과 1개 약 20MB를 2초마다 브라우저로 받아야 했다. 처리(약 1.4초)가 끝나면 사진이 바로 만료되고, 관제 화면은 1초마다 조회하므로 늦게 본 사과는 남은 시간이 더 짧았다.
- **해결:**
  - Backend: 미리보기만 긴 변 240px JPEG로 줄이고(원본은 그대로 추론에 사용), 완료 후 3초 동안은 조회를 허용(#83)
  - 화면: 처리가 끝나도 다음 사과가 들어올 때까지 마지막 사과 12장과 판정 결과를 남겨, 패널이 비었다 채워지며 흔들리던 것도 없앰(#84)
- **결과:** 장당 평균 13.3KB(약 1/120). 서버 화면 30초 측정에서 12장 모두 표시, 만료 0칸.
- **발표 포인트:** 화면에서 "가끔 안 뜬다"를 실제 크기 측정으로 바꿔 원인을 찾았다. 화면 쪽 임시 처리 대신 원인(전송량)을 줄이는 쪽으로 파트 간 합의했다.
- 근거: Issue #53, PR #83·#84

### 12. 배포 안전장치를 넣다가 배포가 막힘

- **상황:** 10-02 MO가 Jenkins에 Python·웹 테스트 단계와 "배포 실패 시 이전 버전 복구"를 넣었다(#69, PR #78).
- **문제:** 이후 빌드 5번(#73~#77)이 연속 실패했다. 단계마다 첫 오류가 달랐다.
  - 테스트 컨테이너에서 `requirements-backend-dev.txt`를 못 찾음
  - `No module named 'src'`
  - 시뮬레이터 시간 검사가 서버컴 디스크 지연으로 흔들림
  - 테스트를 고친 뒤에는 배포 스크립트가 `snapshot-compose.py`를 못 찾음
- **원인:** Jenkins가 컨테이너 안에서 서버컴의 Docker를 빌려 쓰는 구조라, `docker run -v "$PWD/..."`의 작업 폴더 경로를 **호스트에서** 찾는다. 호스트에는 그 경로가 없어 빈 폴더가 마운트됐다.
- **해결:** 테스트는 `docker cp`로 작업 폴더를 복사, `python -m pytest`로 import 경로 해결, 시간 검사는 가상 시계로 고정(#81). 배포 스크립트도 마운트를 없앰(#82).
- **결과:** #78·#79 빌드 성공(Python 287개·웹 46개 통과). 실패하는 동안에도 배포 전 단계에서 멈춰서 서버는 마지막 성공 버전(#72)을 그대로 운영했다.
- **발표 포인트:** 실패 시 이전 버전을 유지하는 설계가 실제 실패에서 서비스를 지켰다. 로컬에서 통과한 테스트도 실제 CI 환경(컨테이너 안의 Docker)에서는 경로 가정이 깨질 수 있다.
- 근거: Jenkins CQC-CICD #73~#79, Issue #69, PR #78·#81·#82

### 발표 흐름 제안

1. **측정 → 원인 → 조치 → 재측정** 순서를 하나의 패턴으로 보여준다(사례 3·7).
2. 모델 개선은 재학습 없이 보정만으로 얻은 효과를 강조한다(사례 1).
3. "예시 데이터로 통과"와 "실제 환경에서 통과"를 구분한 태도를 보여준다(사례 4·6).
4. 목표 미달(초당 2건)은 숨기지 않고 원인과 다음 개선 방향(사진 전달 방식)을 함께 말한다(사례 7).
5. 마지막은 기술이 아니라 협업 문제로 마무리한다. AI 에이전트 시대의 병목은 동기화였고, Git Issue를 사람과 에이전트의 공통 작업 큐로 만들어 풀었다(사례 8·9). 포트폴리오에서도 이 사례를 앞에 둔다.
