## 1. 프로젝트 효과 조사

### 1.1 해결하려는 문제

농산물 품질 판정은 크기, 형태, 외관 상태, 품종과 촬영 조건처럼 여러 시각 요소를 함께 고려해야 한다. 작업자가 많은 물량을 반복해서 검사하면 판정 속도와 일관성이 작업 환경과 숙련도에 영향을 받을 수 있다. 단순 색상 임계값이나 크기 기준만으로는 조명, 촬영각도, 배경, 개체 차이를 안정적으로 처리하기 어렵다.

한 달 프로젝트에서는 실제 유통 등급 판정을 완전히 대체한다고 주장하지 않는다. AI Hub가 제공하는 품질 등급 라벨을 기준으로 제한된 환경의 이미지 분류 모델을 만들고, 모델이 확신하지 못하는 입력을 사람이 확인하도록 분리한다. 이를 통해 자동 판정이 가능한 구간과 사람이 개입해야 하는 구간을 함께 보여준다.

### 1.2 As-Is / To-Be

| 구분 | As-Is | To-Be |
|---|---|---|
| 품질 확인 | 작업자가 이미지를 보고 등급을 반복 판정 | AI가 사과의 특·상·보통 등급과 신뢰도를 제시 |
| 판정 기준 | 작업자 경험과 개별 기준에 따라 차이가 생길 수 있음 | 동일 모델과 전처리 규칙으로 일관된 기준 적용 |
| 예외 처리 | 애매한 개체도 즉시 등급을 정해야 함 | 낮은 신뢰도 결과를 별도 검수 대상으로 분리 |
| 선별 작업 | 판정 후 사람이 분류 위치를 다시 결정 | 예측 등급에 따라 선별 목적지 신호를 자동 생성 |
| 결과 기록 | 판정 근거와 처리 결과가 흩어질 수 있음 | 입력, 예측 등급, 신뢰도, 처리 시각을 한 흐름으로 기록 |
| 모델 검증 | 전체 정확도만 보면 소수 등급 실패를 놓칠 수 있음 | 등급별 Precision·Recall·F1과 혼동행렬로 오류 확인 |

### 1.3 예상 사용자와 사용 장면

| 사용자 | 사용 장면 | MVP에서 제공할 기능 |
|---|---|---|
| 선별 작업자 | 자동 입력된 사과의 등급과 분류 위치 확인 | 품종·등급·신뢰도 표시, 선별 목적지 안내 |
| 품질 관리자 | 애매한 사례와 운영 오류 검토 | 저신뢰·오판 의심 표시, 이력·통계·장애 이미지 관리 |
| 농가·구매자·물류 관제자 | 출품부터 낙찰·배송까지 흐름 확인 | 출품·입찰 역할 전환, 배차·배송 관제 시연 |
| 시연 관람자 | 자동화 흐름 이해 | 자동 입력부터 선별 신호까지 한 화면에서 확인 |

실제 생산라인 운영자, 농가와 유통업체를 대상으로 한 현장 요구사항 조사는 아직 수행하지 않았다. 위 사용자는 MVP 시나리오를 정의하기 위한 가정이다.

## 2. AI 분석 데이터 조사

### 2.1 데이터 개요

[AI Hub 공식 소개](https://aihub.or.kr/aihubdata/data/view.do?aihubDataSe=data&dataSetSn=149&topMenu=103)를 2026-09-29 재확인한 내용은 다음과 같다. 아래 규모와 공개 모델 점수는 전체 제공 데이터에 관한 것이며 CQC가 확보한 사과 부분집합의 성능과 직접 비교하지 않는다.

- 분야: 농축수산
- 유형: 이미지
- 구축년도: 2020년
- 구축량: 정제·가공된 데이터 30만 건
- 원시 수집량: 10개 품목별 6만 건, 총 60만 건
- 대상 품목: 무, 배추, 양파, 마늘, 양배추, 감, 사과, 배, 감귤, 감자
- 품질 분류: 특, 상, 보통
- 이미지 형식: PNG
- 메타데이터 예시: 작물·품종, 촬영각도, 촬영장비·장소·날짜, 크기, 부피
- 라벨 항목 예시: 종 ID, 과일 종류, 품질 등급, 촬영면, 수직·수평 촬영각도, 높이, 너비, 무게
- 공개 기준모델: Inception V3 이미지 분류
- 공개 성능: F1-Score 0.89
- 다운로드: 소개 페이지에 다운로드 기능과 API 파일 목록이 제공되며, 데이터 신청과 승인 절차가 필요하다.

페이지 상단의 20종 표현과 상세 설명의 10개 품목 목록은 다르다. CQC의 실제 확보·학습 범위는 아래 로컬 데이터 점검 결과를 기준으로 한다.

### 2.2 MVP 품목 선정

#### 현재 범위: 사과 품종 2종

- 현재 확보된 이미지는 사과 데이터다.
- 사과 전체 품종을 한 범주로 합치지 않고, 확인된 **부사와 양광 2종**을 데이터 범위로 둔다.
- 두 품종 모두 특·상·보통 라벨을 확보했다. 총 25,024개 이미지·JSON 쌍, 독립 사과 `group_no` 179개다.
- 품종별 촬영 조건과 등급 분포 차이가 모델 판단에 미치는 영향을 따로 분석한다.
- 실제 파일과 라벨을 확인한 결과 품종은 **부사와 양광**으로 확정한다.

품종과 외관 등급은 모두 필수 예측 대상이다. 공유·분리 구조와 4·8·12·16·40장 입력의 50개 교차검증 실험을 비교해 `separate`·대표 12장을 선택했다. 현재 기능 연동 후보는 `cqc-apple-separate12-focal-v2-candidate`이며 구조 선택과 품질 승인은 구분한다.

#### 두 번째 품목 확장 조건

다음 조건을 모두 만족할 때 두 번째 농산물 품목을 추가한다.

1. 사과 품종 2종의 데이터 로더와 학습 파이프라인이 재현 가능하게 동작한다.
2. 두 품종에 대한 3등급 기준선과 품종별 오류 분석이 완료된다.
3. 후보 품목의 등급별 표본 수와 라벨 구조를 확인한다.
4. 품목 추가가 4주차 통합과 발표 준비를 방해하지 않는다.

두 번째 품목은 아직 정하지 않는다. 전체 지원 범위는 사과를 포함해 최대 2개 품목이다.

### 2.3 입력과 예측 대상

| 구분 | MVP 정의 | 확인 상태 |
|---|---|---|
| 입력 | 동일 사과의 다각도 이미지 묶음 | Simulator가 시연 전용 목록의 사전 구성 12장을 전송 |
| 보조 정보 | 촬영면·수직·수평 각도 메타데이터 | Simulator의 대표 프레임 선택과 Inference 입력 검증·추적에 사용 |
| 정답 | 부사·양광 품종과 특·상·보통 품질 등급 | 학습·평가에 사용하고 서비스 모델 입력에서는 제외 |
| 출력 | 예측 품종·품질등급, 각 확률·신뢰도, 시연용 가상 당도와 출처 | 기획 확정 |
| 자동화 출력 | 품종 2종 × 외관 3단계 × 가상 당도 2단계의 정상 12 bin 또는 재검사 bin | 시연용 분기 코드 존재; DB seed·Simulator·저장 연동 대기 |
| 설명 정보 | 모델 주목 영역 시각화 | 구현 여유에 따른 확장 |

첫 기준선은 부사와 양광 이미지를 입력으로 사용하여 품종 라벨과 품질 라벨을 각각 예측한다. 서비스 추론에는 정답 품종·품질과 `group_no`를 모델 입력으로 전달하지 않는다. 당도는 실측값이 없는 현재 데이터에서 판정하지 않으며, 별도 가상 센서가 만든 `virtual_brix`를 `brix_is_measured=false`와 함께 시연한다. 이미지 단독 기준선과 가상 당도를 결합한 late-fusion 실험은 분리 평가한다.

### 2.4 가장 중요한 데이터 누수 위험

공식 설명은 한 농산물을 여러 카메라 위치와 각도에서 반복 촬영한 구조를 보여준다. 같은 개체의 여러 이미지가 학습 데이터와 시험 데이터에 나뉘면 모델이 품질 일반화 대신 동일 개체의 특징을 기억하여 성능이 부풀 수 있다.

실제 라벨의 `group_no`로 사과를 식별하며 한 사과의 사진은 같은 분할에 둔다. seed 42 기준 학습 125개·검증 27개·시험 27개이며, 학습·검증을 합친 개발 사과 152개에 5-fold 교차검증을 적용한다. 최종 재학습에는 개발 사과만 사용한다.

시연 사진은 기존 학습에서 선택될 수 있었던 프레임을 제외해 구성했지만 같은 실제 사과의 다른 사진이다. 따라서 시연 묶음은 신규 사과의 독립 평가 데이터가 아니다. 기존 Test 27개도 결과를 확인한 뒤에는 후속 모델의 독립 승인에 재사용하지 않는다.

### 2.5 데이터 품질 점검

| 점검 대상 | 점검 내용 | 산출물 |
|---|---|---|
| 파일 | 손상, 확장자, 해상도, 읽기 실패 | 파일 검사 보고서 |
| 라벨 | 누락, 알 수 없는 등급, 이미지와 라벨 불일치 | 오류 목록 |
| 분포 | 품목·품종·등급·각도별 건수 | 분포표와 그래프 |
| 중복 | 동일 파일 해시, 유사 이미지, 동일 개체 촬영 | 중복 후보 목록 |
| 배경 | 등급과 배경·촬영장소의 우연한 연관 | 샘플 비교 및 오류 분석 |
| 분할 | 같은 개체가 여러 세트에 포함되는지 확인 | 분할 검증 결과 |

### 2.6 반드시 공개할 한계

- AI Hub 품질 등급은 제공 데이터의 기준이며, 모델 결과가 실제 유통 현장의 공식 등급 판정을 보증하지 않는다.
- 촬영 장비와 배경이 통제된 데이터라면 휴대전화나 현장 컨베이어 이미지에서 성능이 낮아질 수 있다.
- 품질 등급 차이를 만드는 세부 기준과 품종별 기준을 실제 라벨 설명서에서 추가 확인해야 한다.
- 표면에 보이지 않는 당도, 내부 손상과 맛을 RGB 이미지 한 장으로 직접 판단할 수 없다.
- 현재 확보한 표본 수와 품종·품질 분포는 `docs/wbs/reference/DM/data-spec.md`에 기록했으며, 그룹 수가 적은 조합의 성능 변동성을 함께 공개해야 한다.
- 물리 선별기를 연결하지 않으면 선별 자동화는 소프트웨어 신호와 화면 시뮬레이션 수준이다.
- Grad-CAM 같은 시각화는 모델이 본 영역을 설명하는 보조 자료이며 품질 판정의 인과적 근거가 아니다.

발표 표현은 **“AI Hub 이미지 라벨 기준 사과 품질 등급 판정과 선별 흐름 자동화 MVP”**로 통일한다.

### 2.7 분석 및 모델 작업 기준

1. 데이터 설명서와 실제 파일 구조를 비교한다.
2. 사과 이미지만 추출하고 품질 등급 라벨을 정규화한다.
3. 품종, 등급, 촬영각도와 개체 그룹 후보의 분포를 분석한다.
4. 이미지 손상, 라벨 누락과 중복 후보를 제거하거나 별도 기록한다.
5. `group_no` 단위로 학습·검증·시험 세트를 분리하고 교차 포함을 검사한다.
6. 사전학습 이미지 분류 모델로 기준선을 만든다.
7. 클래스 불균형이 확인되면 가중치 또는 샘플링을 비교한다.
8. 밝기, 회전, 크롭 등 증강은 실제 촬영 조건을 벗어나지 않는 범위로 제한한다.
9. 전체 정확도와 Macro F1, 등급별 Precision·Recall·F1, 혼동행렬을 기록한다.
10. 저신뢰 임계값별 자동 판정 비율과 오분류 비율을 비교한다.
11. 실제 시연 입력과 학습 데이터 간 차이를 오류 사례로 정리한다.

### 2.8 기준선 모델 후보

| 후보 | 역할 | 장점 | 주의점 |
|---|---|---|---|
| 단순 다수 클래스 예측 | 최소 기준 | 데이터 불균형 영향 확인 | 실제 이미지 학습 모델 아님 |
| MobileNetV3 Small 공유 특징 | 비교한 기준선 | 품종·외관 예측에서 특징 추출기 공유 | 분리 모델과 검증 성능 비교 |
| 품종·외관 분리 모델 | 현재 선택 구조 | 두 분류의 특징 추출기를 분리 | 대표 12장, CPU 처리시간 확인 |
| 이미지+가상 당도 결합 | 시연용 비교 실험 | 보조 입력 결합 흐름 검토 | 실제 당도 활용 효과로 해석하지 않음 |

#### 현재 다각도 그룹 모델

AI Hub의 공식 촬영 설명은 여러 카메라 위치와 회전 각도로 동일 농산물을 촬영하는 구조다. CQC는 동일 `group_no`를 하나의 사과 묶음으로 사용한다. 촬영 사진 수와 모델이 사용할 대표 사진 수는 구분한다.

다만 상용 장비의 촬영 프레임 수를 i7-4790 CPU가 전부 CNN으로 처리한다고 가정하지 않는다. 촬영·입력 프레임 수와 실제 모델에 투입할 대표 프레임 수를 분리한다. 공유 특징 추출기와 결합 계층을 사용하고, 대표 시점 수에 따른 품종·품질 Macro F1과 CPU 지연을 비교하여 최종 입력 장수를 정한다.

179개 그룹 중 175개는 40장 이상이고 나머지 4개는 8·16·21·30장이다. 원본 1000×1000 RGB 40장을 모두 디코딩하면 약 114.4MiB이므로 사진 수에 따른 메모리·처리시간을 측정해야 한다. 비교 실험 결과 서비스 기본 입력은 대표 12장으로 정했다. 기본 시연은 미리 구성한 `realtime-apple-arrival-demo`의 12장 묶음을 Simulator가 읽고 Backend가 같은 순서로 중계하는 목표 흐름이다.

프레임워크는 PyTorch·torchvision, 인코더는 MobileNetV3 Small로 확정한다. 대표 12장과 품종·품질 분리 구조를 사용하며, 새 버전의 손실·epoch·승인 여부는 해당 버전의 평가 기록으로 관리한다.

### 2.9 모델 버전·가상 당도와 승인 상태

- **v1:** 개발 사과 152개로 19회차 재학습했다. 최초 Test 27개에서 품종 Macro F1 1.0000, 외관 품질 Macro F1 0.7778로 품질 승인 기준 0.90에 미달했다.
- **v2 후보:** 이미지 단독 `separate`·12장·focal 손실·4회차 모델이다. 152개 개발 사과로 재학습했으며 재사용 Test 진단 품질 Macro F1은 1.0000이다. 기존 Test를 이미 확인했으므로 독립 승인 성능이 아니고 패키지 상태는 `unverified_candidate`, 신뢰도 상태는 `not_calibrated`다.
- **당도 결합·상품등급 실험:** 가상 당도를 넣어 외관 정답을 예측하는 실험과 외관·가상 당도 60:40 정책의 합성 상품등급을 학습하는 v3 실험은 별도다. v3 상품등급 5-fold 평균 Macro F1은 0.6283이며 현재 시연의 외관 모델을 대체하지 않는다.
- **현재 선별 기준:** v2 외관 예측과 별도로 사과별 고정 가상 당도를 연결하고, 12°Brix 미만/이상으로 나눠 정상 12개 목적지를 구성한다. 60:40 상품등급 계산은 별도 시연 정책이지 12-bin의 필수 분기 기준이 아니다.
- 가상 당도는 RGB 특징과 고정 난수로 한 번 생성한 시연 데이터이며 실측이 아니다. `brix_is_measured=false`와 생성 근거를 보존한다. 실측 당도 예측이나 현장 품질 승인을 주장하지 않는다.

## 3. 서비스 및 자동화 설계

### 3.1 전체 흐름

```text
AI Hub 원본 이미지·라벨
  → 파일·라벨 검증
  → 사과 데이터 추출
  → 개체 그룹 확인 및 데이터 분할
  → 전처리·증강
  → 기준선 모델 학습·평가
  → 평가 결과·승인 상태를 포함해 후보 모델 저장

시뮬레이터가 시연 전용 묶음(`data/processed/realtime-apple-arrival-demo`)에서 읽은 12장 다각도 이미지 입력
  → multipart 형식·장수·이미지 해석 가능 여부 검증
  → Inference HTTP API 호출과 동일 전처리
  → 품종·품질 추론과 실제 사용 프레임 수 기록
  → 품종·품질 예측과 각각의 확률·신뢰도 반환
  → 두 신뢰도 임계값과 Inference HTTP 구간 500ms 판정
      ├─ 기준 이상·가상 당도 존재: 품종 2종 × 외관 3단계 × 가상 당도 2단계의 정상 목적지 생성
      └─ 저신뢰·시간 초과·추론 오류·필수 당도 누락: 재검사 대상으로 분기
  → 판정 이력과 처리 결과 기록
  → 웹 화면에 결과 표시
```

위 흐름은 통합 완료 기준이다. 현재 저장·조회와 Simulator·관제 API 연결은 남아 있다. 검사 API의 당도 입력은 현재 선택형이며 누락 시 기존 6-bin 호환 경로가 남아 있으므로, 최종 12-bin 시연에서는 필수 당도 누락 처리까지 Backend 계약을 맞춰야 한다. 정상 QC 결과를 출품 데이터로 전달한 뒤 물류 서비스의 입찰·낙찰·배차 흐름을 연결한다.

### 3.3 저신뢰 검수 정책

품종 또는 품질 confidence가 각각의 임계값보다 낮으면 자동 선별하지 않고 검수 대상으로 분리한다. 두 임계값은 임의의 숫자로 확정하지 않는다. 검증 데이터에서 여러 임계값을 비교하여 다음 항목을 함께 본다.

- 자동 판정으로 처리되는 사과 그룹 비율
- 자동 판정 구간의 정확도와 Macro F1
- 검수 대상으로 빠지는 사과 그룹 수
- 특 또는 상을 보통으로 잘못 보내는 사례
- 보통을 특으로 잘못 보내는 사례

최종 임계값은 모델 성능과 시연 목적을 함께 고려해 정하고 설정에서 변경할 수 있게 한다. 실제 검사에 적용한 품종·품질 threshold 값은 검사 이력에 기록한다.

현재 Backend 기본값은 품종·품질 각각 0.50이다. 기존 152개 검증 사과의 자동 처리 비율 98.68%·해당 구간 품종 정확도 98.67%·품질 정확도 98.00%는 [기존 신뢰도 검증 결과](wbs/results/thresholds-separate-12view.json)의 값이며 v2 후보의 신규 보정 결과로 옮겨 적지 않는다. DB 이력 기록은 목표 요구사항이며 실제 저장 연결 확인이 남아 있다.

### 3.4 선별 자동화 시뮬레이션

실제 설비와 PLC는 연동하지 않는다. Backend의 내부 가상 제어와 품질 관제의 처리 카드·상태 표시로 선별 흐름을 시연한다. 현재 품질 관제·관리 창 구성으로 FE 범위를 마무리하며, 별도 선별 애니메이션이나 추가 페이지를 필수 작업으로 늘리지 않는다.

| 판정 결과 | 목적지 수 | 화면 표시 |
|---|---:|---|
| 부사·양광 × 외관 특·상·보통 × 가상 당도 12°Brix 미만/이상 | 정상 bin 12개 | 예측 품종·외관·시연 당도 구간에 대응하는 구역으로 이동 |
| 저신뢰·시간 초과·시스템 오류 | 재검사 bin 1개 | 작업자 재검사 대기 |

목적지 이름은 장비 규격이 아니라 임시 인터페이스다. 실제 장비를 연결할 경우 신호 형식, 통신 방식, 실패 시 안전 동작을 별도 요구사항으로 정의한다.

### 3.5 논리 아키텍처

| 영역 | 책임 | 입력 | 출력 |
|---|---|---|---|
| 데이터 파이프라인 | 원본 검사, 라벨 정규화, 분할, 전처리 | 원본 이미지·라벨 | 학습용 데이터와 분할 목록 |
| 학습 파이프라인 | 모델 학습, 평가, 모델 저장 | 학습·검증 데이터 | 모델 파일과 평가 결과 |
| 추론 모듈 | 다각도 전처리와 품종·품질 예측 | 이미지 그룹 | 품종·품질 확률과 예측값 |
| 가상 당도 모듈 | 색상·균일도 특징 기반 시연값 생성 | 동일 사과 이미지 그룹 | `virtual_brix`, 불확실성, 생성기 버전, 비실측 표시 |
| 판정 정책 | 저신뢰 여부와 선별 목적지 결정 | 예측 결과 | 자동 선별 또는 검수 신호 |
| FastAPI Backend | 검사 오케스트레이션, 화면·Inference 연결과 정책 적용 | Simulator 요청·Inference 응답 | 구조화된 검사 응답 |
| Next.js 웹 | 품질 관제·이력·통계·장애 관리와 물류 화면 | 백엔드 조회·제어 API | 품종, 등급, 신뢰도, 처리 결과와 거래·배송 상태 |
| MySQL | 순환 보존 검사 이력과 통계·분석 조회 지원 | 판정 이벤트와 검사 결과 | 웹 조회용 이력·집계 데이터 |

Backend는 **Python + FastAPI**, QC 이력은 **MySQL**, 판매·물류 데이터는 **MongoDB**, 공통 웹 구현은 **Next.js·React·TypeScript**를 사용한다. QC의 ORM·초기 마이그레이션은 `src/api/db/`에 있고 실제 저장·조회 연결은 남아 있다.

QC 이력 보존 목표는 상한 86,400건 도달 시 오래된 8,640건 삭제다. 초당 2그룹이면 약 10.8~12시간을 보존한다. DB 장애에도 유효한 선별 명령은 계속 처리하고 저장 실패를 별도 상태로 표시하는 것이 목표다. 보존·삭제·장애 요구사항을 구현 완료로 표시하지 않는다.

품질 화면은 `cqc-logistics-platform/apps/web`의 `/`에 구현돼 있다. 기본 모드는 브라우저 데모이며 `CQC_QUALITY_MODE=api`에서 관제 HTTP 계약을 호출한다. 독립 참조 서버는 계약 검증용이고 실제 MySQL·Inference·설비 연결의 증거가 아니다.

### 3.6 현재 API와 추가 통합 계약

#### 시뮬레이터 → 백엔드 검사 요청

| 항목 | 설명 | 상태 |
|---|---|---|
| inspection_id | 전체 처리 흐름에서 공유할 검사 ID | 현재 검사 API 필수 |
| images | 같은 사과의 다각도 이미지 파일, 기본 시연은 사전 구성 12장 | 현재 검사 API 필수 |
| metadata | 이미지별 `view_index`, `angle_direction`, `verticality_angle`, `horizontality_angle`의 JSON 배열 | 현재 검사 API 필수 |
| virtual_brix | 사과 묶음의 고정 가상 당도, 9~18°Brix | 현재 API 선택형; 최종 12-bin 시연 연결 필요 |
| captured_at·sequence_no | 촬영·입력 시각과 Simulator 위치 관리 정보 | 현재 검사 API 필드가 아님; Simulator·저장 계약에서 필요 여부 확정 |

`1 inspection = 사과 1개 = group_no 1개`로 처리한다. 전송 형식은 Base64 JSON이 아닌 `multipart/form-data`를 사용하며 스마트폰 카메라, 사용자 이미지 파일 업로드와 실제 산업용 카메라 입력은 제공하지 않는다. `group_no`와 정답 품종·품질은 모델 입력으로 전달하지 않는다.

#### inference → 백엔드 응답

| 논리 항목 | 내용 |
|---|---|
| 검사 식별 | 요청과 동일한 `inspection_id` |
| 품종 결과 | 예측값, `fuji`·`yanggwang`을 key로 가진 확률 객체와 confidence |
| 품질 결과 | 예측값, `L`·`M`·`S`를 key로 가진 확률 객체와 confidence |
| 진단·버전 | `inference_time_ms`, 모델명·버전, 전처리 버전, 실제 사용 프레임 수 |

현재 요청 경로는 Backend의 `POST /v1/inspections`, Inference의 `POST /v1/predict`다. `virtual_brix`는 Backend 분기용 보조 값이며 현재 이미지 단독 Inference의 모델 입력이 아니다. 가상 당도의 출처·비실측 표시와 묶음 연결은 별도 인계 계약으로 유지한다.

품질 코드는 `L=특`, `M=상`, `S=보통`이다. Backend는 클래스 인덱스를 추측하지 않고 응답의 라벨별 확률을 사용한다. Inference는 예측·진단을 반환하고 저신뢰·시간초과·bin·DB·제어 정책은 Backend가 적용한다. 검사·제어·저장 상태는 각각 구분한다. 지연 결과는 현재 메모리에서 관리하며, 확정된 제어 명령을 바꾸지 않고 DB 진단으로 저장하는 연결은 남아 있다.

FE 관제용 조회·통계·CSV·시연 제어·이미지 관리 계약은 [관제 API 인계](wbs/협업공지/Frontend-관제-API-계약-인계.md)와 [관제 OpenAPI](contracts/quality-operations.openapi.json)를 따른다. 기존 검사 API와 별도이며 실제 Backend adapter 구현·대조가 필요하다.

### 3.7 판매·물류 통합 범위와 구현 원칙

프로젝트의 전체 범위는 QC 검사·선별에 판매·물류 시연을 포함한다. 전체 시연 흐름은 `QC 판정·선별 → 농가 출품 → 구매자 입찰 → 낙찰 주문 → 자동배차 → 상·하차 확인 → 배송 완료/고장 대체배차`다. 앞 절의 가상 제어는 QC 선별 단계의 최종 출력이다. 실제 결제, 차량 제어, 교통 기반 최적 경로와 실제 시장가격 예측은 제외한다.

- QC Backend와 MySQL은 검사·제어·검수 이력의 원본을 관리한다.
- `cqc-logistics-platform`의 FastAPI와 MongoDB는 출품·입찰·주문·차량·노선을 관리한다. QC DB를 대체하지 않는다.
- QC 품질 관제와 물류 화면은 같은 Next.js·TypeScript 코드베이스에 있다. 화면·참조 API 검증과 실제 QC 결과의 거래·배차 연결 완료는 구분한다.
- 결과 연결 계층에서 식별자·품질 코드·신뢰도를 변환하고 농가·수량·좌표를 보완한다. 모델은 수량이나 위치를 예측하지 않는다. 실제 연결 전에는 명시된 데모 데이터를 사용한다.
- 배차는 용량·상태 조건에 맞는 유휴 차량을 우선하고 거리 기반으로 선택한다. 유휴 후보가 없으면 적재 여유가 있는 운행 차량에 새 픽업·하차를 첫 미완료 하차 앞에 삽입한다. 모든 삽입 위치를 비교하는 최적화는 MVP 요구사항에서 제외한다.
- 앞으로도 시연에 필요한 단순한 규칙과 상태 전이를 우선한다. 프론트 화면 흐름에 따라 세부 동작은 조정할 수 있으나 적재 한도, 픽업 후 하차, 확인 게이트, 고장 차량 제외는 유지한다. 변경 시 API·문서·검증 기준을 함께 맞춘다.
- 기존 WBS의 ID·담당·일정은 유지한다. 물류 상세 작업은 별도 작업 순서 문서로 관리하며 추가 담당 배정은 팀 합의로 정한다. 모델 파트는 QC 결과 계약, 백엔드는 실제 결과 전달, 프론트는 역할별 화면, MLOps는 통합 배포 경계를 검토한다.

현재 루트 Compose는 QC 5개 서비스와 물류 3개 서비스(`logistics-mongodb`, `logistics-api`, `logistics-web`)로 구성된다. QC의 MySQL·Backend·Inference는 실제 실행 설정이고, 루트 `frontend`·`simulator`는 placeholder다. 웹 코드와 Dockerfile은 존재하며 `logistics-web` 배포와 QC 프론트 역할의 연결을 정리해야 한다. 전체 흐름 완료는 공동 수용시험으로 확인한다. 상세 기준: [물류 제품 범위](../cqc-logistics-platform/docs/01-product-scope.md), [작업 순서](../cqc-logistics-platform/docs/06-build-order.md).

### 4.2 기술 스택 확정 원칙

1. 팀원이 한 달 안에 구현하고 설명할 수 있는 기술을 선택한다.
2. 핵심 시나리오에 필요하지 않은 분산 시스템과 복잡한 MLOps 도구는 넣지 않는다.
3. GPU가 없는 환경에서도 저장된 모델로 추론할 수 있어야 한다.
4. 학습 코드와 서비스 추론이 동일한 전처리 정의를 사용한다.
5. 모델 파일, 원본 데이터와 생성 결과는 Git 저장소에 직접 올리지 않는다.

### 4.3 Git·배포 운영 기준

- `main`: 발표 전까지 일반 통합에 사용하지 않고 최종 발표 버전을 표시한다.
- `dev`: 통합과 학원 PC 자동 배포 기준 브랜치다.
- `feat/*`: 개인 기능 작업 브랜치다.
- `feat/* → dev`는 Pull Request와 최소 1명 확인 후 병합한다.
- `main`에는 자동 배포를 연결하지 않는다.

- 안정 브랜치는 `dev`이며 최종 발표 버전은 `main`으로 표시한다.
- 주요 작업 브랜치: `feat/data`, `feat/backend`, `feat/front`, `feat/mlops`, `feat/logistics` 계열. 브랜치명과 담당은 실제 작업 분리에 맞춘다.
- 한 사람이 동시에 같은 파일을 크게 수정하지 않도록 문서와 코드 소유 영역을 합의한다.
- API 요청·응답과 데이터 필드는 구현 전에 문서에서 먼저 합의한다.
- 원본 데이터, 모델 가중치와 대용량 출력은 `.gitignore`로 제외한다.
- 통합 전에는 최소 한 명이 변경 내용과 실행 결과를 확인한다.

서버 운영은 Jenkins의 SCM 변경 감지 후 Docker Compose 빌드·배포하는 흐름을 목표로 한다. 운영자가 설명한 방식은 **Poll SCM**이지만, 현재 저장소 `Jenkinsfile`의 트리거는 `githubPush()`이며 `pollSCM(...)` 선언은 없다. Job 화면에서 별도로 Poll SCM이 설정됐는지는 이번 검토로 확인하지 않았다. 실제 Job의 대상 브랜치·폴링 설정을 확인한 뒤 저장소 선언과 운영 문서를 맞춘다. 푸시만으로 배포 성공을 판정하지 않는다.

데이터 작업 순서와 일회성 실험은 [과정별 노트북](../notebooks/README.md), 공통 학습·추론 함수는 `src/`, 원격 PS1은 `scripts/remote/`에서 관리한다.

| 백엔드 담당 | 홍준희 | multipart 검사 요청, inference 조정, 상태·재검사·제어 정책, MySQL·통계·CSV·이미지 생명주기 | OpenAPI, 판정 정책, DB 설계·마이그레이션, simulator·가상 제어 | 프론트 조회 API와 MLOps가 배포할 backend·simulator 서비스 |
| MLOps·CI/CD 담당 | 홍유나 | QC 5개·물류 3개 Compose 구성, healthcheck, dev CI/CD, 모델·볼륨·로그·위치 복구, CPU 시험 환경 | Compose·CI, 배포·복구 문서, 수용시험, 모델 버전 규칙 | 네 영역을 i7-4790 환경에서 검증·실행하는 통합 기반 |

#### 역할 경계

- 데이터 분석·모델 담당은 전처리·대표 프레임 선택 규칙·모델 로딩과 `다각도 이미지 묶음 → 품종·품질 확률` Inference API까지 책임진다.
- 백엔드 담당은 FastAPI, Inference HTTP Client, 정상 12개 bin 또는 재검사 bin 정책, MySQL 이력, 내부 가상 제어와 Simulator 애플리케이션 로직을 책임진다.
- 프론트엔드 담당은 자동 검사 상태와 백엔드 조회·관리 기능을 화면으로 표현하고 Simulator 시작·정지를 제어한다. 사용자 이미지 업로드는 제공하지 않는다.
- MLOps·CI/CD 담당은 Docker·Compose·Volume·healthcheck·재시작 정책과 배포·로그 운영 환경을 책임진다.
- Backend는 모델을 직접 로드하거나 전처리하지 않고 Inference HTTP 계약을 사용한다.
- API 요청·응답과 모델 입력·출력 형식은 구현 전에 네 담당자가 함께 확정한다.

### 5.4 핵심 의존성

```text
M1 요구사항·계약
  └─ M2 독립 개발 기반
       └─ M3 핵심 기능 구현
            └─ M4 모델 선정·전체 흐름 연결
                 └─ M5 성능·장애·운영 검증
                      └─ M6 기능 동결·발표 준비

데이터·모델: 데이터 분할 → 기준선 학습 → 최종 모델·추론 규격
                                      ↓
백엔드: 임시 모델 API → 실제 모델 연결 → 판정 정책·이력
                                      ↓
프론트엔드: 임시 응답 UI → 실제 API 연결 → 시연 화면

MLOps·CI/CD: 기본 실행 환경 → 영역별 자동 검사 → 통합 배포·버전 동결
```

#### 병렬 진행이 가능한 작업

- M1에서 계약을 합의한 뒤 M2의 네 역할 작업은 동시에 진행할 수 있다.
- 프론트엔드는 백엔드 완성을 기다리지 않고 M1의 예시 응답으로 화면을 개발한다.
- 백엔드는 최종 모델을 기다리지 않고 동일한 함수 규격을 가진 임시 모델로 API를 개발한다.
- MLOps·CI/CD는 각 영역의 최소 실행 명령이 생기는 즉시 자동 검사를 붙인다.

#### 통합을 막는 의존성

- 데이터 분할이 확정되지 않으면 최종 모델 성능을 승인할 수 없다.
- 모델 입력·출력 규격이 확정되지 않으면 백엔드의 실제 모델 연결을 완료할 수 없다.
- API 계약이 확정되지 않으면 프론트엔드와 백엔드의 통합 완료를 선언할 수 없다.
- 영역별 실행 명령과 테스트 기준이 없으면 MLOps·CI/CD가 통합 배포를 완료할 수 없다.
- 두 번째 농산물 품목은 이번 필수 WBS에서 제외하고 사과 MVP 완료 후 별도로 평가한다.

## 6. 검증 계획

### 6.1 모델 검증

- 학습·검증·시험 데이터의 등급별 건수를 공개한다.
- Accuracy만 사용하지 않고 Macro F1과 등급별 Precision·Recall·F1을 함께 본다.
- 혼동행렬로 어떤 등급 사이에서 오류가 발생하는지 확인한다.
- 동일 개체의 여러 각도 이미지가 세트 사이에 섞이지 않았는지 검사한다.
- 가장 성능이 좋은 결과뿐 아니라 사용한 seed, 분할과 설정을 기록한다.
- 틀린 예측과 낮은 신뢰도 예측의 공통 조건을 이미지로 검토한다.

이미 결과를 확인한 기존 27개 Test 그룹은 후속 모델의 독립적인 최종 승인 자료로 재사용하지 않는다. 재평가 시 회귀 비교로 표시하고, 새 최종 승인은 독립된 신규 holdout 확보 후 진행한다.

### 6.1.1 CPU·처리량 측정 근거

[i7-4790 모델 단독 시험](wbs/reference/DM/results/i7-4790-model-only-20260923.json)은 합성 텐서 기준으로 `accepted=true`이며 순차 p95 138.50ms다. [별도 Compose HTTP 시험](wbs/reference/DM/results/i7-4790-compose-backend-inference-http-20260923.json)은 같은 합성 JPEG 12장을 반복했고 평균 166.61ms·p95 205.76ms·처리량 6.00건/초다. 모델 실행, HTTP 경로, 전체 운영 시험의 측정 범위를 구분한다.

전체 운영 승인은 실제 시연 사진 크기·내용, 동시 요청, Simulator, 저장·관제 연결을 포함해 확인한다. 다른 CPU의 성능이나 합성 입력 성공을 현장·클라우드의 성능 보장으로 사용하지 않는다.

### 6.2 서비스 검증

| 시험 | 기대 결과 |
|---|---|
| 정상 사과 그룹 입력 | 품종·등급, 각 신뢰도, 선별 목적지 표시 |
| 지원하지 않는 파일 입력 | 명확한 오류 메시지 반환 |
| 손상 이미지가 포함된 그룹 입력 | 추론하지 않고 입력 오류로 처리 |
| 저신뢰 사과 그룹 입력 | 자동 선별 대신 재검사 bin으로 분기 |
| 연속 이미지 처리 | 각 요청에 고유 판정 ID와 이력 생성 |
| 모델 파일 누락 | 서비스가 원인을 알 수 있는 오류 반환 |
| MySQL 연결 실패 | 저장 실패와 경고를 남기되 유효한 선별 명령은 계속 처리 |

| 시간 초과·늦은 응답 | 제한시간에 재검사 명령 확정, 늦은 결과가 명령을 바꾸지 않음 |

| QC→물류 연결 | 검사 결과를 출품 데이터로 매핑하고 낙찰·배차·배송 상태 전이를 확인 |

### 6.3 최종 시연 시나리오

1. 시뮬레이터가 서로 다른 품종·품질의 사과 그룹을 차례로 자동 입력한다.
2. 화면에서 예측 품종·품질과 각각의 신뢰도를 확인한다.
3. 가상 당도의 비실측 표시를 확인하고 품종 2종 × 외관 3단계 × 당도 2단계의 정상 12개 bin 중 하나로 분기한다.
4. 애매한 사과 그룹을 입력해 재검사 bin으로 분리되는 모습을 보여준다.
5. 최근 판정 이력에서 입력과 처리 결과를 확인한다.
6. 기간·품종·등급별 통계와 저신뢰 비율을 확인한다.
7. 시험 데이터의 혼동행렬과 대표 오류 사례를 설명한다.
8. QC 결과를 농가 출품으로 연결해 구매자 입찰·낙찰·자동배차·상하차 확인·배송 관제를 시연한다. 실제 QC 연결 전의 물류 데모 데이터는 구분해 표시한다.

- 실측 라벨이나 NIR·분광 센서 없이 실제 내부 당도와 맛을 판정한다는 주장
- 실제 유통 등급 인증 또는 가격 자동 결정
- 대규모 실시간 스트리밍과 분산 처리

- 별도 모바일 앱과 현재 품질 관제·관리 창을 넘어서는 관리자 시스템 확장
- 스마트폰 카메라 입력과 사용자 이미지 파일 업로드

### 8.1 농가별 설비 대응과 클라우드 서비스 확장 검토

소규모 농가의 개별 AI 서버 구축·관리 부담을 줄이기 위해, AI 판정·검사 이력·웹 모니터링을 공동 클라우드 서비스로 제공하는 방안을 향후 확장 후보로 검토한다. 농가에는 카메라·조명·사진 전송 장치와 선별 설비를 두고, 클라우드에는 추론·기록·조회 기능을 둔다. 실제 비용 효과는 현장 장비 비용, 클라우드 사용료와 이미지 전송량을 함께 산정한 뒤 판단한다.

#### 농가 식별·공유 추론과 API 확장

- 기존 Backend의 이미지 전송 API를 농가 장치의 요청 접점으로 활용하는 방향을 검토한다. Inference는 현재처럼 Backend 내부에서 호출하며, 농가가 모델 서버를 직접 선택·호출하는 구조로 바꾸지 않는다.
- 농가 요청에는 `farm_id`, `device_id`, 사과별 검사 ID, 촬영 시각과 촬영 설정 버전 등을 연결할 수 있다. 현재 이미지별 `metadata`는 각도 정보 배열이므로 농가 정보는 별도 요청 필드나 인증 문맥으로 정의하고 기존 배열과 구분한다. 이 필드는 아직 구현된 계약이 아니다.
- 서버는 인증된 장치의 소속과 요청의 농가 정보를 대조한다. 농가 식별자를 보내는 것만으로 접근 권한이 생기지 않으며, 조회·통계·설정도 농가별로 분리한다. 농가 식별은 관리 정보이고 모델의 분류 입력에 자동으로 추가하지 않는다.
- 여러 농가가 공유 추론 서버를 사용하고 총 유입량·사진 용량·처리시간·선별 제한시간을 측정해 서버 수와 병렬 처리 수를 정한다. 농가별 요청 한도와 대기열 배분으로 한 농가의 대량 입력이 다른 농가의 판정을 지연시키지 않도록 검토한다. 농가 수만큼 서버를 마련하는 것으로 고정하지 않는다.
- 외부 접속에는 HTTPS·장치 인증을 적용하고 중복 전송 식별, 제한시간·끊김 처리를 마련한다. 결과는 기존 검사 응답으로 돌려주는 방식을 먼저 검토하며, 별도 비동기 결과 API는 필요할 때 설계한다.
- 농가별 설비·촬영 설정의 등록·조회와 변경 이력은 별도 관리 계약으로 검토한다. 아직 클라우드 사업자·서버 수·요금·다농가 API를 확정하거나 구현하지 않는다.

#### 농가별 투입 간격과 판정 제한시간

- 현재 시연의 **500ms 투입 간격·초당 2개**는 반복 검증을 위한 고정 설정이다. 실제 농가에서 공통으로 지켜야 할 설비 속도로 보지 않는다.
- 현장 적용 시 농가별 설비 속도와 처리 가능량에 맞춰 투입 간격을 설정하는 방안을 검토한다. 설정한 속도는 실제 촬영·전송·추론·선별 처리량 시험으로 확인하며, 대기열이 쌓이면 감속 또는 투입 중지를 안내한다.
- **투입 간격과 판정 제한시간은 별도 설정**이다. 판정 제한시간은 촬영 완료 후 사과가 선별 지점에 도착하기까지 남은 시간에서 제어 여유를 뺀 값으로 정한다. 이동 거리가 고정된 설비에서는 투입 속도 변경이 이동시간에도 영향을 줄 수 있으므로 두 설정을 함께 검증한다.
- 클라우드 판정의 제한시간에는 사진 업로드, 서버 대기, AI 추론, 결과 수신 시간이 포함된다. 여러 사과를 동시에 처리해 처리량을 유지하더라도 각 결과는 해당 사과의 선별 시점 전에 도착해야 한다.
- 인터넷 단절·응답 지연 시 현장 장치가 재검사 경로로 보내거나 투입을 중지하는 대응을 검토한다. 실제 대응은 설비의 제어 가능 범위에 맞춰 결정한다.

현재 MVP의 Simulator 투입 간격과 Backend→Inference HTTP 구간의 500ms 제한은 유지한다. 농가별 속도 조절·클라우드 배포·실제 설비 제어는 이번 구현 범위에 추가하지 않는다.

#### 농가별 촬영 환경 보정과 모델 검증

농가마다 카메라와 사과의 거리, 촬영 각도, 렌즈, 해상도, 조명과 배경이 다를 수 있다. 현재 AI Hub 데이터만으로 모든 현장 조건에서 성능이 유지된다고 판단하지 않는다. 다음 순서의 현장 도입 절차를 검토한다.

1. **촬영 환경 기록:** 농가·설비별 거리, 방향·각도, 조명, 해상도와 카메라 설정을 기록하고 설정 버전을 관리한다.
2. **촬영 조건 보정:** 가능한 범위에서 조명·배경·노출을 맞추고, 사과 영역 자르기·크기 정규화·대표 사진 선택을 조정한다. 단순 크기 변경만으로 촬영 거리·각도의 영향을 모두 해결할 수 있다고 가정하지 않는다.
3. **현장 표본 검증:** 농가별 실제 사진과 품종·외관 등급 정답을 수집해 기존 모델의 성능과 저신뢰 비율을 먼저 평가한다. 같은 사과의 사진은 학습·검증·시험에 나누지 않고, 다른 촬영일·설비 조건에서도 확인한다.
4. **필요한 튜닝:** 검증 결과를 근거로 전처리·신뢰도 기준을 조정하고, 충분한 라벨 데이터가 확보되면 추가 학습이나 농가별 보정을 검토한다. 농가마다 별도 모델을 반드시 만드는 방식으로 고정하지 않는다.
5. **검증 후 적용:** 촬영 설정·전처리·모델 버전을 묶어 기록하고, 튜닝에 사용하지 않은 현장 시험 데이터로 성능과 처리시간을 확인한 뒤 적용한다.

현재는 농가별 촬영 데이터와 실측 설비 조건이 없어 보정값을 확정하거나 현장 튜닝 기능을 구현하지 않는다. 이 절은 향후 적용 가능성을 정리한 것이며 현장 성능 검증 완료를 의미하지 않는다. 실제 당도를 활용하는 확장에는 동일 사과의 실측 °Brix 데이터가 별도로 필요하다.
