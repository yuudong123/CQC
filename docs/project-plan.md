## 0. 프로젝트 한 문장 정의

현재 확보한 사과 이미지 중 **사과 품종 2종**을 대상으로 특·상·보통 품질 등급과 판정 신뢰도를 제시하고, 등급별 선별 목적지 또는 저신뢰 검수 대상으로 자동 분기하는 농산물 품질 검사 MVP다. 데이터와 일정이 허용하면 두 번째 농산물 품목을 추가하며, 전체 지원 범위는 최대 2개 품목으로 제한한다.

이 프로젝트의 핵심은 이미지 분류 모델만 만드는 데 있지 않다. 이미지 입력부터 등급 판정, 저신뢰 예외 처리, 선별 신호 생성, 결과 기록까지 이어지는 **품질 검사 업무 흐름**을 한 번에 시연하는 것이 목표다.

## 1. 프로젝트 효과 조사

### 1.1 해결하려는 문제

농산물 품질 판정은 크기, 형태, 외관 상태, 품종과 촬영 조건처럼 여러 시각 요소를 함께 고려해야 한다. 작업자가 많은 물량을 반복해서 검사하면 판정 속도와 일관성이 작업 환경과 숙련도에 영향을 받을 수 있다. 단순 색상 임계값이나 크기 기준만으로는 조명, 촬영각도, 배경, 개체 차이를 안정적으로 처리하기 어렵다.

한 달 프로젝트에서는 실제 유통 등급 판정을 완전히 대체한다고 주장하지 않는다. AI Hub가 제공하는 품질 등급 라벨을 기준으로 제한된 환경의 이미지 분류 모델을 만들고, 모델이 확신하지 못하는 입력을 사람이 확인하도록 분리한다. 이를 통해 자동 판정이 가능한 구간과 사람이 개입해야 하는 구간을 함께 보여준다.

### 1.2 As-Is / To-Be

| 구분 | As-Is | To-Be |
|---|---|---|
| 품질 확인 | 작업자가 이미지를 보고 등급을 반복 판정 | AI가 사과의 특·상·보통 등급과 신뢰도를 제시 |
| 판정 기준 | 작업자 경험과 개별 기준에 따라 차이가 생길 수 있음 | 동일 모델과 전처리 규칙으로 일관된 기준 적용 |
| 예외 처리 | 애매한 개체도 즉시 등급을 정해야 함 | 낮은 신뢰도 결과를 별도 검수 대상으로 분리 |
| 선별 작업 | 판정 후 사람이 분류 위치를 다시 결정 | 예측 등급에 따라 선별 목적지 신호를 자동 생성 |
| 결과 기록 | 판정 근거와 처리 결과가 흩어질 수 있음 | 입력, 예측 등급, 신뢰도, 처리 시각을 한 흐름으로 기록 |
| 모델 검증 | 전체 정확도만 보면 소수 등급 실패를 놓칠 수 있음 | 등급별 Precision·Recall·F1과 혼동행렬로 오류 확인 |

### 1.3 예상 사용자와 사용 장면

| 사용자 | 사용 장면 | MVP에서 제공할 기능 |
|---|---|---|
| 선별 작업자 | 자동 입력된 사과의 등급과 분류 위치 확인 | 품종·등급·신뢰도 표시, 선별 목적지 안내 |
| 품질 관리자 | 등급별 오분류와 애매한 사례 검토 | 혼동행렬, 저신뢰 목록, 예측 이력 확인 |
| 시연 관람자 | 자동화 흐름 이해 | 자동 입력부터 선별 신호까지 한 화면에서 확인 |

실제 생산라인 운영자, 농가와 유통업체를 대상으로 한 현장 요구사항 조사는 아직 수행하지 않았다. 위 사용자는 MVP 시나리오를 정의하기 위한 가정이다.

### 1.4 프로젝트 목표 KPI

| 영역 | 측정 지표 | 기초 목표 | 확정 시점 |
|---|---|---|---|
| 분류 성능 | 사과 3등급 Macro F1 | 기준선 결과 확인 후 확정 | 2주차 기준선 학습 후 |
| 등급별 성능 | 등급별 Recall과 F1 | 특정 등급의 실패가 가려지지 않도록 모두 공개 | 2주차 |
| 데이터 품질 | 손상 이미지, 라벨 누락, 중복 후보 수 | 전체 검사 결과 기록 | 1주차 |
| 일반화 | 촬영각도 또는 개체 그룹 분리 시험 | 무작위 분할과 비교 | 데이터 구조 확인 후 |
| 추론 | Backend 요청 전송부터 Inference 응답 전체 수신까지 | 500ms 제한, CPU 실측 | 3주차 |
| 검수 | 저신뢰 결과의 수와 오분류 비율 | 임계값별 비교표 작성 | 3주차 |
| 자동화 | 입력부터 선별 신호 기록까지 성공률 | 정해진 시연 세트 반복 실행 | 4주차 |

목표 수치는 성과를 미리 주장하는 값이 아니다. 최종 발표에는 실제 시험 환경, 데이터 분할 방법과 측정 결과를 함께 기록한다.

## 2. AI 분석 데이터 조사

### 2.1 데이터 개요

AI Hub 공식 소개에서 확인한 내용은 다음과 같다.

- 분야: 농축수산
- 유형: 이미지
- 구축년도: 2020년
- 구축량: 정제·가공된 데이터 30만 건
- 원시 수집량: 10개 품목별 6만 건, 총 60만 건
- 대상 품목: 무, 배추, 양파, 마늘, 양배추, 감, 사과, 배, 감귤, 감자
- 품질 분류: 특, 상, 보통
- 이미지 형식: PNG
- 메타데이터 예시: 작물·품종, 촬영각도, 촬영장비·장소·날짜, 크기, 부피
- 라벨 항목 예시: 종 ID, 과일 종류, 품질 등급, 촬영면, 수직·수평 촬영각도, 높이, 너비, 무게
- 공개 기준모델: Inception V3 이미지 분류
- 공개 성능: F1-Score 0.89
- 다운로드: 소개 페이지에 다운로드 기능과 API 파일 목록이 제공되며, 데이터 신청과 승인 절차가 필요하다.

페이지 상단 소개에는 농산물 20종이라는 문구도 있으나, 상세 설명은 10개 품목을 열거한다. 프로젝트에서는 실제 다운로드 파일과 설명서를 확인하기 전까지 **10개 품목 상세 목록을 기준**으로 사용하고, 불일치 내용을 데이터 점검 기록에 남긴다.

### 2.2 MVP 품목 선정

#### 현재 범위: 사과 품종 2종

- 현재 확보된 이미지는 사과 데이터다.
- 사과 전체 품종을 한 범주로 합치지 않고, 확인된 **부사와 양광 2종**을 데이터 범위로 둔다.
- 두 품종 모두 특·상·보통 품질 등급 데이터를 확보할 수 있는지 먼저 확인한다.
- 품종별 촬영 조건과 등급 분포 차이가 모델 판단에 미치는 영향을 따로 분석한다.
- 실제 파일과 라벨을 확인한 결과 품종은 **부사와 양광**으로 확정한다.

품종과 품질 등급은 모두 MVP의 필수 예측 대상이다. 단일 멀티태스크 모델과 품종·품질 분리 모델을 비교하고 품종 정확도, 품질 정확도, CPU 추론 속도와 운영 복잡도를 기준으로 최종 구조를 선택한다.

#### 두 번째 품목 확장 조건

다음 조건을 모두 만족할 때 두 번째 농산물 품목을 추가한다.

1. 사과 품종 2종의 데이터 로더와 학습 파이프라인이 재현 가능하게 동작한다.
2. 두 품종에 대한 3등급 기준선과 품종별 오류 분석이 완료된다.
3. 후보 품목의 등급별 표본 수와 라벨 구조를 확인한다.
4. 품목 추가가 4주차 통합과 발표 준비를 방해하지 않는다.

두 번째 품목은 아직 정하지 않는다. 전체 지원 범위는 사과를 포함해 최대 2개 품목이다.

### 2.3 입력과 예측 대상

| 구분 | MVP 정의 | 확인 상태 |
|---|---|---|
| 입력 | 동일 사과의 다각도 이미지 묶음 | Simulator가 시연 전용 목록의 사전 구성 12장을 전송 |
| 보조 정보 | 촬영면·수직·수평 각도 메타데이터 | Simulator의 대표 프레임 선택과 Inference 입력 검증·추적에 사용 |
| 정답 | 부사·양광 품종과 특·상·보통 품질 등급 | 학습·평가에 사용하고 서비스 모델 입력에서는 제외 |
| 출력 | 예측 품종·품질등급, 각 확률·신뢰도, 시연용 가상 당도와 출처 | 기획 확정 |
| 자동화 출력 | 품종 2종 × 외관 3단계 × 가상 당도 2단계의 정상 12 bin 또는 재검사 bin | 시연 정책 확정·Backend 연동 대기 |
| 설명 정보 | 모델 주목 영역 시각화 | 구현 여유에 따른 확장 |

첫 기준선은 부사와 양광 이미지를 입력으로 사용하여 품종 라벨과 품질 라벨을 각각 예측한다. 서비스 추론에는 정답 품종·품질과 `group_no`를 모델 입력으로 전달하지 않는다. 당도는 실측값이 없는 현재 데이터에서 판정하지 않으며, 별도 가상 센서가 만든 `virtual_brix`를 `brix_is_measured=false`와 함께 시연한다. 이미지 단독 기준선과 가상 당도를 결합한 late-fusion 실험은 분리 평가한다.

### 2.4 가장 중요한 데이터 누수 위험

공식 설명은 한 농산물을 여러 카메라 위치와 각도에서 반복 촬영한 구조를 보여준다. 같은 개체의 여러 이미지가 학습 데이터와 시험 데이터에 나뉘면 모델이 품질 일반화 대신 동일 개체의 특징을 기억하여 성능이 부풀 수 있다.

데이터 확보 후 다음 순서로 확인한다.

1. 파일명과 라벨에 개체 ID 또는 촬영 묶음 ID가 있는지 찾는다.
2. 동일 개체의 여러 각도 이미지가 몇 장씩 연결되는지 확인한다.
3. 개체 그룹을 식별할 수 있으면 `Group Split`을 사용한다.
4. 그룹 식별이 어렵다면 파일명 규칙, 촬영 시각과 이미지 유사도를 이용해 중복 후보를 조사한다.
5. 무작위 이미지 분할 성능과 그룹 분할 성능을 함께 기록한다.

이 검증이 끝나기 전에는 높은 시험 성능을 실제 새 농산물에 대한 일반화 성능으로 해석하지 않는다.

### 2.5 데이터 품질 점검

| 점검 대상 | 점검 내용 | 산출물 |
|---|---|---|
| 파일 | 손상, 확장자, 해상도, 읽기 실패 | 파일 검사 보고서 |
| 라벨 | 누락, 알 수 없는 등급, 이미지와 라벨 불일치 | 오류 목록 |
| 분포 | 품목·품종·등급·각도별 건수 | 분포표와 그래프 |
| 중복 | 동일 파일 해시, 유사 이미지, 동일 개체 촬영 | 중복 후보 목록 |
| 배경 | 등급과 배경·촬영장소의 우연한 연관 | 샘플 비교 및 오류 분석 |
| 분할 | 같은 개체가 여러 세트에 포함되는지 확인 | 분할 검증 결과 |

### 2.6 반드시 공개할 한계

- AI Hub 품질 등급은 제공 데이터의 기준이며, 모델 결과가 실제 유통 현장의 공식 등급 판정을 보증하지 않는다.
- 촬영 장비와 배경이 통제된 데이터라면 휴대전화나 현장 컨베이어 이미지에서 성능이 낮아질 수 있다.
- 품질 등급 차이를 만드는 세부 기준과 품종별 기준을 실제 라벨 설명서에서 추가 확인해야 한다.
- 표면에 보이지 않는 당도, 내부 손상과 맛을 RGB 이미지 한 장으로 직접 판단할 수 없다.
- 현재 확보한 표본 수와 품종·품질 분포는 `docs/wbs/reference/DM/data-spec.md`에 기록했으며, 그룹 수가 적은 조합의 성능 변동성을 함께 공개해야 한다.
- 물리 선별기를 연결하지 않으면 선별 자동화는 소프트웨어 신호와 화면 시뮬레이션 수준이다.
- Grad-CAM 같은 시각화는 모델이 본 영역을 설명하는 보조 자료이며 품질 판정의 인과적 근거가 아니다.

발표 표현은 **“AI Hub 이미지 라벨 기준 사과 품질 등급 판정과 선별 흐름 자동화 MVP”**로 통일한다.

### 2.7 분석 및 모델 설계

1. 데이터 설명서와 실제 파일 구조를 비교한다.
2. 사과 이미지만 추출하고 품질 등급 라벨을 정규화한다.
3. 품종, 등급, 촬영각도와 개체 그룹 후보의 분포를 분석한다.
4. 이미지 손상, 라벨 누락과 중복 후보를 제거하거나 별도 기록한다.
5. 가능한 경우 개체 단위로 학습·검증·시험 세트를 분리한다.
6. 사전학습 이미지 분류 모델로 기준선을 만든다.
7. 클래스 불균형이 확인되면 가중치 또는 샘플링을 비교한다.
8. 밝기, 회전, 크롭 등 증강은 실제 촬영 조건을 벗어나지 않는 범위로 제한한다.
9. 전체 정확도와 Macro F1, 등급별 Precision·Recall·F1, 혼동행렬을 기록한다.
10. 저신뢰 임계값별 자동 판정 비율과 오분류 비율을 비교한다.
11. 실제 시연 입력과 학습 데이터 간 차이를 오류 사례로 정리한다.

### 2.8 기준선 모델 후보

| 후보 | 역할 | 장점 | 주의점 |
|---|---|---|---|
| 단순 다수 클래스 예측 | 최소 기준 | 데이터 불균형 영향 확인 | 실제 이미지 학습 모델 아님 |
| 경량 CNN 전이학습 | 1차 기준선 | 한 달 프로젝트와 CPU/GPU 제약에 적합 | 모델 종류는 환경 확인 후 확정 |
| 조금 큰 사전학습 모델 | 비교 모델 | 기준선 대비 성능 개선 가능 | 학습 시간과 시연 PC 자원 확인 필요 |
| 이미지+메타데이터 모델 | 확장 실험 | 크기·품종 정보 활용 가능 | 실사용 입력에서 메타데이터 확보 필요 |

#### 다각도 그룹 모델 권장안

상용 사과 선별기는 사과를 개별 캐리어 또는 롤러에서 회전시키며 통제된 조명 아래 360° 외관을 다수 촬영한다. 공개된 상용 사례는 사과 한 개당 40장부터 최대 90장 또는 수백 장까지 생성한다. CQC도 동일 `group_no`를 하나의 사과 묶음으로 사용한다.

다만 상용 장비의 촬영 프레임 수를 i7-4790 CPU가 전부 CNN으로 처리한다고 가정하지 않는다. 촬영·입력 프레임 수와 실제 모델에 투입할 대표 프레임 수를 분리한다. 공유 특징 추출기와 결합 계층을 사용하고, 대표 시점 수에 따른 품종·품질 Macro F1과 CPU 지연을 비교하여 최종 입력 장수를 정한다.

현재 데이터의 179개 그룹 중 175개는 40장 이상이지만 4개 그룹은 8~30장만 제공한다. 또한 1000×1000 RGB 40장은 디코딩 시 사과당 약 114.4MB이므로 Backend 요청 전송부터 Inference 응답 전체 수신까지 500ms를 보장할 수 없다. 비교 실험 결과 서비스 입력은 대표 12장으로 고정한다. 기본 시연은 데이터 담당이 미리 구성한 `realtime-apple-arrival-demo`의 12장 묶음을 Simulator가 읽고 Backend가 순서 변경 없이 Inference에 중계한다.

프레임워크는 PyTorch·torchvision, 인코더는 MobileNetV3 Small로 확정한다. 대표 12장과 품종·품질 분리 구조를 사용하며, 새 버전의 손실·epoch·승인 여부는 해당 버전의 평가 기록으로 관리한다.

## 3. 서비스 및 자동화 설계

### 3.1 전체 흐름

```text
AI Hub 원본 이미지·라벨
  → 파일·라벨 검증
  → 사과 데이터 추출
  → 개체 그룹 확인 및 데이터 분할
  → 전처리·증강
  → 기준선 모델 학습·평가
  → 검증된 모델 저장

시뮬레이터가 시연 전용 묶음(`data/processed/realtime-apple-arrival-demo`)에서 읽은 12장 다각도 이미지 입력
  → multipart 형식·장수·이미지 해석 가능 여부 검증
  → Inference HTTP API 호출과 동일 전처리
  → 품종·품질 추론과 실제 사용 프레임 수 기록
  → 품종·품질 예측과 각각의 확률·신뢰도 반환
  → 두 신뢰도 임계값과 Inference HTTP 구간 500ms 판정
      ├─ 기준 이상·가상 당도 존재: 품종 2종 × 외관 3단계 × 가상 당도 2단계의 정상 목적지 생성
      └─ 기준 미만: 재검사 bin으로 분기
  → 판정 이력과 처리 결과 기록
  → 웹 화면에 결과 표시
```

### 3.2 MVP 기능 범위

| ID | 기능 | 완료 기준 | 우선순위 |
|---|---|---|---|
| F-01 | 자동 이미지 입력 | 시뮬레이터가 시연 전용 `index.json`의 기본 12장 묶음을 500ms 간격으로 multipart 전송 | 필수 |

| F-03 | 품종·품질 추론 | 사과 품종과 특·상·보통 품질 및 각 신뢰도 반환 | 필수 |
| F-12 | 가상 당도 시연 | 이미지 색상 특징과 재현 가능한 잡음으로 가상 °Brix를 생성하고 비실측임을 표시 | 필수 |
| F-04 | 저신뢰 분기 | 설정 임계값 미만을 검수 대상으로 표시 | 필수 |

| F-08 | 통계·분석 조회 | 웹에서 기간·품목·품종·등급 기준의 검사 현황과 분포를 조회 | 필수 |

| F-11 | 가상 제어 API | 검사 결과에 맞는 12개 정상 bin 또는 재검사 bin 명령 생성 | 필수 |

### 3.3 저신뢰 검수 정책

품종 또는 품질 confidence가 각각의 임계값보다 낮으면 자동 선별하지 않고 검수 대상으로 분리한다. 두 임계값은 임의의 숫자로 확정하지 않는다. 검증 데이터에서 여러 임계값을 비교하여 다음 항목을 함께 본다.

- 자동 판정으로 처리되는 이미지 비율
- 자동 판정 구간의 정확도와 Macro F1
- 검수 대상으로 빠지는 이미지 수
- 특 또는 상을 보통으로 잘못 보내는 사례
- 보통을 특으로 잘못 보내는 사례

최종 임계값은 모델 성능과 시연 목적을 함께 고려해 정하고 설정에서 변경할 수 있게 한다. 실제 검사에 적용한 품종·품질 threshold 값은 검사 이력에 기록한다.

### 3.4 선별 자동화 시뮬레이션

실제 설비와 PLC는 연동하지 않는다. 백엔드의 가상 제어 API 호출을 최종 자동화 범위로 하며, 화면 애니메이션은 MVP 이후로 미룬다.

| 판정 결과 | 목적지 수 | 화면 표시 |
|---|---:|---|
| 부사·양광 × 외관 특·상·보통 × 가상 당도 12°Brix 미만/이상 | 정상 bin 12개 | 예측 품종·외관·시연 당도 구간에 대응하는 구역으로 이동 |
| 저신뢰·시간 초과·시스템 오류 | 재검사 bin 1개 | 작업자 재검사 대기 |

목적지 이름은 장비 규격이 아니라 임시 인터페이스다. 실제 장비를 연결할 경우 신호 형식, 통신 방식, 실패 시 안전 동작을 별도 요구사항으로 정의한다.

### 3.5 논리 아키텍처

| 영역 | 책임 | 입력 | 출력 |
|---|---|---|---|
| 데이터 파이프라인 | 원본 검사, 라벨 정규화, 분할, 전처리 | 원본 이미지·라벨 | 학습용 데이터와 분할 목록 |
| 학습 파이프라인 | 모델 학습, 평가, 모델 저장 | 학습·검증 데이터 | 모델 파일과 평가 결과 |
| 추론 모듈 | 다각도 전처리와 품종·품질 예측 | 이미지 그룹 | 품종·품질 확률과 예측값 |
| 가상 당도 모듈 | 색상·균일도 특징 기반 시연값 생성 | 동일 사과 이미지 그룹 | `virtual_brix`, 불확실성, 생성기 버전, 비실측 표시 |
| 판정 정책 | 저신뢰 여부와 선별 목적지 결정 | 예측 결과 | 자동 선별 또는 검수 신호 |
| FastAPI Backend | 검사 오케스트레이션, 화면·Inference 연결과 정책 적용 | Simulator 요청·Inference 응답 | 구조화된 검사 응답 |
| 웹 화면 후보 | 자동 검사 상태와 결과 표시 | 백엔드 API 응답 | 품종, 등급, 신뢰도, 처리 결과 |
| MySQL | 순환 보존 검사 이력과 통계·분석 조회 지원 | 판정 이벤트와 검사 결과 | 웹 조회용 이력·집계 데이터 |

Backend는 **Python + FastAPI**, 데이터베이스는 **MySQL**을 사용한다. DB 목적은 현재 보존 중인 검사 이력을 저장하고 웹에서 통계와 분석 결과를 조회할 수 있게 하는 것이다. 이력의 건수 상한은 86,400건이며 상한에 도달하면 오래된 8,640건을 삭제한다. 초당 2그룹 기준 실제 보존 범위는 약 10.8~12시간이다. 테이블, 컬럼, 인덱스, 관계와 마이그레이션 방식은 백엔드 담당자가 별도 문서로 설계한다. 이 기획서에서는 미확정 DB 구조를 임의로 정의하지 않는다. 웹 프레임워크와 Backend 세부 라이브러리·버전은 역할별 기술 문서에서 확정한다.

### 3.6 데이터 계약 초안

#### 시뮬레이터 → 백엔드 검사 요청

| 항목 | 설명 | 상태 |
|---|---|---|
| inspection_id | 전체 처리 흐름에서 공유할 검사 ID | 필수 |
| captured_at | 시뮬레이터 입력 시각 | 필수 |
| sequence_no | 반복 입력 위치와 순서를 식별하는 번호 | 필수 |
| images | 동일 `group_no`에서 각도 기준으로 선택한 최대 12장의 다각도 이미지 파일 목록 | 필수 |
| angle_metadata | 각 이미지의 `view_index`, 촬영면과 수직·수평 각도 정보 | 필수 |

`1 inspection = 사과 1개 = group_no 1개`로 처리한다. 전송 형식은 Base64 JSON이 아닌 `multipart/form-data`를 사용하며 스마트폰 카메라, 사용자 이미지 파일 업로드와 실제 산업용 카메라 입력은 제공하지 않는다. `group_no`와 정답 품종·품질은 모델 입력으로 전달하지 않는다.

#### inference → 백엔드 응답

| 논리 항목 | 내용 |
|---|---|
| 검사 식별 | 요청과 동일한 `inspection_id` |
| 품종 결과 | 예측값, `fuji`·`yanggwang`을 key로 가진 확률 객체와 confidence |
| 품질 결과 | 예측값, `L`·`M`·`S`를 key로 가진 확률 객체와 confidence |
| 진단·버전 | `inference_time_ms`, 모델명·버전, 전처리 버전, 실제 사용 프레임 수 |

품질 코드는 `L=특`, `M=상`, `S=보통`으로 사용한다. Backend는 class index 순서를 추측하지 않는다. Inference는 예측과 진단 정보만 반환하며 저신뢰·시간 초과·bin·DB·제어 정책은 Backend가 적용한다. 세부 OpenAPI 필드명은 계약 단계에서 확정한다.

### 3.7 판매·물류 통합 범위와 구현 원칙

프로젝트의 전체 범위는 QC 검사·선별에 판매·물류 시연을 포함한다. 전체 시연 흐름은 `QC 판정·선별 → 농가 출품 → 구매자 입찰 → 낙찰 주문 → 자동배차 → 상·하차 확인 → 배송 완료/고장 대체배차`다. 앞 절의 가상 제어는 QC 선별 단계의 최종 출력이다. 실제 결제, 차량 제어, 교통 기반 최적 경로와 실제 시장가격 예측은 제외한다.

- QC Backend와 MySQL은 검사·제어·검수 이력의 원본을 관리한다.
- `cqc-logistics-platform`의 FastAPI와 MongoDB는 출품·입찰·주문·차량·노선을 관리한다. QC DB를 대체하지 않는다.
- 물류 화면은 Next.js·TypeScript이며, QC 대시보드의 구현 완료를 뜻하지 않는다.
- 결과 연결 계층에서 식별자·품질 코드·신뢰도를 변환하고 농가·수량·좌표를 보완한다. 모델은 수량이나 위치를 예측하지 않는다. 실제 연결 전에는 명시된 데모 데이터를 사용한다.
- 배차는 용량·상태 조건에 맞는 유휴 차량을 우선하고 거리 기반으로 선택한다. 유휴 후보가 없으면 적재 여유가 있는 운행 차량에 새 픽업·하차를 첫 미완료 하차 앞에 삽입한다. 모든 삽입 위치를 비교하는 최적화는 MVP 요구사항에서 제외한다.
- 앞으로도 시연에 필요한 단순한 규칙과 상태 전이를 우선한다. 프론트 화면 흐름에 따라 세부 동작은 조정할 수 있으나 적재 한도, 픽업 후 하차, 확인 게이트, 고장 차량 제외는 유지한다. 변경 시 API·문서·검증 기준을 함께 맞춘다.
- 기존 WBS의 ID·담당·일정은 유지한다. 물류 상세 작업은 별도 작업 순서 문서로 관리하며 추가 담당 배정은 팀 합의로 정한다. 모델 파트는 QC 결과 계약, 백엔드는 실제 결과 전달, 프론트는 역할별 화면, MLOps는 통합 배포 경계를 검토한다.

통합 Compose 목표는 QC 5개 서비스와 물류 3개 서비스(`logistics-mongodb`, `logistics-api`, `logistics-web`)다. `origin/dev`에는 이 구성이 반영됐지만 QC의 4개 애플리케이션은 아직 placeholder이므로 전체 흐름 완료로 표시하지 않는다. 상세 기준: [물류 제품 범위](../cqc-logistics-platform/docs/01-product-scope.md), [작업 순서](../cqc-logistics-platform/docs/06-build-order.md).

### 4.2 기술 스택 확정 원칙

1. 팀원이 한 달 안에 구현하고 설명할 수 있는 기술을 선택한다.
2. 핵심 시나리오에 필요하지 않은 분산 시스템과 복잡한 MLOps 도구는 넣지 않는다.
3. GPU가 없는 환경에서도 저장된 모델로 추론할 수 있어야 한다.
4. 학습 코드와 서비스 추론이 동일한 전처리 정의를 사용한다.
5. 모델 파일, 원본 데이터와 생성 결과는 Git 저장소에 직접 올리지 않는다.

### 4.3 Git 운영 초안

- `main`: 발표 전까지 일반 통합에 사용하지 않고 최종 발표 버전을 표시한다.
- `dev`: 통합과 학원 PC 자동 배포 기준 브랜치다.
- `feat/*`: 개인 기능 작업 브랜치다.
- `feat/* → dev`는 Pull Request와 최소 1명 확인 후 병합한다.
- `main`에는 자동 배포를 연결하지 않는다.

- 안정 브랜치는 `dev`이며 최종 발표 버전은 `main`으로 표시한다.
- 작업 브랜치 후보: `feat/data`, `feat/model`, `feat/inference`, `feat/api`, `feat/web`, `docs/plan`
- 한 사람이 동시에 같은 파일을 크게 수정하지 않도록 문서와 코드 소유 영역을 합의한다.
- API 요청·응답과 데이터 필드는 구현 전에 문서에서 먼저 합의한다.
- 원본 데이터, 모델 가중치와 대용량 출력은 `.gitignore`로 제외한다.
- 통합 전에는 최소 한 명이 변경 내용과 실행 결과를 확인한다.

#### 역할 경계

- 데이터 분석·모델 담당은 전처리·대표 프레임 선택 규칙·모델 로딩과 `다각도 이미지 묶음 → 품종·품질 확률` Inference API까지 책임진다.
- 백엔드 담당은 FastAPI, Inference HTTP Client, 정상 12개 bin 또는 재검사 bin 정책, MySQL 이력, 내부 가상 제어와 Simulator 애플리케이션 로직을 책임진다.
- 프론트엔드 담당은 자동 검사 상태와 백엔드 조회·관리 기능을 화면으로 표현하고 Simulator 시작·정지를 제어한다. 사용자 이미지 업로드는 제공하지 않는다.
- MLOps·CI/CD 담당은 Docker·Compose·Volume·healthcheck·재시작 정책과 배포·로그 운영 환경을 책임진다.
- Backend는 모델을 직접 로드하거나 전처리하지 않고 Inference HTTP 계약을 사용한다.
- API 요청·응답과 모델 입력·출력 형식은 구현 전에 네 담당자가 함께 확정한다.

### 5.4 핵심 의존성

```text
M1 요구사항·계약
  └─ M2 독립 개발 기반
       └─ M3 핵심 기능 구현
            └─ M4 모델 선정·전체 흐름 연결
                 └─ M5 성능·장애·운영 검증
                      └─ M6 기능 동결·발표 준비

데이터·모델: 데이터 분할 → 기준선 학습 → 최종 모델·추론 규격
                                      ↓
백엔드: 임시 모델 API → 실제 모델 연결 → 판정 정책·이력
                                      ↓
프론트엔드: 임시 응답 UI → 실제 API 연결 → 시연 화면

MLOps·CI/CD: 기본 실행 환경 → 영역별 자동 검사 → 통합 배포·버전 동결
```

#### 병렬 진행이 가능한 작업

- M1에서 계약을 합의한 뒤 M2의 네 역할 작업은 동시에 진행할 수 있다.
- 프론트엔드는 백엔드 완성을 기다리지 않고 M1의 예시 응답으로 화면을 개발한다.
- 백엔드는 최종 모델을 기다리지 않고 동일한 함수 규격을 가진 임시 모델로 API를 개발한다.
- MLOps·CI/CD는 각 영역의 최소 실행 명령이 생기는 즉시 자동 검사를 붙인다.

#### 통합을 막는 의존성

- 데이터 분할이 확정되지 않으면 최종 모델 성능을 승인할 수 없다.
- 모델 입력·출력 규격이 확정되지 않으면 백엔드의 실제 모델 연결을 완료할 수 없다.
- API 계약이 확정되지 않으면 프론트엔드와 백엔드의 통합 완료를 선언할 수 없다.
- 영역별 실행 명령과 테스트 기준이 없으면 MLOps·CI/CD가 통합 배포를 완료할 수 없다.
- 두 번째 농산물 품목은 이번 필수 WBS에서 제외하고 사과 MVP 완료 후 별도로 평가한다.

| 제공자 | 받는 역할 | 인수인계 항목 | 인수 조건 |

## 6. 검증 계획

### 6.1 모델 검증

- 학습·검증·시험 데이터의 등급별 건수를 공개한다.
- Accuracy만 사용하지 않고 Macro F1과 등급별 Precision·Recall·F1을 함께 본다.
- 혼동행렬로 어떤 등급 사이에서 오류가 발생하는지 확인한다.
- 동일 개체의 여러 각도 이미지가 세트 사이에 섞이지 않았는지 검사한다.
- 가장 성능이 좋은 결과뿐 아니라 사용한 seed, 분할과 설정을 기록한다.
- 틀린 예측과 낮은 신뢰도 예측의 공통 조건을 이미지로 검토한다.

이미 결과를 확인한 기존 27개 Test 그룹은 후속 모델의 독립적인 최종 승인 자료로 재사용하지 않는다. 재평가 시 회귀 비교로 표시하고, 새 최종 승인은 독립된 신규 holdout 확보 후 진행한다.

### 6.2 서비스 검증

| 시험 | 기대 결과 |
|---|---|
| 정상 사과 그룹 입력 | 품종·등급, 각 신뢰도, 선별 목적지 표시 |
| 지원하지 않는 파일 입력 | 명확한 오류 메시지 반환 |
| 손상 이미지가 포함된 그룹 입력 | 추론하지 않고 입력 오류로 처리 |
| 저신뢰 사과 그룹 입력 | 자동 선별 대신 재검사 bin으로 분기 |
| 연속 이미지 처리 | 각 요청에 고유 판정 ID와 이력 생성 |
| 모델 파일 누락 | 서비스가 원인을 알 수 있는 오류 반환 |
| MySQL 연결 실패 | 저장 실패와 경고를 남기되 유효한 선별 명령은 계속 처리 |
| 이력 조건 조회 | 조건과 일치하는 검사 기록만 반환 |
| 통계·분석 조회 | 기간·품목·품종·등급 기준 집계가 이력과 일치 |

### 6.3 최종 시연 시나리오

1. 시뮬레이터가 서로 다른 품종·품질의 사과 그룹을 차례로 자동 입력한다.
2. 화면에서 예측 품종·품질과 각각의 신뢰도를 확인한다.
3. 시스템이 품종 2종 × 품질 3단계에 대응하는 정상 bin 중 하나를 선택하는 모습을 보여준다.
4. 애매한 사과 그룹을 입력해 재검사 bin으로 분리되는 모습을 보여준다.
5. 최근 판정 이력에서 입력과 처리 결과를 확인한다.
6. 기간·품종·등급별 통계와 저신뢰 비율을 확인한다.
7. 시험 데이터의 혼동행렬과 대표 오류 사례를 설명한다.
