## 2026-09-16 기획 인터뷰

### 데이터와 모델

- `data/raw` 확인 결과 품종은 부사(`fuji`)와 양광(`yanggwang`) 2종이다.
- 품질은 파일 코드 `L/M/S`와 라벨 `특/상/보통`이 각각 대응한다.
- 원본은 `1.Training`과 `2.Validation`으로 이미 분리되어 있으며 별도 Test 폴더는 없다.
- 이미지와 JSON 라벨은 총 25,024쌍이다. Training은 21,896쌍, Validation은 3,128쌍이다.
- JSON의 `group_no`별로 여러 각도 이미지가 묶여 있다. 확인된 그룹은 Training 139개, Validation 40개이며 다수 그룹은 184장이다.
- 동일 사과의 여러 각도 이미지는 개별 이미지가 아니라 하나의 사과 단위로 묶어서 판단한다.
- MVP 입력 이미지에는 사과 한 개만 존재한다고 가정하지만, 같은 사과의 여러 각도 이미지를 하나의 검사 입력으로 묶는다.
- 실제 설비의 다각도 촬영, 사과 추적과 YOLO 객체 인식은 MVP 범위에서 제외한다.
- AI는 사과의 **품종과 품질 등급을 모두 판정**한다.
- 단일 멀티태스크 모델과 품종·품질 분리 모델을 비교하되 최종 선택 조건은 실험 결과를 본 뒤 정한다.
- 비교 지표는 품종 Macro F1, 품질 Macro F1, 품종 정확도, 품질 정확도, 각 혼동행렬, CPU 평균·최대·p95 추론시간과 운영 복잡도다.
- 저신뢰 기준값은 모델 검증 후 정하며 설정으로 변경할 수 있게 한다.
- 품종과 품질 신뢰도 기준을 각각 두며 둘 다 기준을 만족해야 정상 bin으로 보낸다. 기준값은 모델 학습·검증 과정에서 정한다.
- 처리량 초당 2건은 이미지 수가 아니라 사과 그룹 2개를 의미한다.
- 모델은 동일 사과의 여러 각도 이미지를 하나의 그룹 입력으로 동시에 학습·추론하는 결합 모델을 우선 검토한다.
- 다각도 입력은 공유 이미지 특징 추출기와 그룹 결합 계층을 사용하고 품종·품질 출력을 만든다. 최종 단일·분리 출력 구조는 비교 후 정한다.
- 초기 4·6·8장 비교안은 연구용 최소 촬영 구성을 기준으로 한 안이므로 철회한다.
- 상용 선과장 설비는 사과를 개별화하여 회전 캐리어·롤러로 이송하고, 통제된 조명과 다수 카메라·파장으로 360° 표면을 촬영한다.
- 확인한 상용 사례는 사과 한 개당 40장, 장비 구성에 따라 최대 90장 또는 수백 장을 생성한다.
- 초기에는 Simulator가 최대 40장을 Backend에 전송하고 성능시험 후 입력 장수를 확정하기로 했다. 이후 비교 결과에 따라 서비스 계약은 Simulator가 대표 12장을 선택해 전송하는 방식으로 대체되었다.
- 로컬 179개 사과 그룹 중 175개는 40장 이상을 보유한다. Training은 139개 중 138개, Validation은 40개 중 37개가 40장 이상이다.
- 40장 미만 그룹은 8장·16장·21장·30장인 그룹 각 1개다. 따라서 고정 40장 입력은 누락 뷰 처리 또는 해당 그룹 제외 규칙이 필요하다.
- 원본은 1000×1000 PNG이며 평균 파일 크기는 약 1.17MB다. 40장을 RGB로 디코딩하면 사과당 약 114.4MB, 초당 2개는 약 228.9MB의 디코딩 데이터가 된다.
- i7-4790에서 40장을 각각 처리하고 Backend 요청 전송부터 Inference 응답 전체 수신까지 500ms를 만족한다고 미리 가정하지 않는다. 대표 프레임 축소, 배치 추론, 입력 해상도와 경량 모델을 실제 시험한 뒤 장수를 확정한다.
- 사과당 모델 입력은 4·8·12·16·40장을 같은 조건에서 비교한다.
- 224×224 수준의 입력 축소, 배치 추론, 경량 모델과 CPU 최적화 방식을 검토한다.
- 품종·품질 Macro F1을 비교하면서 Inference HTTP 구간 500ms 제한을 만족하는 구성을 최종 입력 장수로 채택한다.
- 40장 미만 그룹은 보유 이미지를 전송하고 Inference에서 누락 뷰 마스킹을 적용한다.
- 원본 Training과 Validation을 `group_no` 기준으로 합친 뒤 품종·품질 조합을 층화하여 70/15/15로 다시 분할하는 방안을 우선 적용한다.
- 그룹 단위 교차검증으로 품종·품질 Macro F1의 변동성도 확인한다.
- 최종 시험은 연속 사과 그룹 100개로 수행하고 평균·최대·p95 처리시간을 측정한다.

### 설비 가정과 선별 정책

- 사용 환경은 농가 품질 분류 설비의 상부 카메라다.
- 실제 하드웨어와 PLC 연동은 계획하지 않는다. 백엔드의 가상 제어 API 호출이 최종 범위다.
- 품종 2종과 품질 3단계의 조합에 대응하는 정상 bin 6개를 둔다.
- 저신뢰 또는 시스템 오류 입력을 보내는 재검사 bin 1개를 추가하여 목적지는 총 7개다.
- 가상 제어 명령에는 검사 ID, 품종, 품질등급, 목적 bin, 명령 생성 시각, 처리 상태와 오류 코드를 포함한다.
- 정상 bin 명령이 명시적으로 거부되면 재검사 bin 명령을 한 번 시도한다. 제어 기능 자체가 무응답이면 추가 호출 없이 재검사 필요와 전송 실패를 기록한다.

### 이미지와 검사 이력

- 정상 이미지는 추론 직후 삭제하며 MySQL에 이미지나 이미지 경로를 저장하지 않는다.
- 장애 발생 시에만 관련 이미지를 파일 저장소에 보관한다.
- 장애 이미지는 관리자가 확인·삭제할 수 있고, 저장공간 한도를 넘으면 오래된 이미지부터 자동 삭제한다.
- 검사 이력에는 검사 ID, 품종, 품질등급, 각 신뢰도, 목적 bin, 처리 상태, 오류 코드, 처리 시각, 실제 추론시간, 모델명과 모델 버전을 저장한다.
- 관리자는 이미 끝난 물리 분류 결과를 수정하지 않는다. 대신 `품종 의심`, `품질 의심`, `기타` 중 하나로 오판 의심 표시를 남길 수 있다.

### 웹 대시보드

- MVP에는 로그인을 넣지 않는다.
- 메인 대시보드는 스크롤 없이 한 화면에 표시한다.
- 메인 영역에는 현재 처리 중인 Simulator 이미지와 품종·품질별 통계 시각화를 배치한다.
- 최근 판정 결과는 보조 영역에 작게 표시하며 품종, 품질, 신뢰도, bin, 추론시간과 처리상태를 제공한다.
- 관리 화면은 조작을 위해 스크롤을 허용한다.
- 통계는 일별·기간별 검사량, 품종별 수량, 등급별 수량·비율, bin별 처리량, 재검사율, 평균 추론시간과 오판 의심 건수를 포함한다.

### 실행 환경과 성능

- 학습 환경에는 GPU가 있다.
- 서비스는 학원 컴퓨터의 Docker에서 실행하며 GPU가 없다.
- 배포 장비 기준 사양은 Intel Core i7-4790, RAM 16GB다.
- 목표 처리량은 초당 사과 그룹 2개다. Simulator는 500ms 간격으로 입력하고, Backend가 Inference 요청을 전송한 시점부터 응답 전체를 수신할 때까지 500ms 제한을 적용한다. 전체 검사 흐름은 Virtual Control 목표 100ms를 더해 약 600ms가 될 수 있으며 실제 달성 여부는 CPU 통합 시험으로 판정한다.

### 시연 입력과 공정 동작

- MVP에는 스마트폰 카메라, 사용자 이미지 파일 업로드와 실제 산업용 카메라·PLC를 포함하지 않는다.
- 저장된 사과 이미지를 일정 간격으로 전송하는 입력 시뮬레이터를 사용한다.
- 시뮬레이터는 Test 그룹에서 각도 기준으로 대표 12장을 선택하고, 사과 그룹별 multipart 요청을 500ms 간격으로 전송한다.
- 시연 화면에 시작·정지 기능을 두며 시스템의 기본 상태는 `ON`이다.
- 처리량이 입력 속도를 따라가지 못해도 공정 입력을 늦추거나 대기열에 쌓지 않는다. 제한 시간 내 판정하지 못한 사과는 별도 조작 없이 재검사 bin으로 보낸다.
- 대시보드에는 현재 처리 중인 사과를 표시한다. 동시 처리 구조라면 여러 장을, 순차 처리 구조라면 한 장을 표시한다.
- 정상 입력 이미지는 판정 후 메모리에서도 즉시 제거한다.
- 장애 이미지는 파일 개수 기준 최대 100개를 보관하며, 초과 시 가장 오래된 파일부터 자동 삭제한다.
- bin 코드와 품종·품질 조합의 실제 매핑 방식은 DB 담당자가 설계 문서에서 결정한다.

### 대시보드 동작 기준

- 특정 창 크기나 해상도에 고정하여 설계하지 않는다.
- 상태·제어·핵심 통계처럼 가독성을 유지해야 하는 UI와, 창 크기에 따라 줄어들 수 있는 실시간 이미지 영역을 구분하여 반응형으로 배치한다.
- 대시보드의 구체적인 위치와 레이아웃은 미리 고정하지 않는다. 프론트엔드 구현 과정에서 조정하되 필수 표시 항목과 무스크롤 원칙을 지킨다.
- 기본 통계 기간은 `오늘`이다.
- 대시보드 통계는 검사마다 다시 그리지 않고 1초마다 갱신한다.
- 입력 시뮬레이터는 준비된 이미지를 목록 순서대로 사용한다.
- `정지`는 새로운 입력만 중단하며 이미 처리 중인 검사는 끝까지 처리한다.
- `시작`을 누르면 중단한 이미지 위치부터 이어서 입력한다.

### 시뮬레이터 데이터와 처리 제한시간

- 시뮬레이터는 모델 학습 데이터와 분리된 시험 이미지를 사용한다.
- 별도의 고정된 시연용 이미지 목록은 만들지 않는다.
- 이미지 목록의 끝에 도달하면 첫 이미지부터 다시 반복한다.
- Docker 서비스가 실행되면 웹 대시보드 접속 여부와 관계없이 입력과 검사를 계속 수행한다.
- Inference 제한시간 500ms는 Backend 요청 전송부터 응답 전체 수신까지이며 Inference 측 대기·전처리·모델 실행·응답 직렬화를 포함한다. 이 시간을 넘긴 사과의 물리적 목적지는 재검사 bin으로 확정한다.
- 모델 파일은 `models/`에 보존한다.
- 500ms 이후 도착한 추론 결과는 bin 명령을 변경하지 않고 진단용으로 저장한다. 구체적인 비동기 수신 방식은 Backend 구현 설계에서 정하며 DB 장애나 서버 재시작 시 유실을 허용한다.
- 시간 초과 후 도착한 결과는 정상 품종·품질 통계에서 제외한다.
- 병렬 처리 여부와 동시 처리 개수는 i7-4790 CPU 환경의 성능시험 후 결정한다.

### 통계와 이력 관리

- 모든 업무 시각은 한국 표준시(`Asia/Seoul`)를 사용하며 밀리초 단위까지 기록한다.
- 기본 `오늘` 통계는 한국 시간 00:00:00.000부터 23:59:59.999까지다.
- 품종·품질 통계에서는 `시간 초과` 또는 `시스템 오류`인 건만 제외한다. 저신뢰 건은 두 조건에 해당하지 않으면 품종·품질 통계에 포함한다.
- 전체 검사량에는 정상 bin과 재검사 bin을 모두 포함한다.
- 재검사율은 `재검사 건수 ÷ 전체 검사 건수`로 계산한다.
- 검사 이력의 건수 상한은 86,400건이다. 상한에 도달할 때마다 오래된 8,640건을 삭제하며, 초당 사과 그룹 2개 기준 실제 보존 범위는 약 10.8~12시간이다.
- 관리 화면은 날짜, 품종, 품질, bin, 처리상태, 오류 유형과 오판 의심 유형으로 검사 이력을 필터링한다.
- 필터링한 검사 이력과 통계를 CSV로 내보낼 수 있게 한다. CSV는 재학습 필요성 및 성능 추세를 판단하는 근거로 활용한다.
- CSV 내보내기에는 별도의 행 수 제한을 두지 않으며 현재 보존 중인 필터 결과 전체를 대상으로 한다.
- Docker 재시작 후에는 마지막 처리 이미지 위치부터 이어서 입력한다.
- MySQL은 기록용이므로 DB 장애가 발생해도 정상 판정 사과를 재검사 bin으로 보내지 않는다. 저장 실패는 application log와 상태 정보에 기록하며 DB 자체에 실패 이력을 저장할 수 있다고 가정하지 않는다.
- 대시보드에는 입력 시뮬레이터, 모델, 백엔드 API, MySQL 상태와 최근 오류 시각을 표시한다.
- 프로그램 로그는 크기 제한을 적용하고 오래된 로그부터 자동 삭제한다. 구체적인 크기와 보존 방식은 MLOps 담당자가 정한다.
- DB 장애 중 저장하지 못한 검사 이력은 유실을 허용한다. 메모리 임시 보관분도 서버 재시작 시 사라져도 된다.
- 마지막 처리 이미지 위치는 DB가 아닌 Docker 볼륨의 작은 상태 파일에 저장한다.
- 모델·백엔드 서비스 구성은 `yuudong123/ai-first-project`의 구성을 확인하여 같은 방향으로 정한다.
- 세부 기술 스택은 각 파트 담당자가 선정하고 `docs/`에 기록한다.
- 구성 요소 상태는 모델 테스트 추론, API 상태 응답, MySQL 연결·간단 조회, 시뮬레이터의 최근 1초 입력 여부로 판정한다.
- DB 장애 중에는 마지막으로 저장된 시점까지의 통계를 표시하고 `DB 연결 끊김` 경고를 노출한다.

### 참고 프로젝트 기반 서비스 구성 검토

- 참고 저장소: `yuudong123/ai-first-project`
- 참고 프로젝트는 Docker Compose에서 `producer`, `inference`, `api`를 별도 서비스로 실행한다.
- Producer가 Kafka에 데이터를 발행하고 inference가 소비·추론한 뒤 최신 상태를 만들며, FastAPI가 웹에 상태 API를 제공한다.
- CQC도 입력 시뮬레이터, 추론 작업자, 백엔드 API를 별도 컨테이너로 나누는 원칙을 적용한다.
- 프론트엔드는 추론 컨테이너를 직접 호출하지 않고 백엔드 API만 사용한다.
- Kafka는 사용하지 않는다. 분리된 서비스는 HTTP 기반으로 연결한다.
- 참고 프로젝트처럼 입력 시뮬레이터, inference, API 실행 단위를 분리한다.
- Kafka가 없는 CQC에서는 입력 시뮬레이터가 백엔드 검사 API로 이미지를 보내고, 백엔드가 inference HTTP API를 호출한다.
- inference 서비스는 품종·품질 예측과 라벨별 확률·신뢰도, 추론시간, 모델·전처리 버전과 실제 사용 프레임 수를 반환하며 bin·재검사·DB·제어 정책은 포함하지 않는다.
- 백엔드는 Inference HTTP 구간 500ms 제한, 저신뢰·오류 판정, bin 결정, DB 기록과 가상 제어 명령을 책임진다.
- 백엔드가 inference 서비스에 연결하지 못하거나 호출에 실패하면 시스템 오류로 판정하고 재검사 bin으로 보낸다.
- MVP는 Simulator 자동 입력 전용이며 스마트폰 카메라, 사용자 이미지 파일 업로드와 실제 산업용 카메라 입력을 제공하지 않는다.
- 백엔드는 처리 중인 이미지를 메모리에만 임시 보관하고 프론트엔드가 임시 API로 조회하게 한다.
- 처리 완료 시 이미지를 백엔드 메모리에서 즉시 제거하고 임시 API 접근을 종료하며 브라우저 캐시를 금지한다.
- 병렬 처리 시 프론트엔드는 처리 중인 모든 이미지를 카드로 표시하고, 순차 처리 시 카드 한 개만 표시한다.
- 장애 이미지는 일반 대시보드에 노출하지 않고 관리 화면의 장애 목록에서만 조회한다.

### 가상 제어와 시연 기능

- 서버 자원을 고려하여 가상 제어 장치를 별도 Docker 컨테이너로 만들지 않는다. 백엔드 내부 모듈과 API로 구현한다.
- 정상 제어 응답에는 명령 ID, 검사 ID, 목적 bin, 수신 시각과 성공 여부를 포함한다.
- 정상 bin 명령이 거부되면 재검사 bin 명령을 한 번 추가로 시도한다.
- 가상 제어 기능 자체가 응답하지 않으면 재검사 필요 상태와 명령 전송 실패를 이력에 남긴다.
- 가상 제어 응답 목표는 100ms 이내다.
- 관리 화면에 `시연용 기능` 토글 메뉴를 만들고, 장애 시나리오 버튼이나 체크박스를 그 안에 배치한다.
- 가상 제어 실패 상태를 시연 메뉴에서 켜고 끌 수 있게 한다.
- 처리량은 초당 사과 그룹 2개, Inference HTTP 구간 제한시간은 500ms, 가상 제어 응답 목표는 100ms로 확정한다. 파이프라인의 겹친 실행을 허용하며 개별 흐름은 약 600ms가 될 수 있다.
- 시연용 토글 메뉴에는 추론 시간 초과, 추론 서비스 오류, DB 연결 오류, 정상 bin 명령 거부와 가상 제어 무응답을 모두 제공한다.
- Docker 재시작 시 모든 시연 장애 토글은 `OFF`로 초기화한다.
- 하나 이상의 장애 토글이 활성화되면 일반 대시보드 상단에 `시연 장애 활성화` 경고를 표시한다.

### 최종 기획 질의 확정 사항

#### 데이터·모델

- 통합 데이터는 품종×품질 조합 층화, `group_no` 단위, seed 42로 70/15/15 분할한다.
- 최종 Test를 제외한 Train·Validation에서 5-Fold Group Cross Validation을 수행한다.
- Simulator는 각 그룹에서 대표 12장을 선택하고 12장 미만 그룹은 보유 이미지를 전송한다. Inference는 누락 뷰 마스킹으로 해당 그룹을 유지한다.
- 단일 그룹 결합 모델과 품종·품질 분리 모델을 비교한다.
- 최종 Test는 모델 구조, 입력 장수와 신뢰도 기준을 확정한 뒤 한 번만 평가한다.
- 모델 산출물은 모델 파일, 클래스 매핑, 입력 크기, 프레임 선택 규칙, 전처리 설정, 신뢰도 기준, 평가 결과와 모델 버전을 포함한다.

#### 이미지 전달과 API

- 다각도 이미지는 Base64 JSON 대신 `multipart/form-data`로 전달한다. Base64의 약 33% 용량 증가와 추가 인코딩·디코딩·메모리 복사를 피한다.
- Backend→Inference 요청은 `inspection_id`, `images[]`와 이미지별 `view_index`, `angle_direction`, `verticality_angle`, `horizontality_angle`을 포함한다. `group_no`와 정답 품종·품질은 모델 입력에 포함하지 않는다.
- simulator·backend·inference·DB·제어 이력·application log는 동일한 `inspection_id`를 사용한다.
- inference 응답은 동일 `inspection_id`, 품종 예측과 `fuji`·`yanggwang` 확률 객체·신뢰도, 품질 예측과 `L`·`M`·`S` 확률 객체·신뢰도, 추론시간, 모델명·버전, 전처리 버전과 실제 사용 프레임 수를 포함한다.
- Backend는 class index 순서를 추측하지 않는다.
- 오류 코드는 백엔드 담당자가 초안을 만들고 모델·프론트·MLOps 담당자가 검토한다.

#### 검사 상태

- 단일 `status`로 검사 전체를 표현하지 않고 `inspection_status`, `control_status`, `persistence_status`와 `error_code`를 논리적으로 분리한다.
- DB 저장 실패는 정상 선별 결과나 제어 성공 상태를 덮어쓰지 않는다.
- 구체적인 Enum 값과 전이표는 API·DB 계약 단계에서 확정한다.
- 시간 초과 후 결과는 진단 상태로만 관리하며 확정 bin과 정상 품종·품질 통계를 변경하지 않는다.

#### 화면·시연

- 대시보드 차트 종류는 강사에게 확인한 뒤 확정한다.
- 실시간 시계열은 최근 30초를 1초 단위로 표시한다.
- 시간 조회 빠른 선택값은 1분·5분·10분·30분을 제공한다.
- CSV는 필터 결과 전체를 UTF-8 BOM으로 생성한다.
- 장애 이미지 관리 화면은 미리보기, 검사 ID·오류·시각, 개별 삭제와 전체 삭제를 제공하며 다운로드는 제외한다.
- bin 매핑 변경은 서버 재시작 없이 다음 검사부터 적용한다.
- 장애 토글은 복수 선택할 수 있고 활성 항목을 대시보드 경고에 모두 표시한다.
- 장애 토글은 `전체 요청` 또는 `다음 1건` 적용을 선택할 수 있다.
- 로그인 없는 내부망 MVP에서는 시연 메뉴를 누구나 사용할 수 있으며 기본 접힘 상태로 둔다.

#### Docker·기술 문서

- Backend는 Python + FastAPI, Database는 MySQL, Backend와 Inference 간 통신은 HTTP를 사용한다. 구체적인 라이브러리와 버전은 `backend-stack.md`에서 확정한다.
- Compose 서비스는 `simulator`, `inference`, `backend`, `frontend`, `mysql`로 구성한다.
- 컨테이너 재시작 정책은 `unless-stopped`다.
- MySQL·inference 상태 확인 후 backend, backend 상태 확인 후 simulator·frontend를 시작한다.
- inference가 준비되지 않아도 simulator 입력은 유지하며 시스템 오류·재검사로 처리한다.
- Docker 볼륨에는 MySQL, 장애 이미지, 마지막 시뮬레이터 위치와 순환 로그를 보존한다.
- 파트별 기술 스택은 `model-stack.md`, `backend-stack.md`, `frontend-stack.md`, `mlops-stack.md`에 담당자가 작성한다.

#### Git·CI/CD·완료 조건

- `main`은 발표 전까지 거의 사용하지 않고 최종 발표 버전을 표시하는 용도로 사용한다. `dev`는 통합, `feat/*`는 개인 작업 브랜치다.
- `feat/* → dev`는 Pull Request와 최소 1명 확인 후 병합한다.
- CI는 문법·단위 테스트, API 계약, 모델 로딩, DB 마이그레이션과 Compose 설정을 검사한다.
- 자동 배포 대상은 `dev`뿐이며 `main` 자동 배포는 하지 않는다.
- 모델 파일과 체크포인트는 용량과 무관하게 Git에서 제외하고 배포 환경에 별도로 제공한다.
- 배포 실패 시 기존 실행 버전을 유지하고 CI에 실패 원인을 표시한다.
- 최종 시험은 정상 100개, 초당 2개, 장애 5종, 재시작·위치 복구, DB·장애 이미지 순환 삭제와 CSV 일치 여부를 포함한다.
- 발표 3일 전에 기능을 동결하며 이후에는 치명적 오류만 수정한다.

## 2026-09-21 v1 모델 설정과 시험 전 승인 기준

- 5-fold 비교 결과에 따라 모델 구조는 품종·품질별 MobileNetV3 Small 인코더를 사용하는 `separate`, 입력은 동일 사과의 대표 12장으로 고정한다.
- 두 과제 Macro F1 평균은 `0.9839 ± 0.0163`, 품질 Macro F1 평균은 `0.9809`다.
- 최종 학습 epoch는 5개 fold 최고 epoch `20·15·16·19·20`의 중앙값인 19로 정한다.
- 신뢰도 기준은 품종 0.50, 품질 0.50으로 고정한다. Test를 제외한 validation 152그룹에서 150그룹을 자동 처리하며 coverage 98.68%, 자동 처리 구간 품종 정확도 98.67%, 품질 정확도 98.00%다.
- 최종 Test를 열기 전에 품종·품질 Macro F1 각각 0.90 이상을 모델 승인 기준으로 고정한다. AI Hub 공개 기준모델 F1 0.89보다 높은 최소 기준이다.
- 모델 목표 입력은 12장이고 HTTP 요청은 1~12장, 전체 크기는 24MiB로 고정한다. 12장 미만은 마스크 패딩한다. 실제 179그룹의 12장 원본 합계 최댓값은 19,998,364바이트다.
- 운영 동시 처리 수는 안전한 기본값 1로 둔다. 최종 체크포인트의 i7-14700F 재측정은 p95 113.6ms·초당 9.31건이지만, i7-4790 수용시험 전에는 목표 장비 성능 승인으로 해석하지 않는다.
