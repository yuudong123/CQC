# 개발 중 문제 해결 사례

발표에서 "무엇이 문제였고 어떻게 찾아 어떻게 풀었는지"를 보여주기 위한 소재 모음이다. 모든 수치는 원본 결과 파일이나 작업 문서에 근거가 있다. 날짜별로 추가한다.

## 2026-09-30

### 한눈에 보기

| # | 문제 | 발견 방법 | 해결 | 결과 |
|---|---|---|---|---|
| 1 | 모델이 맞혀도 신뢰도가 낮아 재검사가 많음 | 개발 데이터 신뢰도 보정 오차(ECE) 측정 | 온도 보정(temperature scaling) + 임계값 재선정 | 재검사 23.7%→16.4%, 시연 13.9%→8.3% |

| 3 | 사진 해제가 모델보다 3~4배 느림 | 서버 응답 헤더로 단계별 시간 분리 | 12장 병렬 해제 | 서버컴 추론 p95 309ms, 500ms 초과 0/36 |
| 4 | 실제 Backend에 붙이자 DB 중단 시 선별이 멈춤 등 4건 | 웹을 실제 Backend에 붙여 장애를 직접 일으킴 | 담당 파트에 재현 절차와 함께 요청 | 결함 4건 문서화, 수정 진행 중 |
| 5 | 물류를 MVP에 넣을지 아직 모르는데 시연은 해야 함 | 목요일 결정 일정 | 서버 없이 브라우저에서 도는 가상 물류로 전환 | 결정과 무관하게 시연 가능 |
| 6 | Simulator를 배포했는데 입력이 0건 | 배포 후 관제 상태를 직접 확인 | 기동 시 자동 재생 + "실제로 보내고 있는지"를 health로 검사 | 배포 성공 = 실제 재생 중 |

### 1. 신뢰도 보정으로 재검사 줄이기

- **상황:** 모델은 대부분 맞히는데 신뢰도가 낮게 나와 기준(0.50) 미만 재검사가 많았다. 개발 데이터(OOF) 기준 재검사 23.7%.
- **원인:** 모델 출력 확률이 실제 정답률과 맞지 않았다. 품질 신뢰도 보정 오차(ECE) 0.259.
- **해결:** 온도 보정. 품질 T=0.391, 품종 T=0.384로 확률을 다시 계산했다. 예측 라벨은 그대로이고 신뢰도만 실제 정답률에 맞춘다. 가중치 파일(`model.pt`)은 바꾸지 않고 설정 파일(`model.json`)만 바꿨다(체크섬 동일).
- **임계값:** 보정 후 품종 0.50, 품질 0.60으로 다시 골랐다.
- **결과:**

| 항목 | 보정 전 | 보정 후 |
|---|---:|---:|
| 품질 ECE | 0.259 | 0.081 |
| 개발 데이터 재검사율 | 23.7% | 16.4% |
| 자동 처리 건 품질 정확도 | 92.2% | 92.9% |
| 시연 36묶음 재검사율 | 13.9% | 8.3% |

- **발표 포인트:** 모델을 다시 학습하지 않고, 확률을 실제 정답률에 맞추는 것만으로 재검사를 3분의 1 줄였다. 자동 처리 정확도는 떨어지지 않았다.
- 근거: [DM-08](../wbs/[DM-08]%20신뢰도·병렬%20처리%20기준.md), [보정 결과](../wbs/results/v2-calibration-oof-20260930.json)

### 2. 비교 기준값 버그

- **상황:** 보정 보고서의 "현재 임계값 기준" 행은 보정 전 모델 상태를 보여줘야 한다.
- **원인:** 이 기준값을 보정 전 확률이 아니라 보정 후 확률로 계산하고 있었다. 보정 전후 비교가 성립하지 않았다.
- **해결:** 기준값을 온도 1.0(보정 전)으로 계산하도록 고치고, 같은 실수를 막는 회귀 시험을 추가했다.
- **발표 포인트:** 결과가 좋아 보여도 나빠 보여도 비교 기준부터 검증했다.

### 3. 느린 곳은 모델이 아니라 사진 해제

- **상황:** 추론 한 건 시간을 줄여야 했다.
- **발견:** Inference 응답에 `Server-Timing` 헤더를 넣어 사진 해제·모델·전체 시간을 나눠 봤다. 클라우드 2 vCPU에서는 PNG 12장 해제가 모델 계산보다 3~4배 오래 걸렸다.
- **해결:** 12장을 병렬로 해제한다. 동시 요청 수는 늘리지 않는다(2로 올리면 같은 CPU를 나눠 써서 p95 528ms로 오히려 느려짐).
- **결과 (서버컴, 실제 시연 사진 36묶음):** 해제 p95 149ms, 모델 p95 161ms, 전체 p95 309ms, 500ms 초과 0건.
- **측정 중 문제:** Jenkins 자동 재배포가 측정 도중 두 번 일어나 연결이 끊겼다. 3분간 상태가 안정된 것을 확인한 뒤 다시 쟀고, 스크립트가 실패 요청을 기록하게 바꿨다.
- **발표 포인트:** 감으로 모델을 바꾸기 전에 단계별 시간을 먼저 쟀고, 병목이 모델이 아니었다.
- 근거: [서버컴 서버 내부 지연](../wbs/results/server-real-photos-20260930.json)

### 4. 실제 Backend에 붙여 보니 나온 결함 4건

- **상황:** 화면은 예시 데이터로 다 동작했지만 실제 Backend·DB·모델과 붙인 적은 없었다.
- **방법:** 웹을 실제 Backend에 연결해 500ms 간격으로 3,600건을 넣고(31.5분), MySQL과 Inference를 일부러 멈췄다.
- **확인된 정상 동작:** 브라우저 메모리 안정(heap 중앙값 22~23MB, DOM 노드 2,074개 고정), DB 50초 중단 시 "마지막 수신 시각·기존 화면 유지" 경고 후 재시작 2초 뒤 자동 복구, 장애 이미지 100장 상한 유지.
- **발견한 결함:**
  1. DB가 멈추면 선별도 멈춘다(7~8초 뒤 HTTP 500). 요구사항은 "DB가 죽어도 선별은 계속"
  2. 현재 처리량이 실제보다 낮게(0.0) 표시된다
  3. Inference 연결 실패가 "시간 초과"로 기록된다
  4. Inference 상태가 항상 "알 수 없음"
- **작은 표시 수정:** 신뢰도가 `66.10390000000001%`처럼 보여 소수 첫째 자리로 고쳤다.
- **발표 포인트:** 예시 데이터로 통과한 기능도 실제 장애를 일으켜 보고 나서야 결함이 드러났다.
- 근거: [FE-08](../wbs/FE-08.md), [연속 관제 기록](../wbs/results/fe-long-run-real-backend-20260930.json), [협업 요청](../wbs/협업공지/파트별-협업-요청.md)

### 5. 결정되지 않은 범위를 시연 가능하게 만들기

- **상황:** 물류(출품·경매·배차)를 MVP에 넣을지 목요일(10-01)에 결정한다. 그 전에 시연은 가능해야 했다.
- **해결:** 물류 서버 없이 브라우저 안에서 같은 규칙으로 도는 가상 물류로 바꿨다. 실제 API 모드는 설정 하나(`NEXT_PUBLIC_LOGISTICS_MODE=live`)로 되돌릴 수 있다.
- **발표 포인트:** 결정을 기다리며 멈추지 않고, 어느 쪽으로 결정돼도 버릴 코드가 없게 만들었다.

### 6. "배포 성공"인데 입력이 0건

- **상황:** Simulator를 배포했고 Jenkins도 성공했는데 오늘 검사가 0건이었다.
- **발견:** 관제 상태(snapshot)에서 Simulator `stopped`, `running=false`를 확인했다. 기본값이 정지라 누군가 켜야 입력이 시작됐다. health는 프로세스가 살아 있는지만 봤다.
- **해결:** 기동 시 데이터와 재생 위치를 검증한 뒤 자동 재생한다. health는 "재생 중이고 최근 30초 안에 검사 전송이 성공했는지"를 보고, Jenkins 배포 검증도 같은 조건을 쓴다.
- **발표 포인트:** "컨테이너가 떠 있다"와 "서비스가 일을 하고 있다"는 다르다. 배포 성공 기준을 실제 동작으로 바꿨다.
- 근거: [Simulator 배포 문서](../wbs/reference/MO/simulator-deployment.md)

### 7. 부분 성능과 전체 성능은 다르다

- **상황:** 추론 서버 안에서는 한 건 271ms라 초당 3.7건이 가능해 보였다. 목표는 초당 2건.
- **발견:** Simulator를 실제로 돌린 뒤 운영 이력 200건의 요청 간격을 분석했다. 실제 처리량은 **초당 0.63건**이었다. 한 건 왕복이 약 1.4초다.
- **원인:** 모델 계산은 150ms뿐이다. 나머지는 13.8MB 사진 묶음을 Simulator→Backend→Inference로 두 번 넘기고 두 번 해석하며 DB에 저장하는 시간이다. 입력 간격(500ms)이 처리 주기보다 짧아 요청이 계속 밀렸다.
- **해결:** 입력 간격을 처리 주기 p90(1.8초)보다 긴 2000ms로 맞췄다. 설정한 속도와 실제 속도가 같아지고 요청이 쌓이지 않는다.
- **결과:** 시연 처리량 초당 0.5건. 초당 2건 목표는 현재 구조의 서버컴에서 미달로 기록했다. 병합 후 시간 초과(현재 3%)가 줄어드는지 확인한다.
- **발표 포인트:** 부품별 벤치마크(초당 3.7건)만 보고 통과라고 하지 않고, 전체 흐름을 재서 실제 한계(0.63건)를 찾았다. 목표 미달도 숫자 그대로 밝힌다.
- 근거: [DM-08 운영 경로 처리량](../wbs/[DM-08]%20신뢰도·병렬%20처리%20기준.md), [Simulator 처리량](../wbs/results/server-simulator-throughput-20260930.json)

### 발표 흐름 제안

1. **측정 → 원인 → 조치 → 재측정** 순서를 하나의 패턴으로 보여준다(사례 3·7).
2. 모델 개선은 재학습 없이 보정만으로 얻은 효과를 강조한다(사례 1).
3. "예시 데이터로 통과"와 "실제 환경에서 통과"를 구분한 태도를 보여준다(사례 4·6).
4. 목표 미달(초당 2건)은 숨기지 않고 원인과 다음 개선 방향(사진 전달 방식)을 함께 말한다(사례 7).
