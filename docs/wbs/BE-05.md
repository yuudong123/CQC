# BE-05 검사 이력·오늘 통계·필터·CSV API

- WBS 코드: `BE-05`
- 담당: 홍준희
- 역할: 백엔드·DB
- WBS 예정 기간: 2026-09-26 ~ 2026-10-02
- 완료 확인일: 2026-09-29
- 상태: 완료 (BE-05 범위)

## 1. 작업 목적

BE-04의 검사 판정·가상 제어 결과를 MySQL에 기록하고, Frontend 관제 계약에 맞춰 검사 이력·통계·CSV를 실제 저장 데이터에서 제공한다. BE-04 당시의 정상 6-bin은 완료 이력으로 유지하되, 이 단계의 시연 배차와 DB 계약에는 최신 12-bin 정책을 적용했다.

작업은 다음 네 단계로 진행했다.

```text
1단계: 12-bin DB 계약·후속 Alembic migration·13개 seed
2단계: DB bin mapping·검사/제어/오류 Repository·저장 수직 흐름
3단계: Frontend 관제 검사 이력·필터·페이지 조회
4단계: snapshot·통계·검사 CSV·통계 CSV
```

## 2. WBS 완료 기준과 범위

`docs/wbs.md`의 BE-05 완료 기준은 검사 이력·오늘 통계·필터·CSV API, 한국시간 밀리초 처리, 정상 통계 제외 규칙과 필터 전체 CSV의 UTF-8 BOM이다. 현재 구현은 기존 `POST /v1/inspections`를 유지하면서 아래 조회 API를 추가한다.

| API | 제공 내용 |
|---|---|
| `GET /v1/quality/inspections` | 완료 검사 이력, 필터, 고정 시점 페이지 조회 |
| `GET /v1/quality/snapshot` | 실제 DB 기반 최근 결과·오늘 집계·최근 30초 시계열 |
| `GET /v1/quality/statistics` | 선택 필터와 기간에 대한 DB 집계 |
| `GET /v1/quality/inspections.csv` | 현재 필터에 맞는 전체 검사 이력 |
| `GET /v1/quality/statistics.csv` | 오늘 또는 선택 기간 통계와 시계열 |

이 문서의 `완료`는 BE-05 Backend 기능 범위의 완료를 뜻한다. 실제 Simulator·Inference 사진·Frontend·Compose를 모두 잇는 시연 통합, DB 전체 장애 중 선별 지속, 보존 순환 삭제와 부하 수용시험까지 완료했다는 의미는 아니다.

## 3. 1단계 — 12-bin DB 계약

초기 revision을 고치지 않고 `20260929_02_be05_12_bin_contract.py`를 추가했다. `inspections`에 `virtual_brix`, `brix_source`, `brix_is_measured`, `sweetness_band`를 추가하고, `bin_mappings`의 정상 조합 unique key에 `sweetness_band`를 포함했다. 기존 `mapping_key` 및 사용하지 않는 late 예측 컬럼은 후속 revision에서 정리했다.

정상 seed는 품종 2 × 외관 등급 3 × 당도 구간 2의 `DEMO_BIN_01`~`DEMO_BIN_12`이며, 재검사 seed `TEST_REINSPECTION_BIN` 1개를 더해 총 13개다. 동일 bin code의 같은 seed는 건너뛰고 충돌하는 기존 데이터는 migration 오류로 드러낸다.

- `virtual_brix`는 9~18 범위의 시연용 비실측 배차 값이며 `brix_is_measured=false`다.
- `virtual_brix < 12.0`은 `less_sweet`, `>= 12.0`은 `sweet`이다. 정확히 12.0은 `sweet`이다.
- `commercial_grade`는 12-bin 배차 키가 아니다.
- 시연 요청에서 가상 당도가 없으면 과거 6-bin으로 보내지 않고 재검사 bin을 사용한다.

## 4. 2단계 — DB mapping과 검사 저장

기본 앱 구성에서 `InspectionService`가 `BinMappingRepository`, `InspectionPersistence`, Inference Client와 Virtual Control을 조정한다. 정상 bin은 품종·외관 등급·당도 구간으로 DB에서 찾고, 재검사 bin도 활성 mapping에서 찾는다. Mock 제어 구현은 유지하며 실제 장치 통신으로 확대하지 않았다.

검사 시작 행은 별도 트랜잭션으로 기록하고, 최종 검사 결과·제어 시도·오류는 하나의 트랜잭션으로 확정한다. `inspections`, `control_attempts`, `inspection_errors`, `bin_mappings` 각각의 DB 접근은 Repository에 둔다. `persistence_status`는 검사 판정·제어 상태와 별도로 다루며 저장 실패가 이미 결정된 bin이나 제어 결과를 바꾸지 않는다. 저장 실패 시 로그를 남기고, 가능한 경우 기존 검사 행에 실패 상태를 한 번 기록한다.

업무 시각의 DB `DATETIME(3)`은 UTC naive 값으로 저장하고, 조회 응답의 날짜·시각과 오늘 경계는 KST로 변환한다. 밀리초 정밀도와 KST 자정 경계를 테스트했다. 이미지 BLOB·이미지 경로·`storage_key`는 검사 DB에 추가하지 않았다.

단, **DB 전체 장애로 `bin_mappings` 조회에 실패하면 현재 구현은 목적 bin을 결정하거나 Virtual Control을 호출하지 못한다.** 저장만 실패한 경우의 선별 지속과는 다른 장애다. 마지막 정상 mapping의 메모리 fallback/cache와 DB 장애 중 선별 지속은 BE-09의 명시적 후속 과제이며, BE-05에서 해결된 것으로 표시하지 않는다.

## 5. 3단계 — 검사 이력과 공유 계약

`GET /v1/quality/inspections`는 완료된 검사만 `completed_at DESC, inspection_id DESC`로 정렬한다. `snapshotAt`으로 조회 상한을 고정해 새 검사가 들어와도 페이지 기준이 밀리지 않도록 한다. 기간, 품종, 등급, bin, 처리 상태, 오류, 오판 의심을 필터링하고 DB에서 페이지 수량·전체 건수·bin 선택지를 조회한다. KST 날짜 필터는 UTC 저장 시각의 경계로 바꿔 적용한다.

저장된 내부 코드와 상태는 관제 `Result` 계약으로 변환한다. `control=NOT_REQUESTED`는 제어 요청을 하지 않은 유효 상태로 그대로 전달하며 `HISTORY_CONTRACT_ERROR`로 바꾸지 않는다. `SUCCEEDED`, 정상 bin 거부 후 대체 성공인 `FALLBACK`, `NO_RESPONSE`, `REJECTED`, `FAILED`의 의미는 구분한다. 공유 OpenAPI와 Frontend 타입·검증·표시는 이 계약에 맞춰 보완되었다.

잘못된 필터·날짜·미래 `snapshotAt`은 계약 오류 응답으로, DB 미설정·조회 실패는 `503 DB_UNAVAILABLE`로 처리한다. 응답은 `Cache-Control: no-store`다. 저장된 값 자체를 관제 계약으로 표현할 수 없는 경우의 `HISTORY_CONTRACT_ERROR`는 별도로 유지한다.

## 6. 4단계 — snapshot·통계·CSV

`snapshot`은 `source=backend`로 실제 DB에 저장된 최근 이력 최대 200건, 최근 오류 최대 50건, KST 오늘 집계, 최근 30초의 1초 단위 시계열과 1·5·10·30분 누적을 반환한다. 현재 미구현인 Simulator 조작·장애 토글·검수·장애 이미지 삭제는 capability를 비활성화한다. `state.concurrency`, `state.sequence`, `state.tick`, `state.scope`, `retention.history`는 실제 값이 아직 없어 응답에서 생략한다. 공유 OpenAPI와 Frontend 타입·검증도 optional로 맞췄으며, 참조 서버의 시연값을 실제 Backend 기본값으로 사용하지 않는다.

통계는 전체 행을 메모리로 읽지 않고 DB 집계 쿼리로 계산한다. 전체 검사량에는 정상·재검사를 포함한다. timeout·시스템 오류는 정상 품종·등급 통계에서 제외하고, 유효한 저신뢰 모델 응답은 포함한다. bin 집계는 제어 성공 조건을 적용한다. 오늘의 날짜와 조회 기간은 KST를 기준으로 한다.

두 CSV는 `snapshotAt`과 필터를 공유한다. 검사 CSV는 현재 페이지가 아니라 필터 결과 전체를 순회하며, 이미지 데이터는 포함하지 않는다. 통계 CSV는 날짜 필터가 있으면 해당 기간의 집계, 없으면 KST 오늘 집계와 선택한 1·5·10·30분 시계열을 내보낸다. UTF-8 BOM, `Content-Disposition` 첨부 파일명, `no-store`를 적용하고 CSV 수식 주입을 막는 값 처리를 사용한다.

## 7. 구현 구조와 검증

핵심 책임 방향은 기존 원칙을 유지한다.

```text
Router
→ Service (검사 처리 / 관제 응답 조정)
→ Repository (mapping / 저장 / 이력 / 통계)
→ MySQL
```

주요 구현 위치는 `src/api/services/inspections.py`, `src/api/repositories/`, `src/api/routers/quality_history.py`, `src/api/routers/quality_operations.py`, `src/api/services/quality_history.py`, `src/api/services/quality_operations.py`, `src/api/db/migrations/versions/20260929_02_be05_12_bin_contract.py`다. 공유 필드 계약은 `docs/contracts/quality-operations.openapi.json`을 따른다.

관련 테스트는 migration·mapping·저장·검사 Service, 이력 필터와 adapter, KST 경계·통계 제외 규칙·CSV, 실제 MySQL 통합 경로를 포함한다. 실제 MySQL 통합 테스트는 `CQC_TEST_DATABASE_URL`이 설정된 테스트 DB에서 실행하도록 작성되어 있으며 테스트 데이터 정리를 포함한다.

문서 작성 시점에 `.venv\Scripts\python.exe -m pytest tests/api -q -rs -p no:cacheprovider`를 실행한 결과는 **119 passed, 3 skipped, 2 warnings**다. 건너뛴 3개는 `CQC_TEST_DATABASE_URL`이 없어 실제 MySQL을 사용하는 통합 테스트이며, 이번 실행에서 실DB 경로를 재검증한 것으로 주장하지 않는다. 경고 2개는 TestClient 관련 deprecation이다. 코드 변경은 없으므로 Ruff와 Frontend 테스트는 이번 문서 작업에서 재실행하지 않았다.

## 8. 후속 작업과 완료 경계

1. **BE-06:** 정상 이미지 처리 후 폐기·캐시 금지와 별도 장애 이미지 보존·삭제. BE-05 검사 DB에 이미지를 저장하지 않는다.
2. **BE-07:** Simulator 상태·시작/정지·위치 복구·장애 토글을 실제 값으로 연결한다. 현재 snapshot의 미구현 값은 시연값으로 채우지 않는다.
3. **BE-08:** 실제 시연 이미지·Inference HTTP·Frontend·Compose·DB migration 배포를 묶어 전체 흐름을 검증하고 late-result 진단 저장을 확인한다.
4. **BE-09:** DB 장애 시 마지막 정상 mapping fallback 등 선별 지속, 86,400건 상한/8,640건 순환 삭제, 동적 bin 무재시작 반영을 검증한다.
5. **BE-10:** 연속 요청·오류·필터·CSV 수용시험과 실제 데이터량의 조회 성능을 확인한다. 현재 index는 주로 `created_at` 기준이므로 `completed_at` 정렬·기간 조회의 성능도 이 단계에서 확인한다.
