[선택 증거와 출처](qa-be-sim11-local-20261013/README.md). 기존73검사를 제외한 신규870건 중 첫869건을 전체 순환 구간으로 식별했다. 고유 묶음869개, 누락·묶음 중복·순서 오류·inspection_id 중복0건을 순서표와 DB 원자료로 재확인했다. 868→0 경계는 `1c0bb931-5323-4845-bfe3-c48f30f84cff` → `6f95d606-0d60-4617-bb01-66d79702fc86`이며 같은 묶음의 과거 ID와 새 ID가 다르다. 334회 관찰에서 concurrency4 유지, 신규870건 제어/저장 성공·시스템 오류0이다. 첫869건은 정상779·저신뢰90, 추가1건은 다음 바퀴 index73이다. position은 절대 순번으로 73→942→943이며 modulo 위치와 구분한다. 약29분 실행 후 stopped·concurrency1·2000ms·faults[]·jobs0으로 복원했다. 재시험 없이 E2 대체 인정·공식 증거 검수를 요청한다.

### SIM-12 — 3000ms 충족, 1000ms 정량 불일치 검토 대기

[선택 증거와 출처](qa-be-sim12-local-20261013/README.md). 원래 회차 3000ms는 60초 완료20건·중앙값2.976초로 3.0±0.1초·약0.33건/초 조건을 충족한다. 실행 중 별도 live-apply 원자료에서 3000ms·1000ms 요청 모두 200, running=true 유지·revision 증가를 확인했다. 최초1000ms 회차는 전체 HTTP 시간 부재로 기대식 비교 미확정이며 서비스 내부0.668초를 HTTP 시간으로 사용하지 않는다.

별도 보완 회차는 HTTP 시작~전체 응답 수신을 inspection_id별로 DB와 연결했다. 60초 완료52건·경계 포함53건, HTTP 왕복 중앙값0.7665초(최대0.9761), 요청 시작 간격1.1097초, 완료 간격1.1110초다. HTTP 왕복을 한 건 처리시간으로 해석할 때 max(1초, 처리시간)=1.000초 대비 약+0.111초 차이로 명목 기대값과 불일치한다. 임의 허용오차를 추가하거나 제품 결함·원인을 확정하지 않는다. jobs 최대1·정지 후0, 53건 HTTP200·제어/저장 성공·시스템 오류0이다. 평균 처리량만으로 대기열을 판정하지 않고 시계열을 연결했다.

1000ms 상태에서 프로세스 재시작 후 기본2000ms/revision0 자동 복원을 확인했으며 수동2000 복원으로 대신하지 않았다. Docker compose restart와 E2 환경 인정은 별도 미검증이다. 준비 import 오류의 중단 기록과 실제 측정1회를 구분했다. 팀에 처리시간 정의(HTTP 밖 이미지 준비·position 저장 포함 여부)와 1000ms 수치 판정 기준을 확인 요청한다. 원래/보완 회차 수치를 합치거나 3000ms 허용오차를 전용하지 않는다. 원인 분석·개선 작업이 확정되면 별도 Issue 분리를 권고하되 이번에는 생성하지 않는다.
