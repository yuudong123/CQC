# BE-06 이미지 생명주기·장애 이미지 순환 보존

- WBS 코드: `BE-06`
- 담당: 홍준희
- 역할: 백엔드·DB
- WBS 예정 기간: 2026-09-28 ~ 2026-10-03
- 완료 확인일: 2026-09-29
- 상태: 완료 (Backend BE-06 범위, 단일 프로세스 기준)

## 1. 목표와 구현 범위

정상 검사 이미지는 처리 후 영구 저장하지 않고, Inference 장애 시 입력 이미지를 별도 파일 저장소에 최대 100장 보존한다. Frontend 관제 계약에 따라 개별 장애 이미지의 목록·preview·선택 삭제를 제공한다. 검사 DB의 `inspections`에 이미지 BLOB·경로·storage key를 추가하지 않았다.

```text
1단계: 이미지 리소스 정리와 별도 저장소
2단계: 장애 저장 trigger·개별 이미지 조회·preview
3단계: 선택/전체 삭제·snapshot 보존 수량과 capability 연계
```

## 2. 정상 이미지와 장애 이미지

`POST /v1/inspections`는 PNG/JPEG 1~12장·전체 24MiB 계약을 유지한다. 처리 중 읽은 이미지 bytes를 Inference 요청과 장애 이미지 저장에 재사용하고, 요청 종료 시 `UploadFile`을 명시적으로 닫는다. 정상 이미지를 영구 파일·DB에 보관하지 않으며, 처리 완료 후 정상 preview는 404/410으로 만료된다. 이미지 응답은 `Cache-Control: no-store`다.

장애 이미지 저장 대상은 Inference **business deadline timeout, 연결 오류, HTTP 오류, 잘못된 응답** 네 가지다. 저신뢰는 유효한 Inference 응답이므로 저장하지 않는다. Control 거부·무응답·실패, DB 저장 실패, bin mapping 오류도 저장 trigger가 아니다. 장애 이미지 저장은 best-effort로, 실패해도 검사 판정·목적 bin·제어 결과·`persistence_status`를 바꾸지 않고 application log에 남긴다.

## 3. 저장 구조와 보존 정책

`FaultImageStorage`가 검사 장애 1건의 이미지 묶음을 임시 디렉터리에 쓴 뒤 게시한다. 각 PNG/JPEG는 개별 UUID 기반 fault image ID와 sidecar metadata를 갖는다. sidecar에는 검사 ID, 입력 `view_index`와 같은 `image_index`, 생성 시각, 장애 원인, media type과 내부 파일 식별 정보만 둔다. 공개 응답에는 파일 경로·storage key·원본 filename을 노출하지 않는다.

한도는 **검사 100건이 아니라 이미지 100장**이다. 101번째 이미지부터 오래된 개별 이미지를 이미지 파일·sidecar와 함께 prune한다. 한 검사에서 일부 이미지만 남을 수 있으며, 마지막 이미지가 사라진 record 디렉터리는 정리한다. orphan image/sidecar도 저장소 조회·정리 경로에서 제거한다. 검사 이력과 오판 의심 기록은 이미지 보존 정책과 독립적이다.

## 4. 관제 API와 ID 의미

| API | Backend 동작 |
|---|---|
| `GET /v1/quality/fault-images` | 이미지 1장당 1항목, 최신순, 최대 현재 보존 이미지. `id`는 fault image ID, `inspectionId`는 원 검사 ID다. |
| `GET /v1/quality/previews/{id}` | 개별 fault image ID로 내부 metadata·파일을 찾아 JPEG/PNG를 반환한다. 없는 ID는 410이며 경로를 URL에서 받지 않는다. |
| `DELETE /v1/quality/fault-images` | `ids`로 전달한 개별 fault image ID만 삭제하고, 성공한 ID만 `deletedIds`로 반환한다. |

세 API의 응답은 `no-store`다. DELETE에서 `ids`는 필수 배열(최대 100개)이며 빈 배열은 아무것도 삭제하지 않는다. 별도의 `all` 플래그나 전체 삭제 endpoint는 없다. **전체 삭제는 확인 창을 연 시점의 목록 ID snapshot을 `ids`로 보내는 선택 삭제**다. 그 뒤 도착한 이미지는 보존된다. 없는·이미 삭제된·prune된 ID는 건너뛰고 중복 ID는 한 번만 처리한다. 잘못된 body는 422 `INVALID_IDS`, 저장소가 설정되지 않았거나 이용 불가하면 503을 반환한다.

삭제는 이미지 파일·sidecar·빈 record 디렉터리를 대상으로 하며 DB 검사 이력은 수정하지 않는다. 일부 파일 작업이 실패하면 로그를 남기고 해당 ID를 `deletedIds`에서 제외한다. 실패한 대상의 orphan은 한 번만 정리 시도하며 무한 재시도하지 않는다. 이후 목록·preview에는 성공적으로 삭제된 이미지가 즉시 사라진다.

`snapshot.state.images`는 기존 검사 결과 단위 `Result[]`이고, fault image 목록 DTO와 다르다. `snapshot.retention.images`는 실제 저장소의 **현재 보존 이미지 수**다. 저장소가 설정된 실제 Backend에서는 `capabilities.deleteImages=true`, 미설정이면 `false`다. Simulator 관련 미구현 필드와 `retention.history`는 임시값으로 채우지 않는다.

## 5. 설정·동시성·배포 인계

Settings는 `FAULT_IMAGE_STORAGE_ROOT`(미설정 기본값 `None`)와 `FAULT_IMAGE_LIMIT`(기본 100)를 사용한다. 루트가 없으면 장애 이미지 API는 503이며, 별도 이미지 DB table은 없다. MLOps는 실제 배포에서 Backend가 쓰고 읽을 수 있는 장애 이미지 디렉터리와 영속 Volume, 권한·재시작 후 보존을 연결해야 한다. 이번 BE-06에서는 Compose/Volume을 수정하지 않았다.

저장·prune·목록·preview·삭제는 같은 `FaultImageStorage` 인스턴스의 lock으로 직렬화한다. 삭제는 lock 안에서 요청 ID에 해당하는 현재 이미지만 포착하므로, 이후 들어온 새 이미지가 전체 삭제에 휘말리지 않는다. 이는 **단일 프로세스** 정책이다. 여러 Backend worker/컨테이너가 같은 Volume을 쓰는 경우의 교차 프로세스 잠금과 파일 장애 복구는 통합 배포에서 별도 확인이 필요하다.

## 6. 검증과 후속 작업

BE-06 테스트는 정상 이미지 비저장·업로드 종료, 네 가지 Inference trigger와 제외 대상, 저장 실패 격리, 개별 목록·JPEG/PNG preview·경로 보호, 100장 prune·orphan 정리, 선택/전체 삭제, 존재하지 않는/중복 ID, 부분 실패, 저장·prune·목록·preview와 삭제의 단일 프로세스 동시성, snapshot 건수·capability와 이력·오판 의심 보존을 포함한다.

완료 확인 시 `ruff check src/api tests/api` 통과, 수정 파일 `ruff format --check` 통과, `pytest tests/api` **164 passed, 3 skipped, 2 warnings**다. skip 3건은 테스트 MySQL URL 미설정 통합 테스트이며, 경고 2건은 TestClient deprecation이다. FE 계약 테스트 24개와 typecheck는 통과했고 lint는 오류 0·기존 경고 5다. 전체 Ruff format 검사는 이번 범위 밖의 `src/api/clients/inference.py`, `tests/api/test_http_inference_client.py` 두 파일이 기존부터 미정렬인 상태다.

Frontend 담당자는 reference server와 실제 UI 삭제 흐름을 새 `/fault-images`의 개별 이미지 ID로 맞춰야 한다. 현재 reference server는 예전 검사 결과 `Result[]`/검사 ID 기반 삭제를 시연하고 `retention.images=100`을 한도처럼 반환하므로 Backend의 현재 장수 의미와 다르다. `snapshot.state.images`는 변경하지 않는다. BE-07은 Simulator 시작·정지·위치 복구·500ms 입력과 장애 시연 설정을 담당하며 이번 단계에서 구현하지 않았다. BE-08 이후 실제 사진·Frontend·Compose 연결, 다중 worker/Volume 동작, 실제 MySQL 통합 시험이 남아 있다.

발표용 요약: **정상 이미지는 남기지 않고, Inference 장애 이미지만 개별 ID로 최대 100장 보존한다. 목록·미리보기·확인 시점의 선택/전체 삭제가 가능하며 검사 이력은 삭제하지 않는다.**
