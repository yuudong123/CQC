# BE-02 MySQL 물리 스키마·Alembic migration

- WBS 코드: `BE-02`
- 담당: 홍준희
- 역할: 백엔드·DB
- 작업 기간: 2026-09-22
- 상태: 완료

## 1. 작업 목적

CQC Backend에서 검사 결과와 제어·오류·bin 매핑을 MySQL에 일관되게 저장할 수 있도록 물리 스키마를 설계하고, SQLAlchemy ORM과 Alembic 초기 migration으로 구현했다.

이번 작업은 다음 세 단계로 진행했다.

```text
1단계: 요구사항 기반 DB 스키마 계약 검토
2단계: SQLAlchemy ORM 모델·동기 DB 연결 골격
3단계: Alembic 초기 migration·로컬 MySQL 왕복 검증
```

Repository와 실제 검사 저장 로직은 연결하지 않고, 물리 스키마와 migration의 재현 가능성을 검증하는 범위로 제한했다.

## 2. Backend DB 구조

DB 관련 코드는 AI 모델 경로와 분리하여 `src/api/db/` 아래에 구성했다.

```text
src/api/db/
├─ __init__.py
├─ base.py
├─ session.py
├─ models/
│  ├─ __init__.py
│  ├─ inspection.py
│  ├─ control_attempt.py
│  ├─ inspection_error.py
│  └─ bin_mapping.py
└─ migrations/
   ├─ README.md
   ├─ env.py
   ├─ script.py.mako
   └─ versions/
      └─ 20260922_01_initial_backend_schema.py
```

- `base.py`: SQLAlchemy 2.0 Declarative Base와 constraint naming convention
- `session.py`: Settings 기반 sync Engine과 Session factory
- `models/`: 4개 업무 테이블의 ORM 모델
- `migrations/`: Alembic 실행 환경과 revision 이력
- 루트 `alembic.ini`: migration 경로와 로그 설정

루트 `models/`와 `src/models/`는 AI 모델 영역이므로 DB ORM 파일을 넣거나 수정하지 않았다.

## 3. DB 연결과 설정

MySQL 연결은 다음 형식의 `DATABASE_URL`을 사용한다.

```text
mysql+pymysql://<user>:<password>@<host>:<port>/<database>
```

`DATABASE_URL`은 `pydantic-settings`의 `Settings`로 주입하며 코드에 실제 계정이나 비밀번호를 하드코딩하지 않는다.

DB 연결 구조:

- SQLAlchemy 2.0
- PyMySQL
- sync Engine
- sync Session factory
- `pool_pre_ping=True`
- 요청이나 논리 DB 작업마다 별도 Session 생성 예정

앱 import 또는 실행 시 DB 연결과 테이블 생성을 자동 수행하지 않는다. `Base.metadata.create_all()`은 사용하지 않으며 schema 생성·변경은 Alembic으로만 관리한다.

## 4. 구현한 테이블

### 4.1 `inspections`

검사 한 건의 판정 결과, 적용 정책, 처리 상태, 관리자 검수와 late-result 진단 정보를 저장한다.

주요 컬럼:

- `inspection_id`: 전체 흐름의 공통 검사 식별자이자 PK
- `source_reference`: 입력 원본 추적 후보, 현재 nullable
- `created_at`, `completed_at`, `updated_at`
- 품종·품질 예측과 confidence
- 실제 적용한 품종·품질 threshold
- 모델명·모델 버전·전처리 버전
- 실제 사용 이미지 수와 추론 시간
- `inspection_status`, `control_status`, `persistence_status`, `error_code`
- 재검사·통계 제외 판단에 필요한 상태
- 관리자 검수와 오판 의심 정보
- 시간 초과 후 도착한 late-result 진단 정보

Inference timeout이나 오류 시 정상 예측값이 없을 수 있으므로 예측·confidence·모델 응답 관련 컬럼은 nullable로 구성했다. 상태 Enum 문자열은 아직 미정이므로 DB native ENUM 대신 `VARCHAR`를 사용했다.

### 4.2 `control_attempts`

Virtual Control의 정상 bin 명령과 필요 시 한 번 수행하는 재검사 bin 대체 명령을 개별 시도로 기록한다.

주요 규칙:

- `inspection_id → inspections.inspection_id`
- 검사 1건에 제어 시도 1:N
- `command_id` unique
- `(inspection_id, attempt_no)` unique
- 검사 삭제 시 `ON DELETE CASCADE`

### 4.3 `inspection_errors`

한 검사에서 발생할 수 있는 복수 오류와 진단 정보를 기록한다.

주요 컬럼:

- 오류 발생 component
- error code
- 사용자·관리자 확인용 message
- 구조 변경 가능성이 있는 `diagnostic_data` JSON
- 오류 발생 시각

stack trace, 비밀번호와 민감한 경로를 저장하는 용도로 사용하지 않는다.

### 4.4 `bin_mappings`

품목·품종·품질 조합과 현재 목적 bin의 매핑을 관리한다.

주요 규칙:

- `mapping_key` unique
- `bin_code` unique
- `(crop_type, cultivar, quality_grade)` unique
- 정상 매핑과 재검사 매핑 구분
- 활성 상태 조회 지원

실제 `mapping_key`, `bin_code`와 재검사 매핑 단일성 제약은 최종 계약 전이므로 seed와 추가 제약조건을 넣지 않았다.

## 5. 관계와 삭제 정책

테이블 관계는 다음과 같다.

```text
inspections
├─ 1:N control_attempts
└─ 1:N inspection_errors

bin_mappings
└─ 독립적인 현재 매핑
```

`control_attempts`와 `inspection_errors`는 부모 검사가 순환 보존 정책으로 삭제될 때 함께 제거되도록 FK에 `ON DELETE CASCADE`를 적용했다.

`inspections.target_bin_code`는 검사 당시 실제 결정값의 snapshot이다. 이후 bin mapping이 변경되어도 과거 검사 결과가 달라지지 않도록 `bin_mappings`와 FK로 직접 연결하지 않았다.

## 6. PK·FK·unique·index

초기 schema에 적용한 핵심 제약조건은 다음과 같다.

- 업무 테이블 PK: 4개
- FK: 2개
- unique constraint: 5개
- 명시적 복합 index: 14개

`inspections`는 다음 조회 조건과 생성 시각을 결합한 index를 둔다.

- 품종·품질
- 목적 bin
- 검사 상태
- 제어 상태
- 오류 코드
- 검수·오판 의심
- 모델 버전
- 최신순 조회

`control_attempts`는 검사별 요청 이력과 제어 상태 조회, `inspection_errors`는 검사·오류 코드·component별 발생 시각 조회, `bin_mappings`는 활성·재검사 매핑 조회에 필요한 index를 둔다.

MySQL은 명명된 PK constraint도 `information_schema`에서 이름을 `PRIMARY`로 보고한다. 실제 검증에서는 각 업무 테이블에 `PRIMARY`가 존재하는 방식으로 확인했고, FK·unique·index 이름은 migration 정의와 일치하는지 확인했다.

## 7. 시간 처리

MySQL 시간 컬럼은 모두 밀리초 정밀도의 `DATETIME(3)`을 사용한다.

UTC/KST 최종 저장 정책은 아직 팀 합의 전이므로 다음 원칙을 적용했다.

- migration에 특정 timezone을 하드코딩하지 않음
- `NOW()`와 `CURRENT_TIMESTAMP` 같은 timezone 종속 DB 기본값을 사용하지 않음
- 애플리케이션이 처리 시각을 명시적으로 전달하는 구조
- Python에서는 timezone-aware `datetime`을 사용할 수 있음
- DB 저장·API 표시 변환 정책은 후속 계약에서 확정

## 8. JSON 사용 범위

JSON은 필터·통계 기준 데이터가 아니라 구조가 바뀔 수 있는 진단 정보에만 사용한다.

- `inspections.late_result_payload`
- `inspection_errors.diagnostic_data`

품종, 품질, confidence, 상태, bin, 모델 버전처럼 조회와 집계에 사용되는 값은 일반 컬럼으로 분리했다.

## 9. Alembic 구성

Alembic은 `src/api/db/migrations/env.py`에서 다음과 같이 ORM과 연결된다.

- `target_metadata = Base.metadata`
- `src.api.db.models` import로 4개 모델 등록
- 기존 Backend `Settings`의 `DATABASE_URL` 사용
- 기존 `create_db_engine()`으로 온라인 migration 수행
- `compare_type=True`로 타입 차이 검출

Initial revision:

```text
Revision ID: 20260922_01
Revises: base
```

upgrade 순서:

```text
bin_mappings
→ inspections
→ control_attempts
→ inspection_errors
```

downgrade는 FK 자식부터 안전한 역순으로 제거한다.

```text
inspection_errors
→ control_attempts
→ inspections
→ bin_mappings
```

## 10. 실제 MySQL 검증

Docker나 기존 프로젝트 컨테이너를 사용하지 않고 현재 PC의 로컬 MySQL Server에서 검증했다.

검증 환경:

- Windows 서비스: `MySQL84`
- MySQL 버전: `8.4.11`
- 포트: `3306`
- 전용 검증 DB: `cqc_test`

기존 `cqc` DB는 생성되어 있지 않았으며 다른 DB에는 schema 변경을 적용하지 않았다. 빈 `cqc_test`를 새로 생성한 뒤 다음 흐름을 수행했다.

```text
alembic upgrade head
→ information_schema로 schema 확인
→ alembic downgrade base
→ 업무 테이블 제거 확인
→ alembic upgrade head
→ alembic check
```

결과:

```text
upgrade: 성공
downgrade base: 성공
re-upgrade: 성공
alembic check: No new upgrade operations detected.
```

최종 `cqc_test`는 `20260922_01` head 상태로 유지했다.

## 12. 이미지 저장 구조 제외

팀 합의에 따라 정상 이미지와 장애 이미지를 DB 또는 파일 시스템에 저장하는 구조를 BE-02에서 만들지 않았다.

ORM과 migration에 다음 항목이 없음을 테스트와 실제 MySQL schema에서 확인했다.

- `failure_images`
- `storage_key`
- 이미지 파일 경로
- BLOB·LONGBLOB
- 이미지 보존·순환 삭제 테이블

오류·장애 진단 정보는 `inspection_errors`와 application log를 기준으로 관리한다.

## 16. 아직 미정인 DB 계약

BE-02에서는 다음 항목을 의도적으로 확정하지 않았다.

- UTC/KST 최종 저장·표시 정책
- `source_reference`의 API 포함 여부와 필수 여부
- `inspection_status`, `control_status`, `persistence_status` 최종 문자열
- 상태 전이와 최종 error code
- Virtual Control command type
- 실제 `mapping_key`와 `bin_code`
- 재검사 매핑 단일성 제약 방식
- late-result JSON 최종 상세 구조
- bin mapping seed 입력 방식
- 실제 개발·운영용 MySQL 일반 계정과 최소 권한

현재 로컬 검증 계정은 `root@localhost`다. 실제 Backend 실행과 운영에서는 CQC 전용 일반 계정과 필요한 DB 범위의 최소 권한을 사용해야 한다.

## 17. 의도적으로 구현하지 않은 항목

BE-02에서는 다음 기능을 구현하지 않았다.

- Repository와 Generic Repository
- Service DB 저장 로직
- 실제 검사 INSERT·UPDATE
- 업무용 bin mapping seed
- 통계·CSV Query
- 검사 이력 순환 삭제
- 실제 Inference 연동
- Virtual Control
- 상태 전이 비즈니스 로직
- late-result 비즈니스 로직
- DB 장애 복구
- 이미지 저장
- 불필요한 Interface·Factory·Base class
