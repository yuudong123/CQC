# BE-07 Simulator 구현 진행 기록

- 현재 범위: 2/3 제어 API와 단일 프로세스 상태 관리까지 구현
- 전체 BE-07 완료: 미확인

## 1/3 상태 기반

`SimulatorStateService`는 앱 인스턴스마다 하나씩 생성한다. 초기값은 `revision=0`, `running=false`, `concurrency=1`, `faults=[]`, `scope=ALL`이다. 불변 snapshot과 `threading.Lock`으로 단일 프로세스의 상태 변경을 보호한다. 프로세스 재시작 시 초기화된다.

## 2/3 제어 계약

`PUT /v1/quality/simulator`는 공유 Settings 계약의 부분 변경 요청을 받는다. `expectedRevision`이 현재 값과 같을 때만 변경하고 revision을 1 올린다. 다르면 상태를 유지하고 `409 {"code":"REVISION_CONFLICT"}`를 반환한다. 잘못된 입력은 `422 {"code":"INVALID_SETTINGS"}`다. 응답은 변경된 상태가 반영된 전체 snapshot이며 캐시를 금지한다.

2026-09-30 FE 합의에 따라 concurrency는 1·2·4만 허용한다. 장애 종류는 공유 OpenAPI의 6개 코드, 적용 범위는 `ALL`·`NEXT`만 허용한다. FE 참조 서버와 같이 장애 목록과 적용 범위의 추가 조합 제한은 없다.

`GET /v1/quality/snapshot`은 같은 상태 서비스의 revision·running·concurrency·faults·scope를 읽는다. `capabilities.control`과 `capabilities.faults`는 제어 설정 API의 사용 가능 여부를 나타낸다. `sequence`·`tick`·position은 생성하지 않는다. Simulator 구성 요소는 실제 실행 루프가 없으므로 `stopped`로 표시한다. `running=true`는 현재 단계에서 제어 설정일 뿐 실제 입력 실행을 의미하지 않는다.

내부 `claim_faults_for_inspection()`은 새 Simulator 검사 1건이 장애 설정을 가져갈 때 사용하도록 준비했다. `NEXT`에서는 첫 claim만 장애 목록을 받고 설정의 목록을 비우며 revision을 1 올린다. FE 참조 동작에 따라 scope는 `NEXT`로 유지한다. `ALL`은 목록을 유지한다. 소비와 제어 변경은 같은 lock을 사용한다. 일반 `POST /v1/inspections`에는 장애 설정을 연결하지 않았다.

## 3/3 인계 및 한계

- 실제 500ms 재생 루프, 데이터 묶음 순회, 검사 API 자동 호출과 장애 주입 연결
- sequence·tick·position 저장 및 재시작 복구
- 목표 CPU의 병렬 수 검증과 실제 시작·정지 task 연결
- 상태는 프로세스 메모리에만 있으므로 여러 Uvicorn worker 사이의 revision·NEXT 일관성은 보장하지 않는다. 단일 worker 운영이 필요하다.
- 제어 응답은 현재 DB 기반 snapshot을 사용하므로 DB 조회 장애 시 PUT은 503을 반환하고 상태 변경은 적용하지 않는다. DB 장애 중 제어 지속은 후속 장애 정책과 함께 검토한다.

BE-07 3/3의 실제 실행 결과를 확인하기 전에는 Simulator 전체 완료로 표시하지 않는다.
