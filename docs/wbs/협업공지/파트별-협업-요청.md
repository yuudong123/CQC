# 파트별 협업 요청

> 2026-10-01 dev 기준(PR #30~#33 BE-07 Simulator·MO 배포·입력 간격 반영). 아래 최신 작업표를 우선 적용하며, 이후 절은 데이터·모델 담당 관점의 교류 항목이다.

## 최신 작업 순서와 담당 경계

| 담당 | 이미 있는 구현 | 다음 산출물 |
|---|---|---|
| 홍준희 / Backend | 검사 API, 실제 Inference HTTP client, 12-bin seed, 저장·이력·통계·CSV·관제 조회, 장애 이미지 API, `PUT /simulator`, 검수 API | 아래 09-30·10-01 요청(DB 중단 시 선별 지속, 실패 후 Simulator 계속 전송 등), 지연 결과 DB 저장, 이력 보존 삭제 |
| Backend / Simulator | 독립 Simulator(자동 재생, 정지/재개, 위치 복구, 동시 처리 1·2·4, 장애 6종·다음 1건), 학원 서버 배포 | 검사 1건 실패 시 전체 정지 개선 |
| 강성민 / FE | PR #18·#21 병합: 관제·관리 화면, HTTP client·proxy, OpenAPI·참조 서버, 12장 그룹 관제·자동 경매 시연 | 실제 Backend 조회 API 응답·통계·CSV 대조, 장시간 브라우저 검증 |
| 조현재 / DM | 추론 코드·모델 패키지, 시연 묶음, 14°Brix 구간, v2 보정·임계값 0.50/0.60, 서버컴 지연·처리량 측정, 입력 간격 2000ms | 간격 조정 후 처리량·시간 초과 재측정, DM-09 모델 카드 마무리 |
| 홍유나 / MLOps | Backend·Inference·Simulator 실제 Compose, 데이터·위치 볼륨, 재생 여부 health·Jenkins 검증 | FE Dockerfile을 루트 배포에 연결(API 모드), 실패 시 이전 버전 유지(MO-07) |

1. Simulator 구현과 남은 관제 제어 API를 먼저 진행한다(저장·조회 API는 BE-05로 완료). FE 컨테이너 배포 연결은 병행할 수 있다.
2. [FE 관제 API 인계](Frontend-관제-API-계약-인계.md)의 요청·응답을 Backend adapter로 제공한다. 기존 검사 입력 API는 유지한다.
3. DM은 동일 버전·체크섬의 모델 및 사진 묶음을 전달하고, MLOps는 실제 연결·저장·복구 환경을 구성한다.
4. FE는 실제 응답을 대조한다. 공동으로 정상100개·5종 장애·CSV·보존·복구·장시간 시험을 통과한 뒤 동결한다.

참조 서버 성공, DB health 성공, 합성 입력 CPU 측정만으로 전체 통합 완료를 판정하지 않는다. 이 문서는 협업 요청 정리이며 실제 메시지 발송 기록이 아니다.

## 2026-09-30 실제 연결 시험에서 나온 Backend 요청 (홍준희)

집 PC Compose(MySQL·Inference·Backend `feat/data` `3509329`)에 시연 묶음을 500ms 간격으로 보내고 웹을 연결해 확인했다. 상세는 [FE-05](../FE-05.md)·[FE-08](../FE-08.md).

| # | 현상 | 재현 | 요청 |
|---|---|---|---|
| 1 | DB 중단 시 선별도 멈춤 | MySQL 정지 중 `POST /v1/inspections`가 7~8초 뒤 HTTP 500 `활성 bin mapping 설정을 확인할 수 없습니다` | 마지막으로 읽은 bin 매핑을 메모리에 두고 DB 없이도 판정·제어를 계속, 저장만 유실 처리 (BE-09 조건 "DB 유실 허용·선별 지속") |
| 2 | 현재 처리량이 항상 낮게 표시 | 초당 2건 입력인데 snapshot `throughput`이 1.0 | `points[-1]`이 진행 중인 현재 1초 구간이다. 직전 완료 구간(`points[-2]`) 또는 최근 N초 평균 사용 |
| 3 | 연결 오류가 시간 초과로 기록 | Inference 컨테이너 정지 시 `errorCode`가 `INFERENCE_TIMEOUT` | 연결 거부는 `INFERENCE_ERROR` 등 별도 코드로 구분(장애 원인 표시·통계용) |
| 4 | Inference 상태 미표시 | snapshot `components.Inference`가 항상 `unknown`("상태 확인 연동 전") | Backend가 Inference `/health`를 확인해 상태·마지막 확인 시각 제공 |

MLOps(홍유나): 시험 중 확인한 `alembic upgrade head`·`FAULT_IMAGE_STORAGE_ROOT` 누락은 PR #25(`1c85fbc`)로 dev에 반영됐다. 집 PC override와 같은 구성이다.
## 강성민 — 프론트엔드

### 내가 전달할 것

- 화면에 표시할 품종·품질 코드와 confidence 예시
- 모델 버전, 추론시간, 승인 여부 등 관리자 화면에 필요한 모델 정보
- 저신뢰·오분류 사례의 화면 확인용 샘플 결과

### 내가 받을 것

- 이미 구현된 관제에 Backend를 거친 실제 모델 응답을 연결한 캡처 또는 실행 화면
- 품종·품질 confidence가 각각 표시되는지 확인 결과
- 프론트에서 추가로 필요한 모델 응답 필드 목록

### 교류 완료 기준

- 샘플 응답 한 건으로 정상·저신뢰 화면을 확인하고, 모델 출력 필드의 추가·변경 필요 여부를 서로 확정한다.

## 홍준희 — 백엔드·DB

### 내가 전달할 것

- 실행 가능한 inference API와 OpenAPI 파일
- 모델 입력 장수·형식·용량 제한
- 모델 출력 필드, 신뢰도 기준, 모델 버전
- 연동 검증용 모델 패키지와 체크섬

### 내가 받을 것

- Backend가 inference에 보내는 실제 요청 예시
- Backend가 저장·전달하는 모델 응답 필드 목록
- timeout, 입력 오류, inference 오류 처리 결과
- 실제 연동 중 발견된 요청·응답 계약 불일치 사항

### 교류 완료 기준

- Backend에서 실제 이미지 그룹을 inference로 보내고 응답을 받아 DB·프론트 전달 직전 형태까지 확인한다.
- 계약 불일치가 있으면 어느 쪽을 수정할지 합의하고 OpenAPI에 반영한다.

## 홍유나 — MLOps·CI/CD

### 내가 전달할 것

- 모델 파일·manifest·SHA-256과 모델 버전
- inference 실행 명령, 의존성, healthcheck 경로
- CPU 성능시험 명령과 측정할 지표
- 현재 모델이 연동 검증용이며 품질 승인 모델은 아니라는 상태

### 내가 받을 것

- 배포 환경의 모델 마운트 경로와 실제 로딩 확인 결과
- 서버컴에서 측정한 평균·최대·p95, 처리량 결과
- healthcheck와 체크섬 검증 결과
- 배포 실패 로그 또는 실행환경 차이

### 교류 완료 기준

- 같은 모델 버전과 체크섬이 배포 환경에서 로딩된다.
- 목표 CPU의 성능시험 결과를 받아 모델 카드와 최종 선정 근거에 반영한다.

## 팀 전체

### 내가 요청할 것

- 개선 모델을 검증할 신규 독립 holdout 데이터 확보 여부와 방법 결정
- 모델 품질 기준 미달 상태에서 기능 통합을 계속 진행할지 확인
- 물류 플랫폼을 최종 발표 범위에 포함할지 결정

### 내가 공유할 것

- v2 학습 결과
- v2 기준 미달 시 `data/sampling` 후속 실험 결과
- 새 모델의 승인 여부, 버전, 체크섬, 성능과 한계

## 실제 연락 순서

1. 홍준희에게 inference 연동 요청 및 실제 요청·응답 확인
2. 홍유나에게 동일 모델 패키지 배포와 서버컴 수용시험 요청
3. 강성민에게 Backend를 거친 실제 응답으로 화면 표시 확인 요청
4. 세 결과를 모아 팀 전체에 모델 상태와 통합 가능 여부 공유
