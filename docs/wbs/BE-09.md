# BE-09 DB 장애·순환 삭제·동적 bin 검증

- WBS 코드: `BE-09`
- 담당: 홍준희
- 역할: 백엔드·MySQL 검사 이력·bin mapping·Virtual Control
- WBS 예정 기간: 2026-10-07 ~ 2026-10-11
- 완료 확인일: 2026-10-01
- 상태: **완료 (Backend BE-09 범위)**

## 1. 목표와 완료 경계

선행 작업은 BE-05와 BE-08이다. MySQL이 일시적으로 사용할 수 없어도 마지막 정상 bin mapping으로 검사 판정과 Virtual Control을 계속하고, 저장 실패는 판정과 별도로 표시한다. 검사 이력은 86,400건에 도달할 때마다 오래된 8,640건을 삭제하며, DB 복구 뒤에는 Backend 재시작 없이 최신 mapping과 저장을 다시 사용한다. 세 단계의 구현과 격리 MySQL·실제 Inference·Simulator 기술 검증을 완료했다.

```text
1/3: 완전한 bin mapping snapshot과 Last Known Good(LKG) fallback
2/3: 실제 MySQL 장애·복구, 중복 연결 대기 제거와 1초 연결 timeout
3/3: 86,400/8,640 순환 삭제, 격리 Compose 장애 시험과 전체 회귀
```

## 2. 1/3 — LKG 기반 DB 장애 선별 지속

활성 정상 bin 12개와 재검사 bin 1개를 하나의 snapshot으로 읽고 완전성을 검증한다. 성공한 완전한 snapshot만 LKG로 교체하며 한 inspection의 bin 결정에는 동일 snapshot을 사용한다. DB unavailable이면 LKG를 사용하지만, DB가 응답한 mapping configuration error에는 fallback하지 않고 Virtual Control도 실행하지 않는다. 최초 LKG를 확보하기 전 DB가 unavailable인 경우 임의 bin을 만들지 않고 기존 HTTP 500 흐름을 유지한다.

DB 저장 실패는 이미 결정된 bin과 제어 결과를 바꾸지 않는다. DB 복구 후 다음 정상 조회에서 LKG를 교체하므로 Backend 재시작 없이 변경 mapping을 적용한다. 당시 Backend·Simulator 회귀는 **239 passed, 4 skipped**였고 Ruff check·format check·`git diff --check`가 통과했다. 정상·저신뢰 fallback, configuration error, DB_ERROR와 late result 회귀를 확인했다.

## 3. 2/3 — 실제 MySQL 장애·복구와 연결 지연 보정

격리된 `cqc_be09` MySQL과 별도 Backend에서 실제 DB 중단·복구를 시험했다. LKG 확보 후 정상 판정과 품질 confidence **0.5521**의 저신뢰 재검사가 DB 장애 중에도 HTTP 200, Virtual Control `SUCCEEDED`, persistence `FAILED`로 처리됐다. 복구 뒤 Backend 재시작 없이 저장과 변경 mapping 적용이 재개됐다. 잘못된 mapping은 HTTP 500·제어 0회였고, 최초 LKG 부재 상태의 DB unavailable도 HTTP 500을 유지했다.

초기에는 DB 장애 검사 한 건이 **4.74~5.02초** 걸렸다. 초기 persistence와 mapping 조회가 같은 inspection에서 각각 중단된 DB 연결을 기다린 것이 원인이었다. 초기 저장에서 DB unavailable을 확인하면 해당 inspection의 mapping DB 조회를 생략하고 LKG를 사용한다. Mapping 조회에서 DB unavailable을 확인하면 해당 inspection의 최종 저장 재시도를 생략한다. 초기 행이 없는 late result의 저장도 시도하지 않는다. 이 상태에서 처리시간은 **2.64~2.77초**였다. 다음 inspection에서는 DB 접속을 다시 시도하므로 복구를 감지한다.

실제 Dataset·Inference HTTP와 Simulator `intervalMs=2000` 연속 재생에서 연결 timeout 후보를 비교했다.

| 조건 | 검사 건수 | 평균 처리시간 | 최소~최대 | 평균 요청 시작 간격 |
|---|---:|---:|---:|---:|
| DB 정상, timeout 미지정 | 12 | 0.596초 | 0.462~0.736초 | 2.017초 |
| DB 정상, 1초 후보 | 13 | 0.591초 | 0.465~0.727초 | 2.019초 |
| DB 중단, timeout 미지정 | 21 | 2.627초 | 2.538~2.709초 | 2.832초 |
| DB 중단, 1초 후보 | 25 | 1.580초 | 1.433~1.720초 | 2.007초 |
| 설정 반영 후 DB 중단 | 19 | 1.576초 | 1.492~1.636초 | 2.011초 |

1초 후보에서는 DB 장애 중 LKG 판정·Virtual Control이 지속되고 backlog가 누적되지 않았다. 정상 DB 처리시간의 유의미한 악화나 복구 감지 회귀도 없었다. 따라서 Settings 기본값 `DB_CONNECT_TIMEOUT_SECONDS=1`을 채택하고 SQLAlchemy/PyMySQL `connect_args`로 전달했다. `.env.example`과 테스트를 갱신했으며 실제 `.env`, Compose, 비밀값은 변경하지 않았다. 이 단계의 Backend·Simulator 회귀는 **270 passed**였고 Ruff·format·diff 검사가 통과했다.

## 4. 3/3 — 검사 이력 순환 삭제

`inspections` 행은 정상·오류·재검사를 구분하지 않고 보존한다. 행 수가 **86,400건에 도달하면** `(created_at, inspection_id)` 오름차순으로 가장 오래된 **8,640건**을 삭제한다. 동일한 생성 시각은 검사 ID로 안정적으로 정렬하며 삭제 후 77,760건부터 다시 누적한다. `INSPECTION_HISTORY_LIMIT`과 `INSPECTION_HISTORY_DELETE_BATCH`는 Settings에서 기본값과 관계를 검증한다.

최초 INSERT와 삭제 경계에서만 실제 DB 건수를 조회하고, 그 사이에는 단일 Backend 프로세스의 성공한 INSERT 수를 유지한다. 경계에서 다시 DB 건수를 확인한 뒤 검사 INSERT와 오래된 행 삭제를 하나의 트랜잭션에서 처리한다. 매 요청마다 전체 건수를 세거나 대량 삭제하지 않는다. 기존 `(created_at, inspection_id)` 인덱스와 MySQL FK `ON DELETE CASCADE`를 사용하므로 migration은 추가하지 않았다. 연결된 `control_attempts`와 `inspection_errors`가 함께 삭제되고, 검사 행의 late result 진단 필드도 함께 사라진다. BE-06 장애 이미지 파일은 별도 저장소·보존 정책에 따른다.

격리 MySQL의 축소 경계 시험에서 상한 미만에는 삭제가 없었고, 상한 도달 시 정확한 삭제량, 동일 시각의 ID 순서, 반복 cleanup, 연관 행 무결성을 확인했다. 삭제 뒤 history·statistics·검사 CSV·통계 CSV가 실제 잔존 행 3건과 일치했다. 운영값 시험에서는 86,399건에 한 건을 추가해 **8,640건 삭제·77,760건 잔존**과 최신 행 유지를 확인했다. 해당 INSERT와 삭제는 **0.654초**였다. 일반 실제 모델 검사 14건의 평균 처리시간은 **0.560초**, 평균 시작 간격은 **2.001초**였다.

## 5. GitHub Issues와 격리 Compose 검증

### #45 — MySQL 중단·복구 LKG 선별 지속

열린 [Issue #45](https://github.com/yuudong123/CQC/issues/45)의 Compose `mysql` 중단 조건을 공유 dev·시연 DB와 분리된 Compose 프로젝트에서 검증했다. Docker 시각 기준 중단 시간은 **58.29초**였다. 실제 Dataset·Inference HTTP로 재생 중인 Simulator는 장애 구간에도 실행 상태를 유지했다.

- 장애 구간 **27건 모두** HTTP 200, Virtual Control `SUCCEEDED`, persistence `FAILED`. 정상 판정 22건과 자연 발생한 품질 저신뢰 재검사 3건을 확인했다. 평균 처리시간은 **1.570초**, 평균 시작 간격은 **2.001초**였다.
- MySQL 재기동 뒤 Backend를 재시작하지 않고 저장 15건이 재개됐다. 이후 DB mapping 변경이 응답 2건에 반영됐고 추가 23건의 저장·제어가 성공했다.
- DB 장애 중 snapshot·history·statistics·검사 CSV·통계 CSV는 모두 503 `DB_UNAVAILABLE`, 복구 후 모두 200이었다. 장애 구간의 저장 실패 이력은 재적재하지 않았다.

이 절에 기술 결과를 기록해 #45의 문서 기록 조건까지 충족했다. **GitHub Issue 자체는 닫지 않았으며** close 여부는 요청자가 결정한다.

### #46 — 옛 6-bin 주석

열린 [Issue #46](https://github.com/yuudong123/CQC/issues/46)이 지적한 `src/api/services/bin_policy.py`의 과거 6-bin 설명을 현재 12-bin 기본 mapping 설명으로 고쳤다. 기능 로직과 bin 정책은 변경하지 않았다. 주석의 완료 조건을 충족했으며 Issue 자체는 닫지 않았다.

## 6. 주요 변경 위치와 최종 검증

LKG와 장애 정책은 `src/api/services/bin_mapping_lkg.py`, `src/api/services/inspections.py`, `src/api/repositories/bin_mappings.py`에 있다. 연결 timeout과 순환 삭제는 `src/api/core/config.py`, `src/api/db/session.py`, `src/api/repositories/inspections.py`, `src/api/repositories/persistence.py`, `src/api/main.py`, `.env.example`에 반영했다. #46의 주석은 `src/api/services/bin_policy.py`에 있다. 이 보고서를 작성하면서 기능 코드·설정·테스트는 변경하지 않았다.

LKG·DB 장애·복구·저신뢰·500ms deadline·late result·DB_ERROR·confidence 0.60·Simulator intervalMs와 history·statistics·CSV를 포함한 최종 Backend·Simulator 회귀는 격리 MySQL 통합 시험과 함께 **272 passed**였다. Ruff check, Ruff format check, `git diff --check`가 통과했다. 순환 삭제 통합 시험은 `tests/api/test_history_retention_mysql_integration.py`에 있다.

## 7. 완료 상태와 후속 범위

**BE-09 1/3, 2/3, 3/3과 WBS의 DB 유실 허용·선별 지속, 86,400/8,640 순환 삭제, 무재시작 mapping 적용을 완료했다. BE-09 전체 상태는 완료다.** 이 범위에서 Backend 추가 구현은 확인되지 않았다.

현재 순환 삭제 건수 유지 방식은 **단일 Backend 프로세스**에서 구현·검증했다. 여러 Backend 프로세스가 같은 `inspections` 테이블에 동시에 쓰는 구성의 건수 공유와 보존 상한은 이번 범위 밖이다. 전체 배포 환경의 수용시험도 별도 단계다. 멘토링 기반 불량률·통계 확장, 정상 데이터 저장 정책 변경, 고객 연결·배차, BE-10·BE-11과 무관한 FE·MLOps 작업은 BE-09에 포함하지 않는다.
