# BE-08 실제 Inference·DB·프론트 통합

- WBS 코드: `BE-08`
- 담당: 홍준희
- 역할: 백엔드·Inference HTTP 연동·Simulator 애플리케이션 통합 검증
- WBS 예정 기간: 2026-10-05 ~ 2026-10-08
- Backend 범위 완료 확인일: 2026-10-01
- 상태: **Backend 통합 완료 / MLOps·FE 최종 통합 검증 필요**

## 1. 목표와 완료 경계

WBS의 선행 작업은 DM-07, BE-05, FE-05이며 완료 기준은 전체 HTTP 흐름과 지연 결과의 진단 저장이다. 실제 모델·Dataset·MySQL을 사용한 Backend 담당 구현과 수직 통합 검증은 완료했다. 다만 프로젝트 전체 BE-08 완료는 실제 Frontend의 Compose 배포와 브라우저 화면 E2E 검증 후 확정한다. 이 문서의 Backend 완료를 전체 배포 완료로 해석하지 않는다.

```text
1/4: Inference HTTP 계약·모델 기준선과 confidence 정책 확인
2/4: deadline 이후 Inference 결과의 DB 진단 저장
3/4: 실제 모델·12-view Dataset·MySQL 수직 통합 및 재현 환경 검증
4/4: 최신 dev 병합 HEAD의 Compose 서비스·조회 API·FE 연결 검증
```

## 2. 1/4 — 계약과 판정 기준선

Backend↔Inference의 multipart 요청, 응답 schema, 모델 package·버전과 기존 판정 정책을 확인했다. v2 보정 모델에 맞춰 `QUALITY_CONFIDENCE_THRESHOLD=0.60`을 Settings·문서·테스트에 반영했다. 품질 confidence **0.59는 저신뢰 재검사, 0.60과 0.61은 정상 bin 후보**다. 품종 confidence 기준 `0.50`은 유지했고, public OpenAPI에 threshold 필드를 새로 노출하지 않았다.

## 3. 2/4 — Late Result DB 진단 저장

Inference business deadline 500ms를 넘으면 그 시점의 재검사 판정·bin·Virtual Control을 확정한다. 이후 도착한 결과는 원래 `inspection_id`의 기존 `late_result_received_at`과 `late_result_payload`에 진단용으로만 기록한다. 새 inspection을 생성하거나 정상 품종·품질 통계와 최종 판정을 바꾸지 않는다.

Background 저장은 request-scoped DB session을 재사용하지 않고 새 session을 사용한다. 저장에 실패해도 확정된 응답과 제어 결과를 바꾸지 않는다. 테스트에서 late result의 confidence 0.59·0.60·0.80 모두 timeout 당시의 최종 판정·bin·control이 유지됨을 확인했고, 별도 MySQL 실DB 시험에서 진단 필드 저장과 판정 불변을 확인했다.

## 4. 3/4 전 통합시험 피드백 보정

실제 통합 전 Simulator가 유효한 Dataset이 있으면 자동 시작하고 최초 revision 0을 유지하도록 했다. Backend 단건 전송이 실패해도 runner가 다음 검사를 계속하며, `lastSeenAt`은 성공한 Backend 전송에만 갱신한다. throughput은 완료된 1초 bucket을 사용한다. Backend는 Inference 연결 오류와 deadline 초과를 내부적으로 구분하고 실제 Inference `/health`를 monitoring에 연결했다. Simulator `/state`에는 별도 짧은 timeout을 적용했다. 기존 공개 FE/OpenAPI 계약은 유지했다.

DB 장애 중 Last Known Good bin mapping으로 선별을 계속하는 정책은 BE-09 범위다. 이 보정을 BE-09의 DB 장애 기능 완료로 해석하지 않는다.

## 5. 3/4 — 실제 Inference·MySQL 수직 통합

실제 `model.json`·`model.pt` package의 `model_version`은 `cqc-apple-separate12-focal-v2-cal-20260930`, `views=12`, `approval_status=unverified_candidate`, `threshold_status=calibrated_dev_oof`였다. `model.pt` SHA-256과 manifest 값이 일치했고 Inference가 모델을 로드했다. `index.json`의 기본 재생 대상, 검사당 이미지 12장과 대응 metadata를 확인한 실제 Dataset을 사용했다.

```text
Simulator → Backend → 실제 Inference → Backend 판정·bin → Virtual Control → MySQL
```

1차 수직 검증에서는 57건을 저장했다. 정상 bin 51건, 품질 confidence 0.60 미만 재검사 6건이었으며 control·persistence는 57건 모두 `SUCCEEDED`였다. history·statistics·CSV도 확인했다.

재현 환경을 정리한 뒤 `compose.local.yaml`로 Dataset 디렉터리를 `/data/dataset`에 read-only bind mount하고 임시 환경변수 override 없이 다시 기동했다. 이 재검증에서 23건을 추가 저장했다. 정상 20건, 품질 저신뢰 2건, 실제 500ms deadline 초과 1건이었다. Timeout 건은 재검사 bin으로 확정됐고 늦은 Inference 결과는 진단 필드에 저장됐다. Control·persistence 및 history·statistics·CSV를 확인해 **BE-08 3/4를 완료**했다.

## 6. 4/4 — 최신 병합본 배포 통합 검증

`origin/dev` 병합 뒤 `feat/backend`의 merge HEAD `8dfffd1`에서 기존 로컬 Dataset override를 사용해 MySQL·Inference·Backend·Simulator·Frontend Compose 서비스를 재빌드·재생성했다. Backend·Inference·Simulator는 새 이미지로 실행됐다. MySQL Alembic revision은 `20260929_02 (head)`였다.

- Inference `/health`: `ready`, `model_loaded=true`, 기대 모델 버전과 checkpoint SHA-256 일치, 12 views. Approval·threshold 상태는 위 모델 package 값 그대로였다.
- Backend `/health`: 200. Monitoring에서 MySQL·Inference healthy. 품질 confidence 기준은 0.60이었다.
- Simulator: 유효 Dataset으로 자동 재생했고 실행 중 `/health`가 healthy였다. `/state`와 revision, `intervalMs=2000`을 확인했다. 제어로 정지한 뒤 `/health` 503은 현재의 재생 중 health 조건에 따른 응답이다.

기존 통계 80건을 기준으로 이번 실행에서 19건이 추가돼 MySQL 저장·history·statistics가 모두 99건으로 일치했다. 초기 자동 재생 16건은 `used_frame_count=12`, 기대 모델 버전, 품종·품질·confidence, 정상 bin, Virtual Control 성공, persistence 성공을 기록했다. FE API를 통한 재시작 뒤 3건이 추가 저장됐다. 새 `inspection_id`를 history와 CSV에서 확인했고 monitoring snapshot도 조회했다. 이 19건에서는 저신뢰 결과가 자연 발생하지 않았으며, 그 경로는 3/4의 실제 모델 검증과 자동화 테스트 결과로 구분한다.

실제 FE 앱은 Compose 밖에서 production build/run해 페이지와 API 응답을 확인했다. FE proxy로 Backend snapshot·history·statistics를 조회했고, Simulator start/stop, fault 설정·해제, `intervalMs` 1000→3000→2000 변경 및 revision 증가를 확인했다. Backend public snapshot은 `capabilities.intervals=[1000,2000,3000]`을 제공한다. 별도 Simulator intervalMs 기능의 이 확인은 4/4 연동 확인이며 BE-08 핵심 구현 항목으로 계산하지 않는다. 현재 FE 화면 코드에는 intervalMs 선택 UI가 없어 FE 협업 항목으로 남긴다.

**배포 통합 blocker:** `compose.yaml`의 `frontend`는 실제 FE 앱이 아닌 Alpine placeholder이고 Jenkins도 해당 컨테이너의 실행 상태 위주로 검사한다. FE proxy 응답은 확인했지만 실제 브라우저 화면에 Backend 데이터가 표시되는지는 최종 확인하지 못했다. 따라서 4/4의 Backend 서비스·API 통합 검증은 완료했으나, **프로젝트 전체 BE-08 완료 판정은 보류**한다.

## 7. 주요 변경 위치와 검증

BE-08 구현의 주요 위치는 `src/api/core/config.py`, `src/api/services/inspections.py`, `src/api/services/late_results.py`, `src/api/repositories/inspections.py`, `src/api/repositories/persistence.py`다. 관련 검증은 `tests/api/test_config.py`, `tests/api/test_inspection_policy.py`, `tests/api/test_late_results.py`, `tests/api/test_late_result_mysql_integration.py`와 Simulator·관제 API 회귀 테스트에 있다. 로컬 재현 구성은 `compose.local.yaml`과 `.env.example`에 반영됐다. 통합시험 피드백 보정에는 `src/simulator/`와 Backend의 Inference·Simulator client 및 monitoring 경로가 포함됐다. 이 보고서를 작성하면서 기능 코드는 변경하지 않았다.

최신 병합본 검증에서 Backend·Simulator pytest는 **258 passed, 5 skipped**, Ruff check·Ruff format check·`git diff --check`는 통과했다. Skip 5건은 `CQC_TEST_DATABASE_URL`이 없어 건너뛴 조건부 MySQL 통합 테스트다. 이와 별도로 3/4에서는 실제 MySQL 수직 흐름과 late result 진단 저장을 확인했다. FE 테스트는 **40 passed**, production build 통과, lint는 error 0·warning 5건이었다. Inference는 Docker build/run, 실제 `/health`와 예측 결과로 확인했다.

## 8. 환경과 후속 작업

- `SIMULATOR_FAULT_TOKEN`: 로컬 검증은 `.env.example`의 개발용 예제값을 사용했다. 실제 통합·배포 환경은 별도 secret으로 교체해야 한다. 값 자체는 이 문서에 기록하지 않는다.
- Dataset: 약 12GB의 실제 자료는 Git에서 제외되어 있으며 `compose.local.yaml`의 read-only bind mount로 연결했다. 배포용 `compose.yaml`의 외부 Dataset volume 계약은 변경하지 않았다.
- 모델 package: 현재 저장소의 실행 기준은 **Git이 추적하는 `models/selected/model.json`과 `model.pt`**이며 Dockerfile이 이를 이미지 내부 `/app/models/approved`로 복사한다. 과거 후보 모델 경로와 현재 실행 경로를 구분한다. 폴더명과 모델의 `model_version`·`approval_status`는 별개이며, 실제 승인 상태는 `unverified_candidate`다.
- MLOps: `compose.yaml` placeholder를 실제 FE 이미지·Backend 연결로 교체하고 배포 기동·health를 검증해야 한다.
- FE·MLOps: 실제 배포 FE의 브라우저 화면에서 snapshot·이력·통계·Simulator 상태와 제어가 Backend 실데이터로 표시되는지 E2E 확인해야 한다. Interval 선택 UI는 별도 FE 협업 항목이다.

Backend 쪽 추가 코드 구현이 필요한 BE-08 항목은 확인되지 않았다. BE-09의 LKG DB 장애 fallback·실DB 중단/복구, 86,400/8,640 순환 삭제, BE-10·BE-11은 이 문서의 완료 범위에 포함하지 않는다.
