# BE-03 Mock Inference 검사 API

- WBS 코드: `BE-03`
- 담당: 홍준희
- 역할: 백엔드·DB
- 작업 기간: 2026-09-21 ~ 2026-09-22
- 상태: 완료

## 1. 작업 목적

Simulator가 보낼 검사 요청과 동일한 형식의 multipart 요청을 Backend가 받아, 실제 AI 모델 없이도 Mock 예측 결과를 독립적으로 반환할 수 있는 검사 API 수직 흐름을 구현했다.

이번 작업은 다음 세 단계로 진행했다.

```text
1단계: Inference 요청·응답 Schema와 Mock Inference Client
2단계: InspectionService와 Router → Service → MockInferenceClient 연결
3단계: 실제 Uvicorn 실행·HTTP 요청·OpenAPI·회귀 검증
```

실제 Inference HTTP 호출, DB 저장, bin 결정과 Virtual Control은 연결하지 않고 Mock 검사 API의 계약과 실행 가능성을 검증하는 범위로 제한했다.

## 2. WBS 완료 기준

BE-03의 WBS 완료 기준은 다음과 같다.

```text
Simulator 그룹 요청
→ Mock 예측
→ 판정 응답 독립 실행
```

실제 Simulator 구현과 연동은 후속 WBS 범위이므로, 이번 단계에서는 Simulator가 전송할 것과 같은 HTTP 요청을 직접 보내 Backend가 독립적으로 Mock 판정 응답을 반환하는 것으로 완료 기준을 충족했다.

검증된 전체 흐름:

```text
POST /v1/inspections
→ multipart parsing·입력 validation
→ InspectionService
→ InferenceRequest
→ MockInferenceClient
→ InferenceResponse
→ HTTP 200 응답
```

## 3. Backend 구성

BE-03에서 추가·연결한 주요 구조는 다음과 같다.

```text
src/api/
├─ clients/
│  ├─ __init__.py
│  └─ inference.py
├─ services/
│  ├─ __init__.py
│  └─ inspections.py
├─ schemas/
│  ├─ inspections.py
│  └─ inference.py
├─ routers/
│  └─ inspections.py
└─ main.py
```

- `schemas/inference.py`: Backend와 Inference 사이의 요청·응답 계약
- `clients/inference.py`: 실제 HTTP 없이 고정 결과를 반환하는 Mock Client
- `services/inspections.py`: 이미지 읽기, Inference 요청 생성, Client 호출과 응답 정합성 검증
- `routers/inspections.py`: multipart 파싱·HTTP 입력 검증과 Service 호출
- `main.py`: 기본 Mock Client와 Service 조립, 테스트용 명시적 Service 주입

의존 방향은 다음과 같이 유지했다.

```text
Router → InspectionService → MockInferenceClient
```

## 4. Inference 요청 계약

`InferenceRequest`는 다음 항목을 포함한다.

| 필드 | 형식 | 규칙 |
|---|---|---|
| `inspection_id` | string | 비어 있지 않은 공통 검사 식별자 |
| `images` | `list[bytes]` | 1장 이상 최대 12장 |
| `metadata` | metadata 객체 배열 | 이미지 수와 동일한 1~12개 |

이미지별 metadata는 BE-01의 `InspectionImageMetadata`를 중복 정의하지 않고 재사용한다.

```text
view_index
angle_direction
verticality_angle
horizontality_angle
```

`images[i]`와 `metadata[i]`는 같은 이미지를 의미한다. `view_index`는 `0..N-1` 순서를 따라야 하며 Backend는 이미지나 metadata를 재선택·재정렬하거나 값을 변경하지 않는다.

## 5. Inference 응답 계약

`InferenceResponse`는 현재 실제 Inference가 사용 중인 예측 필드와 Backend 공통 추적 필드를 함께 포함한다.

| 구분 | 필드 |
|---|---|
| 추적 | `inspection_id`, `used_frame_count` |
| 품목 | `crop_type` |
| 품종 | `predicted_cultivar`, `cultivar_confidence`, `cultivar_probabilities` |
| 품질 | `predicted_grade`, `quality_confidence`, `quality_probabilities` |
| 실행 정보 | `inference_time_ms`, `model_name`, `model_version`, `preprocessing_version` |

확률은 클래스 순서에 의존하는 배열이 아니라 라벨을 key로 가진 객체로 정의했다.

```json
{
  "cultivar_probabilities": {
    "fuji": 0.9,
    "yanggwang": 0.1
  },
  "quality_probabilities": {
    "L": 0.8,
    "M": 0.1,
    "S": 0.1
  }
}
```

품종은 `fuji`·`yanggwang`, 품질 등급은 `L`·`M`·`S`, confidence와 개별 확률은 `0..1` 범위로 Schema에서 검증한다.

## 6. Mock Inference Client

`MockInferenceClient.predict()`는 실제 HTTP 요청이나 AI 모델 로딩 없이 `InferenceRequest`를 받아 deterministic한 고정 응답을 반환한다.

동작 규칙:

- 요청의 `inspection_id`를 응답에 그대로 사용
- `used_frame_count`는 전달된 실제 이미지 수로 계산
- 품종은 `fuji`, 품종 confidence는 `0.9`
- 품질은 `L`, 품질 confidence는 `0.8`
- 추론 시간은 `12.5ms`
- Mock임을 구분할 수 있는 모델·전처리 버전 사용
- 랜덤값을 사용하지 않아 반복 실행 결과가 동일함

Mock의 목적은 모델 성능을 재현하는 것이 아니라 Backend 흐름과 Inference 계약을 안정적으로 테스트하는 것이다.

## 7. InspectionService

`InspectionService`는 Router에서 검증된 요청을 Inference 계약으로 변환하고 Client 호출 결과를 확인한다.

주요 책임:

1. `inspection_id`, `UploadFile` 배열과 metadata 수신
2. 이미지 파일을 전달받은 순서대로 `bytes`로 읽음
3. 읽은 파일 위치를 처음으로 되돌려 후속 재사용 가능성 유지
4. 이미지·metadata 순서를 바꾸지 않고 `InferenceRequest` 생성
5. `MockInferenceClient.predict()` 호출
6. 응답의 기본 정합성 검증
7. 검증된 `InferenceResponse` 반환

Service는 생성자에서 Client를 명시적으로 받는다. 별도 DI framework, Factory, Interface 또는 Abstract Base Class를 만들지 않고 테스트에서 Client를 교체할 수 있는 최소 주입 구조만 사용했다.

## 8. Router와 책임 분리

`POST /v1/inspections` Router는 BE-01의 HTTP 입력 검증을 유지하면서 임시 validation 응답을 실제 Mock 추론 응답으로 교체했다.

Router 책임:

- multipart/form-data 파싱
- `inspection_id` 검증
- 이미지 개수·전체 요청 크기·Content-Type 검증
- JSON text `metadata` 파싱
- metadata 개수·값·순서 검증
- `InspectionService` 호출
- Service 결과를 HTTP 응답으로 반환

Service로 이동한 책임:

- `UploadFile`을 `bytes`로 변환
- `InferenceRequest` 생성
- Mock Client 호출
- Inference 응답 정합성 확인

confidence 정책, bin 결정, 상태 전이, DB 저장, Virtual Control, timeout과 late-result 처리는 Router와 Service에 추가하지 않았다.

## 9. HTTP 응답

현재 검사 API는 Mock Inference 결과를 다음과 같이 반환한다.

```json
{
  "inspection_id": "be03-http-1",
  "used_frame_count": 1,
  "crop_type": "apple",
  "predicted_cultivar": "fuji",
  "cultivar_confidence": 0.9,
  "cultivar_probabilities": {
    "fuji": 0.9,
    "yanggwang": 0.1
  },
  "predicted_grade": "L",
  "quality_confidence": 0.8,
  "quality_probabilities": {
    "L": 0.8,
    "M": 0.1,
    "S": 0.1
  },
  "inference_time_ms": 12.5,
  "model_name": "mock-separate",
  "model_version": "mock-cqc-separate12-v1",
  "preprocessing_version": "mock-v1"
}
```

현재 단계에서는 Backend 응답 필드와 Inference 응답 필드가 동일하므로 별도 Backend Schema를 중복 생성하지 않고 `InferenceResponse`를 `response_model`로 재사용했다. 향후 bin·상태·제어·저장 결과가 Backend 응답에 추가되면 책임에 맞는 별도 응답 Schema로 분리한다.

## 10. 응답 정합성 검증

Mock 응답을 받은 뒤 Service에서 다음을 확인한다.

- 응답 `inspection_id`가 요청 값과 동일한지
- `used_frame_count`가 실제 전달 이미지 수와 동일한지
- 품종·품질 prediction이 허용된 값인지
- confidence와 probabilities가 Schema 범위와 구조를 만족하는지
- 모델·전처리 정보와 추론 시간이 응답 Schema를 만족하는지

식별자나 사용 이미지 수가 일치하지 않으면 `InferenceResponseMismatchError`를 발생시킨다. Router는 현재 이를 HTTP `500`으로 변환한다. 최종 공통 오류 응답과 error code 체계는 후속 단계에서 확정한다.

## 11. Backend 단독 실행 검증

실제 Inference 서버와 AI 모델을 실행하지 않고 Uvicorn Backend만 기동해 HTTP 요청·응답을 검증했다.

실행 명령:

```powershell
.\.venv\Scripts\python.exe -m src.api.main
```

검증 결과:

- Uvicorn이 `http://0.0.0.0:8000`에서 정상 기동
- `GET /health`: HTTP `200`
- PNG 1장 검사 요청: HTTP `200`, `used_frame_count=1`
- PNG 12장 검사 요청: HTTP `200`, `used_frame_count=12`
- 두 요청 모두 `inspection_id` 유지
- 품종·품질 예측, confidence, probabilities와 버전 정보 반환
- 검증 후 Backend 정상 종료
- 검증용 임시 이미지·스크립트 정리

이미지와 metadata의 순서 및 값 유지 여부는 Service 테스트의 기록용 Client를 통해 확인했다. HTTP 응답은 입력 배열을 다시 노출하지 않으므로 응답 본문만으로 순서를 재확인하지는 않는다.

## 12. OpenAPI 확인

FastAPI OpenAPI에서 다음을 확인했다.

- `/v1/inspections` endpoint 노출
- 요청 Content-Type이 `multipart/form-data`
- `inspection_id` text field
- 반복 `images` file field
- `metadata` text field
- HTTP `200` 응답이 `InferenceResponse` Schema를 참조

`metadata`는 multipart 내부에서 JSON text로 전달되므로 OpenAPI에는 문자열로 표시된다. 내부 JSON 배열과 객체 구조를 Swagger UI가 직접 표현하지 못하는 한계가 있지만, 이번 단계에서는 이를 위해 복잡한 custom OpenAPI를 추가하지 않았다.

## 13. 실제 Inference와 계약 차이

`src/inference`의 현재 구현은 다음 필드를 이미 사용한다.

- `crop_type`
- `predicted_cultivar`
- `cultivar_confidence`
- `cultivar_probabilities`
- `predicted_grade`
- `quality_confidence`
- `quality_probabilities`
- `inference_time_ms`
- `model_name`
- `model_version`
- `preprocessing_version`

다만 Backend 확정 계약과 비교하면 다음 차이가 남아 있다.

| 구분 | Backend 계약 | 현재 실제 Inference |
|---|---|---|
| 요청 식별자 | `inspection_id` 포함 | 없음 |
| 요청 metadata | 이미지별 metadata 포함 | 없음 |
| 응답 식별자 | `inspection_id` 포함 | 없음 |
| 사용 프레임 수 | `used_frame_count` 포함 | 없음 |

실제 연동 전에 Inference 담당 영역의 요청·응답 Schema, endpoint 구현, OpenAPI와 계약 테스트에 위 항목을 반영해야 한다. BE-03에서는 `src/inference`를 수정하지 않았다.

## 16. 주요 설계 결정

### BE-01 metadata Schema를 재사용한다

동일한 이미지 metadata를 HTTP 입력과 Inference 요청에서 다르게 정의하면 계약이 어긋날 수 있으므로 `InspectionImageMetadata`를 재사용했다.

### Mock은 실제 Inference와 같은 논리 응답을 사용한다

Mock 전용 응답을 별도로 만들지 않아 후속 실제 HTTP Client로 교체할 때 Service와 Router의 변경 범위를 줄였다.

### Client는 단순 생성자 주입으로 교체한다

구현체가 하나인 Interface나 Factory를 만들지 않고, 테스트에 필요한 정도의 명시적 의존성 주입만 적용했다.

### 이미지 파일을 저장하지 않는다

이미지는 Service에서 메모리의 `bytes`로 읽어 Mock에 전달하며 디스크나 DB에 저장하지 않는다.

## 17. 의도적으로 구현하지 않은 항목

BE-03에서는 다음 항목을 구현하지 않았다.

- 실제 `httpx.AsyncClient`와 Inference HTTP 호출
- `src/inference` 요청·응답 계약 수정
- 실제 Simulator 구현과 연동
- Repository와 DB INSERT·UPDATE
- bin mapping 조회와 목적 bin 결정
- confidence threshold 판정과 재검사 정책
- 검사·제어·저장 상태 Enum과 상태 전이
- Virtual Control
- Inference transport timeout과 late-result 처리
- 최종 공통 error code와 오류 응답 Schema
- 이미지 저장
- Generic Repository, 불필요한 Interface·Factory·Base class

## 18. 남은 계약과 후속 작업

BE-03 이후 실제 Inference 연결 전에 다음 사항이 필요하다.

1. Inference 요청에 `inspection_id`와 이미지별 metadata 반영
2. Inference 응답에 `inspection_id`와 `used_frame_count` 반영
3. 실제 endpoint와 multipart wire schema 최종 확인
4. 실제 HTTP Client, URL 설정과 transport timeout 구현
5. 실제 응답 오류·Schema 불일치의 공통 error code 확정
6. BE-04에서 confidence 정책, 상태 분리, bin 결정과 Virtual Control 연결
7. Repository를 통한 검사 결과 저장

실제 Simulator의 그룹 순회·500ms 간격 전송·시작·정지·위치 복구는 Simulator 후속 WBS에서 구현한다.

## 19. 요약

“CQC Backend의 검사 API를 Router, InspectionService와 MockInferenceClient로 연결해 Simulator와 동일한 최대 12장 multipart 요청을 독립적으로 처리하도록 구현했습니다. 실제 Uvicorn 서버에 1장과 12장 요청을 보내 HTTP 200과 고정 Mock 판정 결과를 확인했고, 이미지·metadata 순서 유지와 응답 정합성을 포함한 Backend 테스트 40개를 통과했습니다.”
