# MO-02 5개 서비스 Compose 골격

- WBS 코드: `MO-02`
- 담당: 홍유나
- 역할: MLOps·CI/CD
- 작업 기간: 2026-09-19 ~ 2026-09-22
- 상태: 진행 중

## 1. 작업 목적

CQC 프로젝트의 각 실행 단위를 Docker Compose에서 한 번에 관리할 수 있도록 기본 서비스 구조를 구성했다.

이번 단계에서는 실제 Backend, Inference, Frontend, Simulator 코드가 아직 모두 완성되지 않았기 때문에 실제 실행 환경을 완성하는 것이 아니라, 이후 각 담당자의 구현 결과를 연결할 수 있는 Compose 골격을 먼저 만드는 것을 목표로 했다.

이를 통해 각 파트가 독립적으로 개발되더라도 최종적으로 동일한 Docker Compose 환경에 연결할 수 있도록 공통 실행 기준을 마련했다.

## 2. 이번 작업에서 한 일

프로젝트 루트에 `compose.yaml` 파일을 생성하고 다음 5개 서비스를 등록했다.

- `mysql`
- `inference`
- `backend`
- `frontend`
- `simulator`

각 서비스에는 공통적으로 다음 재시작 정책을 적용했다.

```yaml
restart: unless-stopped
```

해당 정책은 컨테이너가 비정상 종료되거나 Docker가 재시작된 경우 자동으로 다시 실행되도록 하면서, 사용자가 직접 서비스를 중지한 경우에는 자동으로 다시 실행하지 않도록 하기 위해 사용했다.

## 3. 서비스 구성

### 3.1 MySQL

`mysql` 서비스는 검사 이력, 통계, 제어 결과 등 CQC 프로젝트에서 필요한 데이터를 저장하는 데이터베이스 역할을 담당한다.

현재 프로젝트에서 MySQL 사용은 확정된 상태이므로 공식 MySQL Docker 이미지를 사용하도록 구성했다.

```yaml
mysql:
  image: mysql:8.4
  restart: unless-stopped
```

초기 실행에 필요한 DB 이름, 사용자, 비밀번호는 환경 변수 형식으로 작성했다.

실제 운영 환경의 비밀번호는 이후 `.env` 파일을 이용해 별도로 관리할 예정이다.

## 4. Placeholder 서비스 구성

현재 `inference`, `backend`, `frontend`, `simulator`는 실제 Dockerfile과 실행 명령이 아직 확정되지 않은 상태다.

따라서 MO-02 단계에서는 Alpine Linux 기반의 임시 컨테이너를 사용했다.

```yaml
image: alpine:3.20
```

각 컨테이너는 실행 시 자신의 서비스 이름을 출력한 뒤 종료되지 않고 유지되도록 구성했다.

예시:

```yaml
command:
  - sh
  - -c
  - |
    echo "[MO-02 placeholder] backend"
    tail -f /dev/null
```

이 방식은 아직 구현되지 않은 애플리케이션 실행 명령을 임의로 결정하지 않으면서도, Docker Compose 안에 5개 서비스 구조를 미리 구성할 수 있다는 장점이 있다.

## 5. 서비스 역할

### inference

AI 모델 추론을 담당하는 서비스다.

Backend에서 전달한 다각도 사과 이미지를 받아 품종, 품질, 신뢰도, 모델 버전 등의 예측 결과를 반환하는 역할을 한다.

실제 모델 담당자의 inference API 구현이 완료되면 현재 placeholder 설정을 실제 Dockerfile과 실행 명령으로 교체할 예정이다.

### backend

전체 검사 흐름을 제어하는 핵심 API 서비스다.

주요 역할은 다음과 같다.

- simulator 입력 수신
- inference API 호출
- 예측 결과 처리
- 저신뢰 및 재검사 정책 처리
- Virtual Control 및 bin 판정
- MySQL 검사 이력 저장
- Frontend API 제공

Backend는 FastAPI 사용이 확정되어 있지만 실제 실행 명령은 아직 확정되지 않았기 때문에 현재 단계에서는 placeholder 상태로 구성했다.

### frontend

사용자에게 현재 검사 상태와 결과를 보여주는 웹 서비스다.

주요 화면은 다음과 같다.

- 현재 검사 상태
- 품종·품질 판정 결과
- 최근 검사 이력
- 통계 및 차트
- 시스템 상태

Frontend 구현이 완료되면 실제 빌드 방식과 웹 서버 실행 명령을 Compose에 연결할 예정이다.

### simulator

실제 농산물 검사 장비 대신 저장된 사과 이미지 그룹을 자동으로 Backend에 전송하는 역할을 한다.

실제 프로젝트에서는 약 500ms 간격으로 사과 그룹을 입력해 실제 검사 라인과 유사한 흐름을 재현한다.

목표 처리량은 초당 사과 그룹 2개이다.

Simulator 구현이 완료되면 실제 실행 명령과 상태 저장 기능을 Compose에 연결한다.

## 6. 이번 단계에서 제외한 작업

MO-02에서는 Compose 서비스 구조만 먼저 구성하고 다음 항목은 의도적으로 제외했다.

### Healthcheck

서비스가 실제로 정상 사용 가능한 상태인지 확인하는 healthcheck 구성은 `MO-04`에서 진행한다.

### 서비스 기동 순서

다음과 같은 실제 기동 의존성도 `MO-04`에서 구성한다.

```text
MySQL + inference
        ↓
      backend
        ↓
simulator + frontend
```

### Docker Volume

다음 데이터의 영구 저장을 위한 Volume 구성은 `MO-05`에서 진행한다.

- MySQL 데이터
- 장애 이미지
- simulator 마지막 처리 위치
- 로그

### 환경 변수 및 비밀값 관리

실제 DB 비밀번호, 서비스 URL 등의 환경 변수 상세 구성도 `MO-05`에서 추가한다.

### 실제 Dockerfile 연결

Backend, Inference, Frontend, Simulator 담당자의 실제 실행 코드와 Dockerfile이 완성된 뒤 현재 placeholder 설정을 실제 `build` 또는 `image` 설정으로 변경한다.

## 7. 확인 방법

Compose 파일의 YAML 문법과 설정이 정상인지 다음 명령으로 확인한다.

```powershell
docker compose config
```

서비스 실행은 다음 명령으로 확인한다.

```powershell
docker compose up -d
```

실행 중인 서비스 상태는 다음 명령으로 확인한다.

```powershell
docker compose ps
```

정상적인 경우 다음 5개 서비스가 확인되어야 한다.

```text
mysql
inference
backend
frontend
simulator
```

Placeholder 서비스의 로그는 다음 명령으로 확인할 수 있다.

```powershell
docker compose logs --tail=20
```

## 8. 이렇게 구성한 이유

현재 프로젝트는 각 파트가 동시에 구현을 진행하고 있기 때문에 모든 서비스의 실제 실행 명령이 확정될 때까지 기다린 뒤 Compose를 작성하면 MLOps 작업 전체가 늦어질 수 있다.

반대로 MLOps 담당자가 각 서비스의 실행 방법과 포트를 임의로 정하면 Backend, Model, Frontend 담당자의 구현 방식과 충돌할 수 있다.

따라서 이번 단계에서는 실행 단위와 재시작 정책만 먼저 확정하고, 실제 실행 설정은 각 담당자의 구현 결과가 나오는 시점에 연결하도록 구성했다.

이 방식으로 각 파트의 독립 개발과 MLOps 작업을 병렬로 진행할 수 있다.
