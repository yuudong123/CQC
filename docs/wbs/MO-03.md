# MO-03 Jenkins CI 환경 연결·기본 검사

## 1. 작업 개요

- **WBS 코드:** MO-03
- **담당:** MLOps / CI·CD
- **작업명:** Jenkins CI 환경 연결·기본 검사
- **선행 작업:** MO-01, MO-02

CQC 프로젝트의 CI 환경을 구성하기 위해 GitHub 저장소와 Jenkins를 연결하고, Jenkins가 프로젝트 코드를 Checkout한 뒤 Docker 및 Docker Compose를 사용할 수 있도록 기본 실행 환경을 구성하였다.

이후 `Jenkinsfile`을 기반으로 `feat/* → dev` 개발 흐름에서 기본 검사를 자동으로 수행할 수 있는 CI 구조를 준비하였다.

---

## 2. 작업 목적

개발자가 코드를 수정한 뒤 수동으로 모든 실행 여부를 확인하는 방식은 누락이나 환경 차이로 인한 오류가 발생할 수 있다.

이를 줄이기 위해 Jenkins를 사용하여 다음 과정을 자동화할 수 있는 기반을 구성하였다.

```text
GitHub
   ↓
Jenkins
   ↓
Repository Checkout
   ↓
기본 코드 검사
   ↓
Docker / Docker Compose 검사
   ↓
통합 실행 및 배포 단계
```

MO-03에서는 실제 통합 배포보다 먼저 **CI가 실행될 수 있는 기본 연결 환경을 구축하는 것**을 목표로 한다.

---

## 3. 주요 작업 내용

### 3.1 Jenkins 실행 환경 확인

Jenkins가 실행되는 환경에서 CI Pipeline을 수행할 수 있도록 Jenkins 실행 상태와 Java 환경을 확인하였다.

확인 항목:

```bash
java -version
```

Jenkins 웹 화면 접속 여부:

```text
http://localhost:8080
```

이를 통해 Jenkins Pipeline을 실행할 수 있는 기본 환경을 준비하였다.

---

### 3.2 GitHub 저장소 연결

Jenkins에서 CQC GitHub 저장소를 Checkout할 수 있도록 저장소 연결을 구성하였다.

대상 저장소:

```text
CQC
```

주요 브랜치 구조:

```text
feat/*
   ↓
dev
   ↓
main
```

CI는 개발 작업이 이루어지는 `feat/*`와 통합 브랜치인 `dev`를 중심으로 구성한다.

`main`은 최종 발표 및 안정 버전을 표시하는 용도로 사용하며 개발 중 자동 배포 대상으로 사용하지 않는다.

---

### 3.3 Jenkins Git Checkout 확인

Jenkins Pipeline에서 GitHub 저장소의 코드를 가져올 수 있는지 확인한다.

주요 확인 사항:

- Jenkins에서 Git 사용 가능 여부
- Repository 접근 가능 여부
- `dev` 브랜치 Checkout 여부
- Pipeline 작업 공간에 프로젝트 파일 생성 여부

Git 설치 상태는 다음 명령으로 확인할 수 있다.

```bash
git --version
```

---

### 3.4 Jenkins에서 Docker 사용 환경 확인

CQC 프로젝트는 Docker Compose 기반으로 여러 서비스를 실행하기 때문에 Jenkins에서도 Docker 명령을 실행할 수 있어야 한다.

확인 명령:

```bash
docker --version
docker compose version
```

이를 통해 Jenkins 실행 환경에서 Docker 및 Docker Compose를 사용할 수 있는지 확인한다.

---

### 3.5 Docker Compose 구성 검사

MO-02에서 작성한 Compose 환경을 Jenkins에서 검사할 수 있도록 연결한다.

기본 검사:

```bash
docker compose config
```

이 검사를 통해 실제 컨테이너를 실행하기 전에 Compose 파일의 문법과 환경변수 구성이 올바른지 확인할 수 있다.

MO-02에서 Compose 골격을 먼저 구성한 뒤 MO-03에서 Jenkins와 연결하는 이유도 이 때문이다.

```text
MO-01
환경·브랜치 규칙 정의
   ↓
MO-02
Docker Compose 골격 구성
   ↓
MO-03
Jenkins CI 연결 및 검사
```

## 4. Jenkinsfile 구성

GitHub Actions의 `.github/workflows/ci.yml` 대신 Jenkins를 CI/CD 도구로 사용하므로 프로젝트 루트에 `Jenkinsfile`을 사용한다.

초기 Pipeline은 복잡한 배포 기능보다 기본 검사를 중심으로 구성한다.

예상 흐름:

```text
Checkout
   ↓
환경 확인
   ↓
Python 기본 검사
   ↓
Docker Compose 검사
   ↓
테스트
```

초기 MO-03에서는 다음 항목을 우선 확인한다.

- GitHub Repository Checkout
- Python 기본 문법 검사
- Docker 사용 가능 여부
- Docker Compose 구성 검사
- Pipeline 성공/실패 결과 확인

추후 테스트 코드가 추가되면 동일 Pipeline에 자동 테스트 단계를 확장한다.

---

## 5. 브랜치별 CI 정책

### feat/*

각 기능 개발 브랜치에서 작업한 코드는 `dev`로 병합하기 전에 기본 검사를 수행한다.

```text
feat/*
  ↓
CI 검사
  ↓
Pull Request
  ↓
dev
```

### dev

팀원 작업이 통합되는 개발 브랜치로 사용한다.

`dev` 반영 후 Jenkins Pipeline을 통해 통합 상태를 확인한다.

### main

`main`은 개발 중 자동 배포 대상으로 사용하지 않고 최종적으로 검증된 발표 버전을 표시하는 용도로 사용한다.

---

## 6. GitHub Actions를 사용하지 않은 이유

초기에는 GitHub Actions의 `ci.yml`을 사용하는 방안도 검토했으나, CQC 프로젝트에서는 Jenkins를 CI/CD 도구로 사용하기로 하였다.

따라서 CI 도구를 중복으로 구성하지 않고 다음과 같이 통일하였다.

```text
사용

GitHub
Jenkins
Jenkinsfile
Docker
Docker Compose
```

```text
미사용

GitHub Actions ci.yml
```

CI 도구를 하나로 통일하여 관리 포인트를 줄이고 이후 Docker 기반 통합 배포 단계까지 Jenkins Pipeline으로 연결할 수 있도록 구성한다.

## 9. 정리

MO-03에서는 단순히 `Jenkinsfile`만 작성하는 것이 아니라 Jenkins가 실제 CI를 수행할 수 있도록 **GitHub → Jenkins → Docker/Docker Compose** 연결 환경을 먼저 구성한다.

이를 통해 개발 코드가 `dev`에 통합되기 전에 기본 오류를 자동으로 확인하고, 이후 healthcheck·통합 시험·배포 자동화로 확장할 수 있는 CI/CD 기반을 마련한다.
