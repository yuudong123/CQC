# MO-01 기술 스택·브랜치·환경 규칙 작성

- WBS 코드: `MO-01`
- 담당: 홍유나
- 역할: MLOps·CI/CD
- 작업 기간: 2026-09-16 ~ 2026-09-18
- 상태: 완료

## 1. 작업 목적

CQC 프로젝트에서 각 파트가 개발한 기능을 하나의 실행 환경에서 안정적으로 통합하기 위해
MLOps 기준이 되는 기술 스택, Git 브랜치 규칙, 실행·배포 환경 규칙을 먼저 정리했다.

이 작업의 핵심 목적은 이후 Compose 구성과 CI/CD 작업에서 팀원마다 다른 방식으로 실행하거나
배포하는 문제를 줄이고, 발표 환경에서도 같은 절차로 프로젝트를 재현할 수 있도록 기준을 만드는 것이다.

## 2. 이번 작업에서 한 일

### 2.1 Docker 실행 환경 확인

실제 프로젝트를 실행할 PC에서 Docker와 Docker Compose 버전을 확인했다.

- Docker: `29.7.2`
- Docker Compose: `v5.4.0`
- 프로젝트 루트: `C:\CQC`

확인 명령:

```powershell
docker --version
docker compose version
```

### 2.2 프로젝트 구조 확인

현재 프로젝트 루트와 `src`, `scripts` 내부 구조를 확인했다.

확인 당시 실제 코드가 확인된 부분은 `src/data/manifest.py`였으며,
`src/api`, `src/inference`, `src/web`, `scripts`는 아직 실행 코드가 없는 골격 상태였다.

따라서 아직 정해지지 않은 실행 명령, 포트, Dockerfile, healthcheck URL 등은 임의로 확정하지 않고
각 담당자의 실제 구현 완료 후 연결하도록 했다.

### 2.3 Docker Compose 서비스 기준 정리

CQC 프로젝트는 다음 5개 서비스를 Compose 실행 단위로 사용하도록 정리했다.

- `simulator`
- `inference`
- `backend`
- `frontend`
- `mysql`

가상 제어 기능은 별도 컨테이너로 분리하지 않고 `backend` 내부 기능으로 처리한다.

서비스 간 통신은 Kafka를 사용하지 않고 HTTP를 사용한다.

기본 흐름:

```text
simulator
    ↓
backend
    ↓
inference

backend
    ↓
mysql

frontend
    ↓
backend
```

## 3. Git 브랜치 규칙

브랜치 역할을 다음과 같이 정리했다.

- `feat/*`: 개인 기능 개발
- `dev`: 팀 통합 및 자동 배포 기준
- `main`: 최종 발표 버전 표시

`feat/* → dev` 병합은 Pull Request를 사용하고 최소 1명의 확인을 받는다.

자동 배포는 `dev` 브랜치만 대상으로 하며,
`main` 브랜치에는 자동 배포를 연결하지 않는다.

## 4. 실행 환경 기본 규칙

### 4.1 재시작 정책

Docker 컨테이너의 기본 재시작 정책은 다음을 사용한다.

```yaml
restart: unless-stopped
```

비정상 종료 시 자동 재시작하되,
사용자가 직접 중지한 경우에는 다시 자동 실행하지 않도록 하기 위해 선택했다.

### 4.2 정상 기동 순서

정상 시작 시 서비스 의존 순서는 다음과 같이 정리했다.

```text
MySQL + inference
        ↓
      backend
        ↓
simulator + frontend
```

- MySQL과 inference 상태 확인
- 필요한 MySQL 마이그레이션 적용
- backend 시작
- backend 정상 확인
- simulator와 frontend 시작

실행 중 inference 장애가 발생해도 backend는 시스템 오류로 처리하고 재검사 흐름을 유지한다.

실행 중 MySQL 장애가 발생해도 정상 선별 처리는 계속하며,
저장 실패는 상태와 로그로 남긴다.

## 5. Healthcheck 기준

각 서비스가 단순히 실행 중인지가 아니라 실제로 사용할 수 있는 상태인지 확인하기 위한 기준을 정리했다.

| 서비스 | 확인 기준 |
|---|---|
| `mysql` | DB 연결 및 간단 조회가 가능한지 확인 |
| `inference` | 테스트 추론이 정상 동작하는지 확인 |
| `backend` | health API가 정상 응답하는지 확인 |
| `frontend` | 웹 페이지가 정상적으로 응답하는지 확인 |
| `simulator` | 최근 1초 내 입력이 생성되고 있는지 확인 |

실제 URL과 세부 명령은 각 서비스 구현 후 확정한다.

## 6. 환경 변수·비밀값·Git 관리 기준

실제 비밀번호와 접속 정보는 Git에 저장하지 않는다.

```text
.env
→ 실제 환경 값
→ Git 제외

.env.example
→ 필요한 환경 변수 이름과 예시 형식
→ Git 포함 가능
```

추가로 다음 항목도 Git에서 제외한다.

- 원본 데이터
- 모델 파일
- 모델 가중치·체크포인트
- 대용량 생성 출력

## 7. 모델 관리 기준

MLOps는 모델 자체를 학습하거나 선정하지 않고,
모델 담당자가 제공한 승인 모델을 배포 환경에 연결한다.

관리 대상:

- 모델 파일
- 모델명
- 모델 버전
- 클래스 매핑
- 입력 크기
- 프레임 선택 규칙
- 전처리 설정
- 신뢰도 기준
- 모델 체크섬
- 평가 결과

모델 파일이 없거나 로딩에 실패하면 inference 상태를 실패로 표시하고 로그에 원인을 기록하도록 기준을 잡았다.

## 8. 저장 데이터와 Volume 기준

재시작 이후에도 유지되어야 하는 데이터는 Docker Volume을 사용하도록 정리했다.

보존 대상:

- MySQL 데이터
- 장애 이미지
- simulator 마지막 입력 위치
- 순환 로그

장애 이미지는 최대 100개까지만 유지하고,
100개를 초과하면 가장 오래된 이미지부터 삭제한다.

MySQL 검사 이력은 86,400건 도달 시 오래된 8,640건을 삭제하는 순환 정책을 사용한다.

## 9. simulator 재시작·자동 실행 기준

Docker Compose가 정상 기동되면 simulator의 입력과 검사 흐름도 자동으로 시작하도록 기준을 정했다.

- 웹 페이지 접속 여부와 관계없이 백그라운드에서 계속 동작
- 기본 입력 목표: 500ms마다 사과 그룹 1개
- 목표 처리량: 초당 사과 그룹 2개
- Docker 재시작 후 마지막 처리 위치의 다음 입력부터 재개
- 마지막 위치는 Docker Volume의 상태 파일로 관리

## 10. 로그 관리 기준

장시간 실행해도 로그가 계속 쌓이지 않도록 로그 순환 정책을 사용한다.

로그에는 다음 정보를 구분해서 남길 수 있어야 한다.

- API 오류
- 모델 오류
- DB 오류
- 배포·실행 실패 원인

다음 정보는 로그에 기록하지 않는다.

- DB 비밀번호
- 비밀값
- 민감한 경로

로그 최대 크기와 보존 개수는 실제 통합 실행 후 결정한다.

## 11. CI/CD 기본 방향

CI/CD는 다음 흐름을 기준으로 정리했다.

```text
feat/*
   ↓ PR
자동 검사
   ↓
dev 병합
   ↓
통합 검사
   ↓
검사 통과
   ↓
배포 환경 반영
```

검사 대상:

- 데이터 검사
- 문법 및 단위 테스트
- API 계약
- 모델 로딩
- DB 마이그레이션
- Docker Compose 설정
- 핵심 통합 동작

새로운 `dev` 버전의 검사 또는 배포가 실패하면
기존에 정상 실행 중인 버전을 유지하도록 했다.

CI/CD 제품 자체는 아직 확정하지 않았으며,
실제 개발 환경과 팀 사용성을 확인한 뒤 결정한다.

## 12. CPU 성능 시험 기준

최종 배포 환경은 다음과 같다.

```text
Intel Core i7-4790
RAM 16GB
CPU Docker 환경
```

같은 Compose 환경에서 다음 조건을 비교할 수 있도록 기준을 정했다.

- 입력 이미지 수: 4 / 8 / 12 / 16 / 40장
- 순차 처리와 병렬 처리 비교
- 동시 처리 수 비교
- 평균 처리시간
- 최대 처리시간
- p95
- 처리량

목표:

- 초당 사과 그룹 2개
- 그룹당 모델 추론 500ms 이내
- 가상 제어 응답 100ms 목표

## 13. 최종 수용시험 기준

최종 배포 전 다음 항목을 반복 가능한 방식으로 시험하도록 정리했다.

- 정상 검사 100건
- 고정 시험 이미지에서 같은 모델·입력·설정의 예측 재현 여부
- 초당 사과 그룹 2개 처리
- 그룹당 모델 추론 500ms 목표 확인
- 가상 제어 응답 100ms 목표 확인
- 장애 시나리오 5종
- Docker 재시작 및 simulator 위치 복구
- healthcheck
- DB 86,400건 도달 시 오래된 8,640건 삭제 확인
- 장애 이미지 100개 초과 시 오래된 이미지 삭제 확인
- CSV 결과와 필터·검사 이력 일치 확인
- 로그 순환 확인
- 배포 모델 버전과 inference 응답·검사 이력의 모델 버전 일치 확인
- 새 환경에서 문서화된 절차로 서비스 실행 가능 여부 확인

## 14. 발표 버전 관리 기준

2026-10-13 기능 동결 이후에는 치명적 오류를 제외한 기능 변경을 하지 않는다.

최종 수용시험을 통과한 버전을 발표용 배포 후보로 지정하고
Git 태그 후보를 부여한다.

발표 리허설과 최종 확인이 끝난 버전은 `main`에 최종 발표 버전으로 표시한다.

`main`은 최종 버전 표시용이며 자동 배포에는 사용하지 않는다.

## 15. 아직 확정하지 않은 항목

MO-01 단계에서는 다음 항목을 일부러 확정하지 않았다.

- CI/CD 제품과 버전
- backend Dockerfile과 실행 명령
- inference Dockerfile과 실행 명령
- frontend Dockerfile과 빌드·실행 명령
- simulator Dockerfile과 실행 명령
- 서비스별 포트
- 실제 healthcheck URL
- Docker Volume 실제 이름과 마운트 경로
- 로그 최대 크기와 보존 개수
- 실제 배포·롤백 구현 방식
- 모델 실제 배포 경로

각 담당자의 실제 구현과 계약이 확정된 후 연결할 예정이다.

## 16. 이렇게 결정한 이유

CQC는 약 한 달 동안 구현하는 프로젝트이기 때문에
복잡한 분산 시스템이나 불필요한 MLOps 도구를 추가하기보다
팀원이 직접 이해하고 설명할 수 있는 구조를 우선했다.

Docker와 Docker Compose를 사용하면 각 팀원의 실행 환경 차이를 줄이고,
발표 PC에서도 같은 방식으로 서비스를 실행할 수 있다.

또한 미확정된 백엔드·프론트·모델 설정을 MLOps에서 임의로 결정하지 않고,
각 담당자의 구현 결과를 기준으로 연결하도록 하여 역할 간 충돌을 줄였다.
