# BE-04 Inference 500ms·저신뢰·상태 분리·가상 제어

- WBS 코드: `BE-04`
- 담당: 홍준희
- 역할: 백엔드·DB
- 작업 기간: 2026-09-23 ~ 2026-09-28
- 상태: 완료

## 1. 작업 목적

Inference 결과에 confidence와 제한시간 정책을 적용해 정상·재검사 여부와 목적 bin을 결정하고, 실제 장치 없이도 Virtual Control 흐름을 독립적으로 검증할 수 있도록 구현했다.

이번 작업은 다음 네 단계로 진행했다.

```text
1단계: 검사 상태·confidence 판정 정책·설정값
2단계: 임시 bin mapping·Mock Virtual Control·거부 대체 흐름
3단계: Inference 500ms business deadline·timeout 판정
4단계: late-result 정책·task 제한·서버 종료 정리·완료 검증
```

실제 Inference HTTP Client, DB 저장, Repository와 실제 장치 통신은 연결하지 않고 Mock 기반 Backend 정책과 전체 수직 흐름을 검증하는 범위로 제한했다.

## 2. WBS 완료 기준

BE-04의 WBS 완료 기준은 다음과 같다.

```text
정상 품종 2종 × 품질 3종 = 정상 bin 6개
저신뢰·timeout·오류용 재검사 bin 1개
정상 bin 명령 거부 시 재검사 bin 대체 요청 1회
Virtual Control 무응답 기록
```

Mock·in-memory Backend 범위에서 다음 전체 흐름을 구현하고 검증했다.

```text
POST /v1/inspections
→ InspectionService
→ MockInferenceClient
→ 500ms business deadline
→ confidence 또는 timeout 판정
→ 목적 bin 결정
→ MockVirtualControl
→ Backend 검사 응답
→ 필요한 경우 late-result 진단 수집
```

## 4. 상태 모델

DB native ENUM으로 고정하지 않고 기존 ORM의 `VARCHAR` 컬럼과 호환되는 문자열 Enum으로 정의했다.

### `InspectionStatus`

```text
PROCESSING
COMPLETED
REINSPECTION_REQUIRED
```

### `ControlStatus`

```text
NOT_REQUESTED
PENDING
SUCCEEDED
REJECTED
NO_RESPONSE

```


## 5. 실행 설정

BE-04 정책값은 Service에 하드코딩하지 않고 `pydantic-settings`로 관리한다.

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| `CULTIVAR_CONFIDENCE_THRESHOLD` | `0.50` | 품종 정상 판정 최소 confidence |
| `QUALITY_CONFIDENCE_THRESHOLD` | `0.50` | 품질 정상 판정 최소 confidence |
| `INFERENCE_BUSINESS_DEADLINE_MS` | `500` | 정상 판정 결과를 확정하는 제한시간 |
| `INFERENCE_HARD_TIMEOUT_MS` | `2000` | late Inference task 최대 생존시간 초안 |
| `MAX_LATE_TASKS` | `4` | 동시에 추적할 late task 수 초안 |

두 threshold는 `0..1` 범위로 검증한다. hard timeout은 business deadline보다 커야 하며, hard timeout과 late task 수는 운영 확정값이 아닌 초기 구현값이다.

## 6. Confidence 판정 정책

Inference가 business deadline 안에 정상 응답하면 두 confidence를 각각 설정 threshold와 비교한다.

정상 판정:

```text
cultivar_confidence >= cultivar threshold
AND
quality_confidence >= quality threshold

inspection_status = COMPLETED
review_required = false
exclude_from_normal_stats = false
decision_reason = NORMAL
```

저신뢰 판정:

```text
cultivar_confidence < cultivar threshold
OR
quality_confidence < quality threshold

inspection_status = REINSPECTION_REQUIRED
review_required = true
exclude_from_normal_stats = false
```

threshold와 정확히 같은 값은 정상으로 판정한다. 저신뢰는 유효한 모델 응답이므로 정상 품종·품질 통계에서 제외하지 않는다.

## 7. 내부 판정 결과

`InspectionDecision`은 Inference 응답과 분리된 Backend 내부 판정 결과다.

포함 정보:

- `inspection_status`
- `review_required`
- `exclude_from_normal_stats`
- `reason`
- 실제 적용한 품종 confidence threshold
- 실제 적용한 품질 confidence threshold

판정 사유:

```text
NORMAL
LOW_CULTIVAR_CONFIDENCE
LOW_QUALITY_CONFIDENCE
LOW_BOTH_CONFIDENCE
INFERENCE_DEADLINE_EXCEEDED
```

판정 사유는 최종 공통 error code와 분리된 내부 업무 결과다.

## 8. 임시 bin mapping

BE-02의 `bin_mappings` ORM과 실제 DB seed가 아직 연결되지 않았으므로 BE-04 제어 흐름 검증용 in-memory mapping을 사용한다.

```text
fuji + L       → TEST_NORMAL_BIN_1
fuji + M       → TEST_NORMAL_BIN_2
fuji + S       → TEST_NORMAL_BIN_3
yanggwang + L  → TEST_NORMAL_BIN_4
yanggwang + M  → TEST_NORMAL_BIN_5
yanggwang + S  → TEST_NORMAL_BIN_6

재검사          → TEST_REINSPECTION_BIN
```

`TEST_` 접두어를 사용해 운영 bin code가 아님을 명확히 했다. 기존 `bin_mappings` ORM과 Alembic migration은 수정하지 않았다.

## 9. Bin 결정 규칙

```text
COMPLETED
→ predicted_cultivar + predicted_grade
→ 정상 6개 mapping 중 하나

REINSPECTION_REQUIRED
→ prediction 값과 관계없이 TEST_REINSPECTION_BIN
```

저신뢰와 timeout은 품종·품질 prediction이 존재하거나 늦게 도착하더라도 정상 bin을 사용하지 않는다. bin 조건은 `InspectionService`에 직접 나열하지 않고 `determine_target_bin()`으로 분리했다.

## 10. Virtual Control 계약

Virtual Control 요청:

```json
{
  "inspection_id": "inspection-001",
  "target_bin_code": "TEST_NORMAL_BIN_1"
}
```

Virtual Control 응답:

```json
{
  "inspection_id": "inspection-001",
  "target_bin_code": "TEST_NORMAL_BIN_1",
  "control_status": "SUCCEEDED",
  "reason": null
}
```

`ControlExecutionResult`는 최초 요청과 선택적인 대체 요청을 최대 두 건까지 순서대로 보존한다. HTTP 응답에는 전체 시도 내역을 노출하지 않고 마지막 제어 결과만 반환한다.

## 11. MockVirtualControl

`MockVirtualControl`은 실제 장치나 네트워크 없이 다음 결과를 deterministic하게 반환한다.

```text
SUCCEEDED
REJECTED
NO_RESPONSE
FAILED
```

동작 원칙:

- 기본 실행은 매 요청마다 `SUCCEEDED`
- 테스트에서는 결과 목록을 순서대로 주입
- 랜덤 결과 사용 금지
- 요청 순서와 상태 전이 기록
- 설정하지 않은 추가 호출이 발생하면 오류로 탐지

각 호출의 상태 전이는 다음과 같이 기록한다.

```text
NOT_REQUESTED → PENDING → 종료 상태
```

## 12. 정상 bin 거부 대체 정책

명시적인 `REJECTED`에만 재검사 bin 대체 요청을 한 번 수행한다.

```text
정상 bin → SUCCEEDED
         → 종료

정상 bin → REJECTED
         → TEST_REINSPECTION_BIN 1회 요청
         → 종료 상태와 관계없이 추가 요청 없음
```

대체 요청이 성공하면 최종 응답은 재검사 bin과 `SUCCEEDED`를 반환한다. 최초 정상 bin의 `REJECTED` 결과는 내부 `ControlExecutionResult.attempts`에 유지한다.

처음부터 저신뢰 또는 timeout인 검사는 재검사 bin만 한 번 요청하며, 그 요청이 거부·무응답·실패여도 다시 시도하지 않는다.

## 13. NO_RESPONSE·FAILED 처리

두 상태에는 대체 요청을 추가하지 않는다.

- `NO_RESPONSE`: 제어 기능이 응답하지 않은 상태를 명시적으로 유지
- `FAILED`: 제어 처리 실패를 유지
- 실제 시도한 `target_bin_code`와 종료 상태를 함께 반환
- confidence 기반 검사 상태와 제어 상태를 서로 덮어쓰지 않음

이는 정상 bin의 명시적 `REJECTED`에만 대체 요청을 허용하고, 무응답과 일반 실패에는 추가 호출을 하지 않는 팀 정책을 따른다.

## 14. Business deadline과 timeout 판정

`INFERENCE_BUSINESS_DEADLINE_MS`는 HTTP transport timeout이 아니라 정상 판정 여부를 확정하는 업무 제한시간이다.

```text
Inference task 시작
├─ 500ms 이내 완료
│  → 응답 정합성 검증
│  → confidence 판정
│  → 정상 또는 재검사 bin
└─ 500ms 초과
   → timeout 결과 즉시 확정
   → 재검사 bin
   → Virtual Control
```

timeout 판정:

```text
inspection_status = REINSPECTION_REQUIRED
review_required = true
exclude_from_normal_stats = true
decision_reason = INFERENCE_DEADLINE_EXCEEDED
```

timeout에는 유효한 Inference 응답이 없으므로 품종·품질 예측을 임의로 생성하지 않는다.

## 15. Backend 검사 응답

BE-04부터 `InspectionResponse`는 `InferenceResponse`를 그대로 노출하지 않고 Backend 판정과 제어 결과를 표현하는 독립 Schema로 사용한다.

추가된 주요 필드:

- `inspection_status`
- `review_required`
- `exclude_from_normal_stats`
- `decision_reason`
- `target_bin_code`
- `control_status`

정상 응답 예시:

```json
{
  "inspection_id": "inspection-normal",
  "predicted_cultivar": "fuji",
  "cultivar_confidence": 0.9,
  "predicted_grade": "L",
  "quality_confidence": 0.8,
  "inspection_status": "COMPLETED",
  "review_required": false,
  "exclude_from_normal_stats": false,
  "decision_reason": "NORMAL",
  "target_bin_code": "TEST_NORMAL_BIN_1",
  "control_status": "SUCCEEDED"
}
```

timeout 응답에서는 예측·confidence·probabilities·모델 버전·사용 프레임 수가 `null`이며, timeout 판정과 재검사 bin 제어 결과만 반환한다.

## 16. Business deadline과 hard timeout 분리

BE-04 4단계에서는 Inference를 명시적인 `asyncio.Task`로 시작하고 business deadline에는 완료 여부만 확인한다.

```text
Business deadline 500ms
→ HTTP 검사 결과와 bin을 확정하는 시점

Hard timeout 2000ms 초안
→ 진단용 late Inference task의 최대 생존시간
```

business deadline을 초과해도 task를 즉시 취소하지 않는다. `LateResultManager`가 전체 Inference 시작 시점 기준 hard timeout까지 제한적으로 유지하고, 그때까지 완료되지 않으면 취소한다.

connect·read·write·pool timeout은 실제 Inference HTTP Client 단계에서 별도로 구성한다.

## 17. Late-result 정책

늦게 도착한 Inference 결과는 메모리의 `LateInferenceResult`로만 보관한다.

```text
inspection_id
is_late = true
inference_response
```

late-result는 다음 값을 절대 변경하지 않는다.

- `inspection_status`
- `review_required`
- `exclude_from_normal_stats`
- `decision_reason`
- `target_bin_code`
- `control_status`
- 이미 실행한 Virtual Control 결과

고신뢰 또는 저신뢰 응답이 늦게 도착하더라도 confidence 판정을 다시 실행하거나 정상 bin으로 변경하지 않는다. 현재 DB 저장과 late-result 조회 API는 없다.

## 18. Late task 제한과 종료 처리

`LateResultManager`는 동시에 추적할 task 수를 `MAX_LATE_TASKS`로 제한한다.

한도 초과 시:

- 이미 확정된 timeout 응답 유지
- 재검사 bin 제어 유지
- 추가 진단 수집만 포기
- 초과 Inference task 취소
- 대기 queue를 생성하지 않음

FastAPI lifespan 종료 시 남아 있는 watcher와 연결된 Inference task를 취소하고 회수한다. 서버 재시작 시 메모리 late-result와 미완료 task가 유실되는 것은 기존 정책상 허용한다.

## 19. Service 전체 흐름

BE-04 완료 시점의 `InspectionService` 흐름은 다음과 같다.

```text
UploadFile 순서 유지·bytes 변환
→ InferenceRequest
→ Inference task 생성
→ business deadline 확인
   ├─ 완료: 응답 검증·confidence 판정
   └─ 초과: timeout 판정·late task 등록
→ target bin 결정
→ MockVirtualControl
→ 최종 InspectionResponse
```

bin mapping, confidence 판정, 제어 대체 정책과 late task 세부 동작은 각각 작은 모듈로 분리하고 Factory·ABC·복잡한 Strategy 계층은 만들지 않았다.

| 정상 bin `REJECTED` 대체 1회 | 충족 |
| `NO_RESPONSE` 표현 | 충족 |
| `FAILED` 표현 | 충족 |
| 검사 상태와 제어 상태 분리 | 충족 |
| late-result가 확정 판정·bin을 변경하지 않음 | 충족 |
| late task hard timeout·개수 제한 | 충족 |
| 서버 종료 cleanup | 충족 |

무응답과 제어 시도는 현재 HTTP 응답과 메모리 구조에서 확인할 수 있다. 영구 이력 저장은 DB·Repository 후속 작업 범위다.

## 24. 주요 설계 결정

### 검사 상태와 제어 상태를 분리한다

정상 모델 판정 이후 제어가 실패해도 confidence 판정 자체를 덮어쓰지 않는다. `inspection_status`와 `control_status`를 별도로 유지해 원인을 구분한다.

### Business deadline은 transport timeout이 아니다

500ms는 정상 bin 판정을 확정하는 시점이다. 실제 HTTP 연결과 읽기 제한은 실제 Client에서 별도로 적용한다.

### Late-result는 진단 전용이다

timeout 시 물리적 목적지를 먼저 확정하며 늦은 모델 응답이 이를 뒤집지 못하도록 결과 객체와 진단 저장 구조를 분리했다.

### 임시 bin은 운영값이 아니다

현재 상수는 Service 흐름 테스트용이다. Repository가 추가되면 DB `bin_mappings` 조회로 교체한다.

## 25. 의도적으로 구현하지 않은 항목

BE-04에서는 다음 항목을 구현하지 않았다.

- 실제 `httpx.AsyncClient`
- 실제 Inference HTTP 서버 호출
- connect·read·write·pool transport timeout
- `src/inference` 수정
- 실제 DB INSERT·UPDATE와 Repository
- 실제 DB `bin_mappings` 조회와 seed
- late-result DB 저장
- 실제 Virtual Control 장치 통신
- `persistence_status` 상태 전이
- 최종 공통 error code 체계
- Simulator 수정
- 이미지 저장과 장애 이미지 순환 보존
- Kafka·Redis·Celery·별도 broker

## 26. 후속 작업

BE-04 이후 다음 구현 후보는 다음과 같다.

1. 실제 Inference 요청·응답 계약 동기화와 HTTP Client
2. transport timeout과 실제 HTTP late-result 동작 검증
3. Repository를 통한 검사·제어·오류·late-result 저장
4. 임시 bin mapping을 DB 조회로 교체
5. `persistence_status` 전이와 DB 장애 분리
6. BE-05 검사 이력·오늘 통계·필터·CSV API
7. BE-06 이미지 생명주기와 장애 이미지 순환 보존
8. BE-07 Simulator와 장애 시연 토글 연동

운영 hard timeout, late task 수, 실제 bin code와 공통 error code는 관련 통합 단계에서 최종 계약을 확인해야 한다.

## 27. 요약

“CQC Backend에 품종·품질 confidence 정책, 정상 6개와 재검사 bin, Virtual Control과 거부 대체 요청을 구현했습니다. Inference가 500ms를 초과하면 즉시 재검사 bin으로 확정하고, 늦게 도착한 결과는 최대 개수와 hard timeout을 적용한 진단 정보로만 관리하여 기존 판정과 제어 결과를 변경하지 않도록 했습니다. 정상·timeout Uvicorn HTTP 실행과 Backend 테스트 79개로 전체 흐름을 검증했습니다.”
