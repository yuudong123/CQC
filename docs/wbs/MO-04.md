# MO-04 healthcheck·기동 의존성

## 1. 작업 개요

- **WBS 코드:** MO-04
- **작업명:** healthcheck·기동 의존성
- **담당:** 홍유나
- **상태:** 완료 (실제 Backend·Inference 연동 기준)
- **목적:** Docker Compose로 실행되는 각 서비스의 정상 상태를 확인하고, 선행 서비스가 실제로 사용 가능한 상태가 된 뒤 후속 서비스가 기동되도록 구성한다.

기존에는 컨테이너가 단순히 `running` 상태인지 여부만 확인할 수 있었기 때문에, MySQL이나 Backend가 아직 준비되지 않은 상태에서 다음 서비스가 먼저 실행될 가능성이 있었다.

MO-04에서는 `healthcheck`와 `depends_on.condition: service_healthy`를 적용하여 서비스 기동 순서를 제어하고, Jenkins에서도 실제 상태를 검증하도록 구성했다.

---

## 2. 대상 서비스

CQC 프로젝트의 Docker Compose 서비스는 다음 5개이다.

- `mysql`
- `inference`
- `backend`
- `frontend`
- `simulator`

이 중 healthcheck 대상은 다음 3개이다.

- `mysql`
- `inference`
- `backend`

`frontend`와 `simulator`는 현재 별도의 healthcheck를 두지 않고, Backend 정상 기동 이후 실행 상태만 확인한다.

---

## 3. 목표 기동 구조

```text
MySQL ─────┐
           ├→ Backend → Simulator
Inference ─┘          └→ Frontend
```

기동 순서는 다음과 같다.

1. MySQL과 Inference 실행
2. MySQL과 Inference가 `healthy` 상태가 될 때까지 대기
3. Backend 실행
4. Backend가 `healthy` 상태가 될 때까지 대기
5. Frontend와 Simulator 실행

---

## 4. 주요 작업 내용

### 4.1 MySQL healthcheck 추가

MySQL 컨테이너가 단순히 실행 중인지가 아니라 실제 연결 요청을 받을 수 있는 상태인지 확인하도록 설정했다.

```yaml
healthcheck:
  test:
    - CMD-SHELL
    - mysqladmin ping -h localhost -u root -p$$MYSQL_ROOT_PASSWORD --silent
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 30s
```

`MYSQL_ROOT_PASSWORD`는 Compose 치환이 아니라 컨테이너 내부 환경변수를 사용하기 위해 `$$` 형식으로 작성했다.

---

### 4.2 실제 Inference 서비스와 healthcheck 연결

Inference는 `Dockerfile.inference`로 CPU 이미지를 빌드하고 승인된 모델 패키지를 읽어 실제 FastAPI를 실행한다. 모델 디렉터리는 `INFERENCE_MODEL_DIR`로 주입하고 컨테이너 안에서는 읽기 전용으로 마운트한다.

```yaml
command:
  - python
  - -m
  - src.inference.api
  - --model-dir
  - /app/models/approved
  - --device
  - cpu
  - --host
  - 0.0.0.0
  - --port
  - "8001"

healthcheck:
  test:
    - CMD
    - python
    - -c
    - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8001/health', timeout=3)"
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 60s
```

`/health` 응답에서 모델 로딩 완료와 모델 버전을 함께 확인하므로 프로세스 실행만으로는 healthy가 되지 않는다.

---

### 4.3 Backend 기동 의존성 및 healthcheck 추가

Backend는 MySQL과 Inference를 모두 사용하므로 두 서비스가 `healthy` 상태가 된 이후 시작하도록 설정했다.

```yaml
depends_on:
  mysql:
    condition: service_healthy
  inference:
    condition: service_healthy
```

Backend는 `Dockerfile.backend`로 FastAPI 이미지를 빌드하고 `INFERENCE_CLIENT_MODE=http`와 서비스 DNS 주소를 주입한다.

```yaml
healthcheck:
  test:
    - CMD
    - python
    - -c
    - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3)"
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 15s
```

Backend의 `/v1/inspections` 요청은 Inference의 `/v1/predict`로 전달되며, Jenkins는 두 서비스의 HTTP health endpoint를 추가로 확인한다.

---

### 4.4 Frontend / Simulator 기동 의존성 추가

Frontend와 Simulator는 Backend가 정상 상태가 된 이후 실행되도록 구성했다.

```yaml
depends_on:
  backend:
    condition: service_healthy
```

이를 통해 Backend가 준비되지 않은 상태에서 API 요청이나 시뮬레이션 입력이 먼저 발생하는 상황을 방지한다.

---

## 5. Jenkins 검증 추가

Jenkins Pipeline의 `Verify` 단계에서 MO-04 상태를 자동 검증하도록 수정했다.

검증 항목은 다음과 같다.

- MySQL 컨테이너 존재 여부
- Inference 컨테이너 존재 여부
- Backend 컨테이너 존재 여부
- MySQL `healthy` 상태 확인
- Inference `healthy` 상태 확인
- Backend `healthy` 상태 확인
- Inference `/health` HTTP 응답 확인
- Backend `/health` HTTP 응답 확인
- Frontend 실행 상태 확인
- Simulator 실행 상태 확인

healthcheck 완료까지 시간이 걸릴 수 있으므로 일정 시간 동안 반복 확인하도록 구성했다.

---

## 6. 자동 빌드 방식

현재 Jenkins 자동 빌드는 GitHub Webhook이 아닌 **Poll SCM 방식**을 사용한다.

```text
git push
↓
Jenkins Poll SCM이 원격 브랜치 확인
↓
새 커밋 감지
↓
Pipeline 자동 실행
```

작업 브랜치 검증 당시에는 다음과 같이 설정했다.

```text
Branch Specifier: */feat/mlops
Poll SCM: * * * * *
```

즉 Jenkins가 약 1분 간격으로 원격 브랜치 변경 여부를 확인한다.

`dev` 브랜치로 전환할 경우 Jenkins Job의 Branch Specifier를 `*/dev`로 변경하여 사용한다.

## 7. 검증 결과

로컬에서 Jenkins와 같은 Compose 설정을 사용해 다음 항목을 확인했다.

```text
mysql       : healthy
inference   : healthy
backend     : healthy
frontend    : running
simulator   : running
```

추가로 Backend `/v1/inspections`에 12장 합성 JPEG를 전송해 실제 Backend → Inference 흐름을 확인했으며, 응답의 `model_version`은 `cqc-apple-separate12-focal-v2-candidate`였다.

서비스 기동 순서도 다음과 같이 정상 동작했다.

```text
MySQL / Inference
       ↓
     Backend
       ↓
Frontend / Simulator
```

기존 Jenkins 실행 결과:

```text
MO-04 healthcheck verification OK
CQC CI/CD + MO-04 VERIFY SUCCESS
Finished: SUCCESS
```

따라서 Compose healthcheck, 기동 의존성, 실제 Backend → Inference 경로 검증까지 완료했다. 변경된 Jenkinsfile은 다음 Poll SCM 실행부터 같은 모델 경로와 HTTP 검증을 사용한다.

---

## 8. 작업 이유

이번 작업을 적용한 이유는 컨테이너의 `running` 상태만으로는 실제 서비스 준비 여부를 판단할 수 없기 때문이다.

예를 들어 MySQL 컨테이너가 시작되더라도 내부 초기화가 완료되기 전에 Backend가 먼저 접속하면 연결 오류가 발생할 수 있다.

따라서 다음 기준으로 변경했다.

```text
기존
컨테이너 실행 → 다음 서비스 실행

변경
컨테이너 실행
→ healthcheck 통과
→ service_healthy
→ 다음 서비스 실행
```

이를 통해 Docker Compose 기동 과정의 안정성을 높이고, Jenkins에서도 동일한 상태를 자동으로 검증할 수 있도록 했다.
