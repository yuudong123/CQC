# BE-01 FastAPI 기술 스택·검사 요청 API 계약

- WBS 코드: `BE-01`
- 담당: 홍준희
- 역할: 백엔드·DB
- 작업 기간: 2026-09-17 ~ 2026-09-18
- 상태: 완료

## 1. 작업 목적

CQC Backend를 단독 실행할 수 있는 최소 FastAPI 골격을 만들고, Simulator가 전달하는 검사 요청을 Backend가 일관된 형식으로 검증할 수 있도록 HTTP 입력 계약을 구현했다.

이번 작업은 전체 검사 흐름을 한 번에 구현하지 않고 다음 두 단계로 나누어 진행했다.

```text
1단계: FastAPI 실행 골격·Settings·health endpoint
2단계: POST /v1/inspections multipart 요청 계약·validation
```

Service·Inference·DB·Virtual Control은 아직 연결하지 않고 Router가 HTTP 전송 계약만 책임지도록 범위를 제한했다.

## 2. 확정한 Backend 기본 구조

현재 Backend 코드는 다음과 같이 구성했다.

```text
src/api/
├─ __init__.py
├─ main.py
├─ core/
│  ├─ __init__.py
│  └─ config.py
├─ routers/
│  ├─ __init__.py
│  └─ inspections.py
└─ schemas/
   ├─ __init__.py
   └─ inspections.py
```

- `main.py`: FastAPI app factory, Router 등록, 실행 진입점과 health endpoint
- `core/config.py`: 환경변수와 `.env`를 읽는 pydantic-settings 설정
- `routers/inspections.py`: 검사 요청의 multipart 파싱과 HTTP 계약 검증
- `schemas/inspections.py`: 이미지별 metadata Pydantic Schema

향후 구조는 다음 의존 방향으로 확장한다.

```text
Router
  → Service
      ├─ Repository
      ├─ Inference Client
      └─ Virtual Control
```

BE-01에서는 아직 필요하지 않은 Service·Repository·Client·DB·Control 디렉터리와 추상 계층을 만들지 않았다.

## 3. FastAPI 실행 골격

`src/api/main.py`에 `create_app()` app factory와 실행 가능한 `app`을 구성했다. Settings를 인자로 주입할 수 있어 테스트가 실제 `.env`에 의존하지 않는다.

실행 명령:

```powershell
uv venv .venv --python 3.13
uv pip install --python .venv\Scripts\python.exe -r requirements-backend-dev.txt
.\.venv\Scripts\python.exe -m src.api.main
```

기본 실행 주소:

```text
http://127.0.0.1:8000
```

FastAPI 자동 문서:

- Swagger UI: `GET /docs`
- OpenAPI JSON: `GET /openapi.json`

## 4. Settings 구성

`pydantic-settings`를 사용하여 현재 단계에 필요한 실행값과 확정된 요청 제한을 관리한다.

| 환경변수 | 기본값 | 목적 |
|---|---:|---|
| `APP_NAME` | `CQC Backend` | 애플리케이션 이름 |
| `APP_ENV` | `local` | 실행 환경 표시 |
| `APP_HOST` | `0.0.0.0` | bind host |
| `APP_PORT` | `8000` | bind port |
| `INFERENCE_MAX_FILES` | `12` | 검사·Inference 요청 최대 이미지 수 |
| `INFERENCE_MAX_REQUEST_BYTES` | `25165824` | multipart 요청 최대 크기 24MiB |

알 수 없는 `.env` 항목은 무시하므로 현재 MySQL 환경변수가 있어도 Backend 기본 실행에 영향을 주지 않는다. 설정 객체는 `get_settings()`에서 프로세스 범위로 재사용한다.

## 5. Health endpoint

Backend 프로세스의 기본 실행 상태를 확인하는 endpoint를 추가했다.

```http
GET /health
```

응답 예시:

```json
{
  "status": "ok",
  "service": "CQC Backend",
  "environment": "local"
}
```

현재 health는 Backend 프로세스의 liveness만 확인한다. Inference·MySQL 연결을 확인하는 readiness는 해당 기능 구현 후 추가한다.

## 6. 검사 요청 API 계약

Simulator가 대표 이미지를 선택한 뒤 Backend에 전달하는 endpoint를 다음과 같이 구성했다.

```http
POST /v1/inspections
Content-Type: multipart/form-data
```

multipart 필드:

| 필드 | 형식 | 규칙 |
|---|---|---|
| `inspection_id` | text | 비어 있지 않은 검사 식별값 |
| `images` | 반복 file field | PNG·JPEG, 1장 이상 최대 12장 |
| `metadata` | JSON text field | 이미지별 metadata 객체 배열 |

`metadata` 예시:

```json
[
  {
    "view_index": 0,
    "angle_direction": "top",
    "verticality_angle": 0,
    "horizontality_angle": 45
  }
]
```

`images[i]`와 `metadata[i]`는 같은 이미지를 나타낸다. Backend는 Simulator가 선택한 이미지와 metadata를 재선택하거나 재정렬하지 않는다.

## 7. 적용한 validation

Router와 Pydantic Schema에서 다음 입력 검증을 수행한다.

1. `inspection_id`가 비어 있거나 공백뿐인지 확인
2. 이미지 수가 1~12장인지 확인
3. 전체 multipart 요청이 24MiB를 초과하는지 확인
4. 이미지 Content-Type이 `image/png` 또는 `image/jpeg`인지 확인
5. `metadata`가 유효한 JSON 배열인지 확인
6. metadata의 필수 필드와 타입 확인
7. 정의되지 않은 metadata 필드 거부
8. images와 metadata 개수 일치 확인
9. `view_index` 중복 확인
10. `view_index`가 현재 선택 이미지 순서에 따라 `0..N-1`로 연속되는지 확인
11. `angle_direction`이 `top` 또는 `bottom`인지 확인

두 angle 필드는 현재 정수 여부만 검사한다. 최종 허용 범위는 팀 계약이 확정된 뒤 적용한다.

## 8. HTTP 오류 초안

최종 error code 체계는 확정하지 않고 FastAPI 기본 `detail` 응답을 사용한다.

| HTTP | 현재 적용 상황 |
|---:|---|
| `413` | 이미지 12장 또는 설정된 요청 크기 초과 |
| `415` | PNG·JPEG 외 Content-Type |
| `422` | 필수 필드, JSON, metadata 개수·값·순서 검증 실패 |

상태 Enum 문자열과 공통 error response Schema는 후속 계약에서 확정한다.

※ 위 상태 코드는 BE-01 입력 검증용 임시 계약이며,
   최종 error code 및 공통 오류 응답 Schema는 후속 단계에서 확정한다.

## 9. BE-01 임시 검증 응답

아직 Service와 판정 흐름이 없으므로 유효한 요청에는 계약 검증 결과만 반환한다.

```json
{
  "inspection_id": "inspection-001",
  "image_count": 2,
  "validation": "passed"
}
```

이 응답은 최종 검사 상태나 판정 결과가 아니다. 후속 단계에서 Router가 Service를 호출하게 되면 실제 검사 응답 Schema로 교체한다.

## 10. 주요 설계 결정과 이유

### metadata는 JSON text field로 받는다

네 metadata 값을 각각 병렬 form 배열로 보내면 필드 누락이나 순서 불일치를 확인하기 어렵다. 하나의 JSON 배열로 묶어 Pydantic으로 검증하면 이미지 한 장에 대응하는 값을 명확하게 관리할 수 있다.

### Router는 전송 계약만 검증한다

현재 Router에는 confidence, bin, 상태 전이와 같은 비즈니스 정책을 넣지 않았다. 이후 Service가 추가되어도 multipart 파싱과 요청 검증 부분만 유지할 수 있도록 책임을 제한했다.

### 이미지 순서를 변경하지 않는다

대표 이미지 선택과 순서는 Simulator 책임이다. Backend는 `view_index`와 배열 위치의 대응만 확인하며 이미지를 다시 선택·정렬하지 않는다.

### 요청 크기 제한은 설정에서 관리한다

확정값 24MiB를 Settings 기본값으로 두고 `Content-Length`와 확인 가능한 payload 크기를 검사한다. 현재 검증은 FastAPI가 multipart를 파싱한 뒤 Router에서 수행된다. 파싱 전 자원 보호는 배포 proxy 또는 ASGI 수신 제한에서 같은 값으로 추가해야 한다.

## 11. 수정·생성 파일

- `src/api/main.py`: FastAPI app factory, health endpoint, 검사 Router 등록
- `src/api/core/config.py`: 실행 설정과 12장·24MiB 제한
- `src/api/routers/inspections.py`: multipart 파싱과 요청 validation
- `src/api/schemas/inspections.py`: 이미지 metadata Schema
- `requirements-backend.txt`: Backend 실행 의존성
- `requirements-backend-dev.txt`: pytest·TestClient 개발 의존성
- `tests/api/test_config.py`: 환경변수 Settings 테스트
- `tests/api/test_health.py`: health와 OpenAPI 경로 테스트
- `tests/api/test_inspections.py`: 검사 요청 계약과 오류 테스트

Backend 코드의 주석과 docstring은 프로젝트 담당자가 빠르게 이해할 수 있도록 한글로 작성한다.

## 12. 검증 결과

테스트 명령:

```powershell
.\.venv\Scripts\python.exe -m pytest tests\api -q -p no:cacheprovider
```

결과:

```text

```

검증한 주요 항목:

- Settings 환경변수 로딩
- Backend app factory와 health 응답
- OpenAPI에 `/health`, `/v1/inspections` 노출
- PNG·JPEG 요청 성공
- 1장과 12장 경계값
- 13장 요청 거부
- images와 metadata 개수 불일치 거부
- 중복·역순 `view_index` 거부
- 잘못된 `angle_direction` 거부
- 잘못된 metadata JSON 거부
- 지원하지 않는 Content-Type 거부
- 설정 크기를 초과한 요청 거부

경고 2건은 설치된 FastAPI·Starlette TestClient 내부 deprecation 경고이며 테스트 실패는 아니다.

## 13. 의도적으로 구현하지 않은 항목

BE-01에서는 다음 항목을 구현하지 않았다.

- 검사 Service와 실제 판정 응답
- Mock 또는 실제 Inference Client
- Inference HTTP 호출
- SQLAlchemy·MySQL·Repository·Alembic
- Virtual Control과 bin mapping
- 검사·제어·저장 상태 전이
- 최종 상태 Enum 문자열과 error code
- confidence 정책
- timeout과 late-result 처리
- 파일 디코딩과 손상 이미지 판정

`inspection_status`, `control_status`, `persistence_status`, `error_code`를 논리적으로 분리한다는 원칙은 유지하되 구체적인 Enum과 전이는 후속 계약에서 확정한다.

## 14. 다른 파트에 전달할 계약

- Simulator는 각도 기준 대표 이미지를 최대 12장 선택한다.
- Backend는 `inspection_id`, 반복 `images`, JSON text `metadata`를 받는다.
- `images[i]`와 `metadata[i]`가 대응한다.
- `view_index`는 현재 선택된 이미지 순서 기준 `0..N-1`이다.
- Backend는 이미지와 metadata를 재선택하거나 재정렬하지 않는다.
- 요청 이미지는 PNG·JPEG이며 전체 multipart 기준은 24MiB다.
- Backend의 현재 검사 응답은 전송 계약 검증용 임시 응답이다.
- 실제 Inference 연동 전 `inspection_id`, metadata와 `used_frame_count` 계약을 Inference OpenAPI에도 반영해야 한다.
