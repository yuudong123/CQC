# [DM-08] 신뢰도·병렬 처리 기준

## 준비 완료

- `src/training/export_predictions.py`: 최종 Test를 제외한 validation fold 그룹별 확률·정답 CSV 생성
- `src/training/thresholds.py`: 품종·품질 최소 정확도 요구를 입력받아 두 임계값 조합 중 최대 coverage 후보 선정
- `src/training/benchmark.py`: CPU·GPU 평균·최대·p95 추론시간 측정
- `src/training/benchmark_concurrency.py`: 동시 처리 수별 p95·처리량, 500ms·초당 2건 충족 여부 측정

## 결정 원칙

- 품종과 품질 임계값을 별도로 둔다.
- 두 신뢰도가 모두 기준 이상일 때만 정상 후보로 전달한다.
- 임계값은 최종 Test가 아니라 5-fold validation 예측으로 정한다.
- 최소 정확도 요구값은 모델 파트가 임의로 정하지 않고 백엔드·서비스 요구사항으로 입력받는다.
- 병렬 처리 수는 i7-4790에서 500ms 제한과 초당 그룹 2개를 함께 만족하는 실제 측정값으로 정한다.

## 임시 후보 검증 결과

`separate/12장`의 5개 fold, 총 152개 validation 그룹 예측을 내보냈다.

| 공통 임계값 | coverage | 품종 정확도 | 품질 정확도 |
|---:|---:|---:|---:|
| 0.50 | 0.9868 | 0.9867 | 0.9800 |
| 0.60 | 0.9605 | 0.9863 | 0.9795 |
| 0.70 | 0.9145 | 0.9856 | 0.9784 |
| 0.80 | 0.8947 | 0.9926 | 0.9779 |
| 0.90 | 0.8092 | 1.0000 | 0.9756 |
| 0.95 | 0.7105 | 1.0000 | 0.9815 |

품질 오분류 중 일부가 높은 신뢰도를 보여 임계값 상승이 품질 정확도를 단조롭게 개선하지 않는다. 서비스가 요구하는 최소 품종·품질 정확도를 먼저 받아 두 임계값을 별도로 결정해야 한다.

i7-14700F, PyTorch thread 1 예비 측정에서 동시 처리 1·2·4의 p95는 각각 145.1ms·136.6ms·166.3ms였고 처리량은 초당 9.49·14.99·25.68건이었다. 모두 500ms와 초당 2건을 만족하지만 목표 i7-4790 결과로 대체해야 한다.

## 확정 설정 (v1 검증 예측 기준)

> 2026-09-29 확인: 아래 0.50은 v1 `separate`·12장의 fold별 best 체크포인트 예측(검증 fold로 epoch를 고른 낙관적 추정)으로 정했다. 현재 서비스 모델인 v2 후보(Focal·4 epoch)는 확률 분포가 달라 이 근거가 적용되지 않는다. 기존 Test 27개 회귀 진단에서 v2 품질 신뢰도는 평균 0.715·최저 0.527로, v1(평균 0.939)과 반대로 과소 확신 경향이다. v2 설정의 5-fold OOF 예측으로 보정·임계값을 다시 정하기 전까지 0.50은 운영 기본값으로만 사용한다.


- MVP 자동 처리 구간 최소 정확도: 품종 98%, 품질 98%
- 품종 신뢰도 기준: 0.50
- 품질 신뢰도 기준: 0.50
- validation 자동 처리: 150/152그룹, coverage 98.68%
- 자동 처리 구간 정확도: 품종 98.67%, 품질 98.00%
- 운영 기본 동시 처리 수: 1

목표 i7-4790 장비는 학원 Jenkins 서버 `192.168.133.106`이다. 실제 성능 수용시험 결과는 아직 없으며, Docker에서 실행 가능한 데이터·모델 파트의 시험 코드와 MLOps 인계 절차는 [i7-4790 수용시험](reference/DM/i7-4790-acceptance.md)에 정리했다. i7-14700F 결과는 기능·예비 성능 근거로 유지한다.

최종 학습 체크포인트의 i7-14700F 100회 재측정에서 동시 처리 1·2·4의 p95는 각각 113.6ms·151.2ms·182.1ms, 처리량은 초당 9.31·14.46·23.41건이었다. 운영 기본값 1은 유지한다.

최종 Test의 품질 오분류 6건 중 4건은 신뢰도 0.96 이상이었다. 임계값만 높여 품질 승인 실패를 해결할 수 없으며, Test 결과를 이용한 임계값 재선정은 하지 않는다.

## 2026-09-30: v2 신뢰도 보정 파이프라인

위 0.50은 v1 근거라 v2에 적용할 수 없다. v2 설정 그대로 5-fold OOF 예측을 다시 만들어 보정하는 도구를 추가했다. **실행(집 PC GPU)과 임계값 결정은 남아 있다.**

### 절차

1. `scripts/remote/run_v2_calibration.ps1` (집 PC 저장소 루트, RTX 4070 기준 15~30분)
   - fold 0~4를 v2 설정(separate·12장·Focal γ2·lr 3e-4·dropout 0.4·wd 5e-4·batch 2·seed 42)으로 **고정 4 epoch** 학습하고 `--save-last`로 마지막 체크포인트를 쓴다. v2 최종 학습과 같은 epoch이며 검증 fold로 epoch를 고르지 않으므로 v1 임계값의 낙관 편향이 없다.
   - fold별 검증 사과 logits를 `export_predictions`로 `oof-fold-N.csv`에 쓴다(`cultivar_logit_*`, `quality_logit_*`, `checkpoint_epoch` 열 추가).
   - `python -m src.training.calibration fit`이 152개 OOF로 품종·품질 temperature를 NLL 최소화로 구하고, 보정 전후 정확도·NLL·Brier·ECE(10구간)·신뢰도 구간표와 임계값 표를 만든다. Test는 읽지 않는다(`test_used: false`).
2. 결과 `calibration.json`, `threshold-table.csv`를 팀이 보고 임계값을 정한다. 표 열: 두 임계값, 자동 처리 비율(coverage), 재검사 비율, 자동 처리 구간 품종·품질 정확도·품질 Macro F1, 상위 등급→보통 오분류, 보통→상위 오분류, L↔S 극단 오분류.
   - 기본 추천 제약은 자동 처리 품질 정확도 0.95 이상·재검사 30% 이하 중 coverage 최대. 제약값은 스크립트 인자로 바꾼다. 추천은 참고값이며 확정은 팀이 한다.
   - 비교 기준 `reference_at_current_thresholds`에 현재 0.50/0.50의 값을 함께 기록한다.
3. `python -m src.training.calibration apply --calibration … --package … --model-version … [--output-package …]`
   - 체크포인트 SHA-256을 확인하고 manifest에 temperature, `threshold_status: calibrated_dev_oof`, 새 `model_version`, 보정 출처를 쓴다. 가중치는 바꾸지 않는다. 같은 폴더에 쓰면 원래 manifest를 `model.json.before-calibration`으로 백업한다.
   - `approval_status`는 `unverified_candidate` 그대로 둔다. 보정은 승인이 아니다.
4. 확정 임계값은 Backend 설정 `CULTIVAR_CONFIDENCE_THRESHOLD`·`QUALITY_CONFIDENCE_THRESHOLD`(기본 0.50)로 반영한다(MO·BE 협의).

### 검증

- 합성 과신·과소 확신 데이터에서 temperature 복원, 보정 후 ECE·NLL 감소, 정확도 불변, 임계값 표 단조성, 추천 제약, CLI fit→apply, 중복 사과·logit 없는 CSV 거부 시험 6개 통과.
- 실제 v2 패키지 복사본에 `apply` 후 Predictor 로딩·예측 확인: 체크포인트 SHA 유지, 예측 등급 불변, 신뢰도만 변경. 원본 패키지는 변경하지 않았다.
