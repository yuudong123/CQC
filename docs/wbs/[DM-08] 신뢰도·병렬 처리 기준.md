# [DM-08] 신뢰도·병렬 처리 기준

## 준비 완료

- `src/training/export_predictions.py`: 최종 Test를 제외한 validation fold 그룹별 확률·정답 CSV 생성
- `src/training/thresholds.py`: 품종·품질 최소 정확도 요구를 입력받아 두 임계값 조합 중 최대 coverage 후보 선정
- `src/training/benchmark.py`: CPU·GPU 평균·최대·p95 추론시간 측정
- `src/training/benchmark_concurrency.py`: 동시 처리 수별 p95·처리량, 500ms·초당 2건 충족 여부 측정

## 결정 원칙

- 품종과 품질 임계값을 별도로 둔다.
- 두 신뢰도가 모두 기준 이상일 때만 정상 후보로 전달한다.
- 임계값은 최종 Test가 아니라 5-fold validation 예측으로 정한다.
- 최소 정확도 요구값은 모델 파트가 임의로 정하지 않고 백엔드·서비스 요구사항으로 입력받는다.
- 병렬 처리 수는 서버컴에서 라인 간격 안에 끝나는 실제 측정값으로 정한다. 처음에는 500ms 제한과 초당 그룹 2개였으나 입력 간격 2000ms(09-30)와 제한시간 = 라인 간격(#87, 10-05)으로 바뀌었다. 아래 500ms 열은 당시 기준의 기록이다.

- 품질 신뢰도 기준: 0.50

목표 서버컴 장비는 학원 Jenkins 서버 `192.168.133.106`이다. 실제 성능 수용시험 결과는 아직 없으며, Docker에서 실행 가능한 데이터·모델 파트의 시험 코드와 MLOps 인계 절차는 [서버컴 수용시험](reference/DM/server-acceptance.md)에 정리했다. i7-14700F 결과는 기능·예비 성능 근거로 유지한다.

## 2026-09-30: v2 신뢰도 보정 파이프라인

위 0.50은 v1 근거라 v2에 적용할 수 없다. v2 설정 그대로 5-fold OOF 예측을 다시 만들어 보정하는 도구를 추가했다. **실행(집 PC GPU)과 임계값 결정은 남아 있다.**

### 절차

1. `scripts/remote/run_v2_calibration.ps1` (집 PC 저장소 루트, RTX 4070 기준 15~30분)
   - fold 0~4를 v2 설정(separate·12장·Focal γ2·lr 3e-4·dropout 0.4·wd 5e-4·batch 2·seed 42)으로 **고정 4 epoch** 학습하고 `--save-last`로 마지막 체크포인트를 쓴다. v2 최종 학습과 같은 epoch이며 검증 fold로 epoch를 고르지 않으므로 v1 임계값의 낙관 편향이 없다.
   - fold별 검증 사과 logits를 `export_predictions`로 `oof-fold-N.csv`에 쓴다(`cultivar_logit_*`, `quality_logit_*`, `checkpoint_epoch` 열 추가).
   - `python -m src.training.calibration fit`이 152개 OOF로 품종·품질 temperature를 NLL 최소화로 구하고, 보정 전후 정확도·NLL·Brier·ECE(10구간)·신뢰도 구간표와 임계값 표를 만든다. Test는 읽지 않는다(`test_used: false`).
2. 결과 `calibration.json`, `threshold-table.csv`를 팀이 보고 임계값을 정한다. 표 열: 두 임계값, 자동 처리 비율(coverage), 재검사 비율, 자동 처리 구간 품종·품질 정확도·품질 Macro F1, 상위 등급→보통 오분류, 보통→상위 오분류, L↔S 극단 오분류.
   - 기본 추천 제약은 자동 처리 품질 정확도 0.95 이상·재검사 30% 이하 중 coverage 최대. 제약값은 스크립트 인자로 바꾼다. 추천은 참고값이며 확정은 팀이 한다.
   - 비교 기준 `reference_at_current_thresholds`에 현재 0.50/0.50의 값을 함께 기록한다.
3. `python -m src.training.calibration apply --calibration … --package … --model-version … [--output-package …]`
   - 체크포인트 SHA-256을 확인하고 manifest에 temperature, `threshold_status: calibrated_dev_oof`, 새 `model_version`, 보정 출처를 쓴다. 가중치는 바꾸지 않는다. 같은 폴더에 쓰면 원래 manifest를 `model.json.before-calibration`으로 백업한다.
   - `approval_status`는 `unverified_candidate` 그대로 둔다. 보정은 승인이 아니다.
4. 확정 임계값은 Backend 설정 `CULTIVAR_CONFIDENCE_THRESHOLD`·`QUALITY_CONFIDENCE_THRESHOLD`(기본 0.50)로 반영한다(MO·BE 협의).

### 검증

- 합성 과신·과소 확신 데이터에서 temperature 복원, 보정 후 ECE·NLL 감소, 정확도 불변, 임계값 표 단조성, 추천 제약, CLI fit→apply, 중복 사과·logit 없는 CSV 거부 시험 6개 통과.
- 실제 v2 패키지 복사본에 `apply` 후 Predictor 로딩·예측 확인: 체크포인트 SHA 유지, 예측 등급 불변, 신뢰도만 변경. 원본 패키지는 변경하지 않았다.

| head | temperature | ECE 전→후 | NLL 전→후 | 정확도 |

temperature < 1로 과소 확신이 예상대로 보정됐다. 보정은 가중치와 예측 등급을 바꾸지 않고 신뢰도만 바꾼다.

**결정: 품종 0.50, 품질 0.60.** 재검사 30% 이하에서 개발 OOF 자동 처리 품질 정확도가 가장 높은 조합이다(0.59와 같은 결과). 기본 추천 제약(품질 정확도 0.95 이상·재검사 30% 이하)을 동시에 만족하는 조합은 없었다. 0.95 제약은 적용하지 않고, 정확도 향상 근거로 아래 비교를 공개한다.

| 개발 OOF 152그룹 | 자동 처리 | 재검사 | 자동 구간 품질 정확도 | 품종 정확도 | 보통→상위 오분류 | L↔S |
|---|---:|---:|---:|---:|---:|---:|
| 임계값 없음 | 152 | 0.0% | 88.8% | 98.0% | 8 | 1 |
| 현재 운영: 보정 전 0.50/0.50 | 116 | 23.7% | 92.2% | 98.3% | 4 | 1 |
| **보정 후 0.50/0.60 (채택)** | 127 | 16.4% | **92.9%** | 98.4% | 4 | 1 |
| 보정 후 0.50/0.75 | 109 | 28.3% | 92.7% | 100% | 3 | 0 |
| 보정 후 0.50/0.85 | 91 | 40.1% | 94.5% | 100% | 1 | 0 |

- 현재 운영값 대비 **재검사 23.7% → 16.4%(7.3%p 감소)와 자동 처리 품질 정확도 92.2% → 92.9%를 함께 개선**했다. 보정 전에는 과소 확신 때문에 맞는 사과도 재검사로 빠졌다.
- 정확도 향상은 저신뢰 사과를 재검사로 보내 얻은 **자동 처리 구간** 정확도다. 전체 정확도(88.8%)는 그대로다.
- `calibration fit`이 기록하던 `reference_at_current_thresholds`는 보정 후 확률로 계산돼 현재 운영값과 달랐다(141건·90.1%). 보정 전 확률로 계산하도록 고치고 원본 JSON도 다시 계산했다.
- 이 OOF 정확도는 v1 기록의 98%(검증 fold로 epoch를 고른 낙관 추정)와 직접 비교하지 않는다. v2는 고정 4 epoch라 낙관 편향이 없다.
- 품질 오류를 더 줄이려면 재검사가 빠르게 늘어난다(0.85에서 40%). 발표에서는 0.60을 기본으로, 0.75를 "품종 오류 0·L↔S 0" 대안으로 설명할 수 있다.

### Simulator 운영 경로 처리량과 입력 간격 (2026-09-30 17시)

BE-07 Simulator가 학원 서버에 배포된 뒤(dev `bbc5b7c`, 입력 간격 500ms·동시 처리 1) 운영 중인 결과 200건을 관제 이력 API로 읽었다. 설정은 바꾸지 않았다. 원본: [Simulator 처리량](results/server-simulator-throughput-20260930.json).

| 항목 | 값 |
|---|---|
| 실제 처리량 | 초당 0.63건 (5분 19초, 200건) |
| 요청 시작 간격 | p10 1.23초, 중앙값 1.39초, p90 1.80초 |
| Backend→Inference 500ms 초과 | 안정 구간 3%(6/200), 배포 직후 1분 30초는 18%(14/78) |
| 모델 계산 | 중앙값 150ms, p95 196ms |

- Simulator→Backend→Inference 한 건 왕복이 약 1.4초다. 모델 계산(150ms)과 추론 함수 전체(p95 309ms)를 빼면 나머지 약 1.1초는 13.8MiB 사진을 두 번 넘기고 multipart를 두 번 해석하며 DB에 저장하는 구간이다.
- 500ms 입력 간격은 처리 주기보다 짧아 Simulator가 앞 요청이 끝나자마자 다음 요청을 보낸다. 설정(초당 2건)과 실제(0.63건)가 달라진다.
- **입력 간격을 2000ms로 조정한다.** 처리 주기 p90(1.8초)보다 길게 두어 요청이 밀리지 않고 설정한 속도가 실제 처리 속도가 되게 한다. 시연 처리량은 초당 0.5건이다. 반영: [PR #33](https://github.com/yuudong123/CQC/pull/33), `SIMULATOR_INTERVAL_MS` 환경변수로 바꿀 수 있다.
- 초당 2건(요구사항 FR-01·NFR-19)은 서버컴에서 현재 구조로 달성하지 못한다. 동시 처리 2는 추론 함수 안에서도 p95 528ms로 느려지므로(위 표) 처리량 해결책으로 쓰지 않는다.
- 병합·배포 후 처리량이 초당 약 0.5건으로 일정한지, 시간 초과가 3%보다 줄어드는지 확인한다. 줄지 않으면 원인은 입력 속도가 아니라 Backend→Inference 구간 자체다.
