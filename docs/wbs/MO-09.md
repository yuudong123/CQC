# MO-09 최종 수용시험 자동화

기준: [Issue #71](https://github.com/yuudong123/CQC/issues/71), [QA 케이스](reference/ALL/qa-test-cases.md), [ALL-04](https://github.com/yuudong123/CQC/issues/65).

[Issue #103](https://github.com/yuudong123/CQC/issues/103)의 QA 초안·분담을 반영했다. 자동화가 다른 파트의 케이스를 실행해도 QA 문서 6.1의 담당은 유지한다. 기준·분담·E2 진행 방식은 10-08 회의에서 확정하며, 기존 실행의 확인 범위와 남은 항목은 QA 문서 6.5에 기록했다.

## 시연 직전 1회 실행

1. dev 배포와 Jenkins 빌드가 끝난 뒤 10분 이상 기다리고, Simulator가 정상 재생 중인지 확인한다. 측정 중 dev에 푸시하지 않는다.
2. 저장소 루트에서 실행한다. 기본 주소는 이 컴퓨터의 `127.0.0.1:8000`(Backend), `127.0.0.1:8001`(Inference)이다. 다른 호스트라면 두 URL을 명시한다.

```powershell
python scripts/qa/run_mo09_acceptance.py --mode live --observe-100 --stable-minutes 10 --actor "홍유나"
```

3. 출력 끝에 표시된 고유 실행 폴더의 `all04-rows.md`와 원본 `results.json`·`run.json`을 보존한다. 출력은 QA 문서 6.4와 같은 **7열(케이스 / 담당 / 결과 / 실행자 / 일시 / 커밋·모델 / 비고)**이고 담당은 QA 기록표에서 가져온다. `정상 100건`을 실행하면 `normal-100.json`에 표본과 중앙값·p90·최대 간격을 남긴다.

전체 기대값을 검사한 항목만 `통과`로 옮긴다. 부분 검증·자동 회귀·합의 전 제안 기준은 관찰이 통과해도 기록표에는 `차단`으로 출력하며, 비고에 `관찰=통과`와 확인 범위를 남긴다. JSON의 `status`는 자동 검사 결과, `record_status`는 기록표 결과다. 실패는 부분 검증이어도 `실패`로 남긴다. 프로세스 종료 코드는 0(선택한 자동 검사 통과), 1(실패), 2(환경·옵션 등으로 자동 검사 미실행)이며, 0이 ALL-04 전체 수용 통과를 뜻하지 않는다.

## 실행 범위

| 방식 | 자동 확인 | 운영 영향 |
|---|---|---|
| `--mode live` | QA-DEP-01·02·03·04, QA-SIM-01 현재 상태, QA-OPS-10·13 부분 검증, QA-SIM-02·13(정상 100건 옵션) | GET 및 Docker 조회만 한다. 컨테이너 조회는 로컬 `cqc-cicd` 프로젝트 기준이다. 정상 100건은 새 검사 기록을 관찰할 뿐 입력을 추가하지 않는다. |
| `--mode isolated` | 기존 pytest로 추론 시간 초과·DB 오류 시 LKG·제어 거부·Simulator 장애 6종·장애 이미지 순환을 재검증한다. 별도 시험 DB가 지정되면 이력 순환 삭제(시험용 5/2 한도)와 CSV 통합 시험도 실행한다. | 운영 컨테이너를 중단하지 않는다. `CQC_TEST_DATABASE_URL`과 `CQC_RETENTION_TEST_DATABASE_URL`은 **운영 DB가 아닌 시험 전용 DB**를 가리켜야 한다. 로컬 호스트의 `_test`·`_retention` 접미사 DB만 허용한다. |
| E2 격리 Compose | `scripts/qa/run_mo09_e2_faults.py`로 QA-SIM-06의 장애 6종을 실제 서비스에 `NEXT`로 주입하고 장애 행·다음 정상 행을 확인한다. | 별도 Compose 프로젝트·DB·루프백 포트 18000/18001을 사용한다. 외부 이미지 데이터 볼륨은 읽기 전용이다. 실행 뒤 프로젝트와 전용 볼륨을 제거한다. |

```powershell
python scripts/qa/run_mo09_acceptance.py --mode isolated --actor "홍유나"
```

시험 전용 MySQL이 준비되지 않았다면 아래 명령을 쓴다. 이 명령은 localhost에 임시 MySQL을 띄우고 두 시험 DB에 migration을 적용한 뒤 시험 종료 시 컨테이너를 제거한다.

```powershell
python scripts/qa/run_mo09_acceptance.py --mode isolated --disposable-mysql --actor "홍유나"
```

pytest 출력은 UTF-8로 읽고 항목별 `*-pytest.txt`에 보존한다. Windows에서 QA-IMG-06이 알려진 KI-8(`WinError 5`)로 실패하면 Windows 원문을 `qa-img-06-windows.txt`에 남기고 임시 Linux 컨테이너에서 같은 최신 소스를 다시 시험한다. 로컬 `cqc-cicd-backend:latest`를 의존성 이미지로 쓰되 저장소를 읽기 전용으로 연결하고 소스·시험 파일을 컨테이너 내부 `/tmp`로 복사한다. 운영 DB·호스트 파일에는 쓰지 않는다. 해당 이미지가 없으면 `--linux-test-image <Backend 의존성이 설치된 이미지>`를 지정한다. Linux에서도 실패하면 실패로 기록한다.

`--mode all`은 두 방식을 순서대로 실행한다. `--observe-100`이 없으면 QA-SIM-13은 `차단`으로 출력한다. `--stable-minutes 10`은 최근 컨테이너 교체 후 10분이 지날 때까지 기다린다. 정상 100건의 기준(간격 2.0±0.1초, 최대 공백 4초 미만, 시간 초과·추론 오류 0, 재검사 20% 이하, 약 0.5건/초)은 QA 문서의 **제안값**이므로 ALL-04 최종 판정 전에 팀이 기준을 확정해야 한다.

```powershell
python scripts/qa/run_mo09_acceptance.py --mode all --observe-100 --stable-minutes 10 --disposable-mysql --actor "홍유나"
```

QA-SIM-02는 같은 100건의 p90 ≤ 2.2초도 검사한다. QA-SIM-13 제안 기준과 별도 결과 행으로 남긴다. `--mode all`의 격리 회귀에는 실행한 로컬 HEAD를 기록하며, 운영 이미지의 미확인 SHA를 로컬 코드 SHA로 대체하지 않는다.

## E2 장애 주입 실행

먼저 독립 `cqc-mo09-e2-<회차>` 프로젝트의 MySQL·Inference·Backend·Simulator를 준비한다. Backend는 `127.0.0.1:18000`, Inference는 `127.0.0.1:18001`에 노출하고 DB는 해당 프로젝트의 `mysql`을 사용한다. 시험 전용 DB 비밀번호·Simulator 토큰을 지정한다. `scripts/qa/compose.mo09.yaml`은 `cqc-cicd-*:latest` 이미지를 재사용하며 `--no-build`로 기동하므로, 체크아웃 코드의 새 빌드를 검증한다는 뜻은 아니다. 재사용한 이미지 ID와 미확인 배포 SHA는 `run.json`에 남는다.

로컬 `cqc-cicd` 이미지와 외부 데이터 볼륨이 준비된 컴퓨터에서 아래를 실행한다. 운영 정상 100건 측정과 동시에 실행하지 않는다.

```powershell
$mo09Run = Get-Date -Format 'yyyyMMdd-HHmmss'
$mo09Project = "cqc-mo09-e2-$mo09Run"
$mo09Compose = @('-p', $mo09Project, '-f', 'compose.yaml', '-f', 'scripts/qa/compose.mo09.yaml')
$env:MYSQL_ROOT_PASSWORD = [Guid]::NewGuid().ToString('N')
$env:MYSQL_DATABASE = 'cqc'
$env:MYSQL_USER = 'cqc'
$env:MYSQL_PASSWORD = [Guid]::NewGuid().ToString('N')
$env:SIMULATOR_FAULT_TOKEN = [Guid]::NewGuid().ToString('N')
$env:DATABASE_URL = "mysql+pymysql://cqc:$($env:MYSQL_PASSWORD)@mysql:3306/cqc"
$env:BACKEND_PORT = '127.0.0.1:18000'
$env:INFERENCE_PORT = '127.0.0.1:18001'
try {
    docker compose @mo09Compose up -d --no-build --wait --wait-timeout 300 mysql inference backend simulator
    if ($LASTEXITCODE -ne 0) { throw 'E2 기동 실패' }
    python scripts/qa/run_mo09_e2_faults.py --project $mo09Project --actor "홍유나" --output "outputs/mo09-e2-$mo09Run"
    if ($LASTEXITCODE -ne 0) { throw 'E2 장애 관찰 실패: 결과 파일 확인' }
} finally {
    docker compose @mo09Compose down -v
}
```

시험용 변수는 현재 PowerShell 세션에 적용된다. E1 명령을 실행할 때는 새 터미널을 사용한다.

이 스크립트는 프로젝트 이름·Backend 루프백 포트·프로젝트 전용 MySQL을 확인한 뒤에만 주입한다. 관찰 원문은 `fault-evidence.json`, 7열 기록표는 `all04-rows.md`다. 추론 장애 이미지 12장, 장애별 제어 시도 횟수, 후속 정상 저장까지 검사하지만 전체 통계와 MySQL·Inference 중단 복구는 별도 확인이므로 기록표는 부분 검증 `차단`으로 남긴다. 실패한 경우에도 원문을 보존하고, 종료 후 같은 프로젝트 옵션으로 `docker compose down -v`를 실행해 시험 컨테이너·전용 볼륨만 정리한다.

## 자동화 밖의 공동 확인

- MySQL·Inference 중단과 복구, Simulator 재시작 위치 복구는 기존 단위 시험 통과나 QA-SIM-06 장애 주입 결과만으로 완료 처리하지 않는다. 격리 환경에서 QA-SIM-08·09 및 QA-INS-10~15 절차를 실행하고 결과 행을 별도 기록한다.
- 이력 순환 삭제 회귀 시험은 한도 5건·삭제 2건으로 알고리즘을 확인한다. 실제 86,400/8,640건 운영 DB 시험의 대체 증거로 쓰지 않는다.
- 격리 자동 시험은 비고·JSON `coverage`에 `자동 회귀`를 명시한다. 같은 번호의 E2 실환경 수용시험 통과로 옮겨 적지 않는다.
- 웹 무스크롤 화면과 장시간 브라우저 메모리, 모델 예측의 사진별 정확도는 화면·모델 담당 확인이 필요하다.
- 현재 배포 컨테이너에 Git SHA 레이블이 없으면 결과의 `커밋·모델`에는 `deployed SHA unverified`로 출력한다. Jenkins 성공 SHA를 현재 배포 SHA로 단정하지 않는다.
- QA 문서의 QA-DEP-01에 남아 있던 과거 8개 서비스·placeholder 기대값을 현재 Compose의 7개 서비스로 갱신했다. 스크립트는 7개 상태와 재시작 정책을 검사한다.

ALL-04 최종 기준 합의 전의 예비 결과다.

- `outputs/mo09-isolated-disposable-verified/`: `--disposable-mysql` 한 줄 실행도 8개 자동 회귀 모두 통과. 스크립트가 임시 DB 생성·migration·시험·컨테이너 제거를 수행했고, 종료 후 임시 MySQL 컨테이너가 남지 않은 것을 확인했다.
- `outputs/mo09-e2-faults-20261006/`: 별도 `cqc-mo09-e2-20261006` Compose 프로젝트에서 QA-SIM-06 장애 6종(`INFERENCE_TIMEOUT`, `INFERENCE_ERROR`, `DB_ERROR`, `CONTROL_REJECTED`, `CONTROL_NO_RESPONSE`, `CONTROL_FAILED`)을 실제 주입해 장애 상태·설정 자동 해제·후속 정상 저장을 확인했다. 추론 장애 이미지 12장, 제어 재시도 횟수·성공 bin 통계는 직접 확인하지 않아 QA-SIM-06 전체 통과로 옮기지 않는다. `DB_ERROR`는 설정 revision 자동 해제, 장애 행 부재, 뒤따른 정상 저장을 확인했다. DB 오류가 발생한 검사 ID는 이력에 남지 않으므로 그 ID 자체는 확인하지 못한다. 상세 행은 `all04-rows.md`, 원자료는 `results.json`에 있다. 문서와 함께 보존할 원문 사본은 [예비 증거 JSON](results/mo09-qa-preliminary-20261006.json)에 있다. 본 결과는 ALL-04 최종 수용 판정을 대신하지 않는다.

## 최신 dev 재검증 (2026-10-06)

실행 코드 HEAD는 `3504195ee3c0e629bff4a5a04cb5e6984e20a8f7`이며 MO-09 수정은 미커밋 상태다. 운영 이미지의 Git SHA는 별도로 미확인이다.

- 기록표 출력: QA 6.4와 같은 7열·담당 배정·셀 이스케이프 확인. 부분 검증·제안 기준의 관찰 통과는 기록표 차단, 실제 실패는 실패로 보존한다.
- 운영 측정(`outputs/mo09-latest-live-20261006/`, 11:04~11:07 KST): 배포·상태 4항목 통과, Simulator 현재 상태·CSV 부분 검증 관찰 통과. 정상 100건 저장, 중앙값 1.998초·p90 2.277초·최대 4.141초·0.494건/초·재검사 12건·시간 초과/추론 오류 0건. **QA-SIM-02(p90 ≤ 2.2초)와 QA-SIM-13 제안 기준(최대 < 4초)은 실패**로 보존했다. 컨테이너 변경 감지는 발생하지 않았으며 간격 증가 원인은 아직 확정하지 못했다.
- 임시 MySQL 최초 재검증(`outputs/mo09-latest-isolated-20261006/`)은 DB 준비 단계에서 차단됐다. 초기화용 socket 서버를 준비 완료로 판단한 뒤 서버가 전환되는 문제가 있어, 최종 TCP 서버의 `SELECT 1` 확인으로 수정했다. 이 회차는 통과 증거로 사용하지 않는다.
- 격리 자동 회귀 최신 회차(`outputs/mo09-latest-isolated-final-20261006/`)는 7개 항목 통과했다. QA-IMG-06은 Windows `WinError 5`가 재현되는 환경 결함이 있어 Linux 컨테이너에서 1 passed로 재확인했고, Windows 원문도 보존했다. 자동 회귀는 기록표에서 차단으로 구분한다.
