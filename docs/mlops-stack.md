# MLOps·CI/CD 기술 스택

- 담당자: 홍유나
- 마지막 수정: 2026-09-17
- 상태: 완료

## 1. 목적

CQC의 MLOps·CI/CD 영역은 데이터·모델, 백엔드, 프론트엔드에서 개발한 서비스를 하나의 실행 환경으로 통합하고, 동일한 환경에서 반복 실행·검증·배포할 수 있도록 관리하는 것을 목적으로 한다.

MLOps 담당자는 모델 학습, 백엔드 비즈니스 로직, 프론트엔드 화면을 직접 구현하지 않는다. 대신 각 파트가 제공한 실행 단위와 설정을 Docker Compose에 연결하고, 자동 검사·배포·상태 확인·복구가 가능하도록 공통 실행 환경을 관리한다.

## 2. 현재 개발 환경

Docker를 실제 실행할 배포·시연 PC에서 다음 버전을 확인하였다.

- Docker: `29.7.2`
- Docker Compose: `v5.4.0`

프로젝트 루트는 다음 경로를 기준으로 한다.

```text
C:\CQC
```

현재 프로젝트 구조는 다음과 같다.

```text
C:\CQC
├─ configs/
├─ docs/
├─ models/
├─ notebooks/
├─ outputs/
├─ scripts/
├─ src/
│  ├─ api/
│  ├─ data/
│  ├─ inference/
│  ├─ models/
│  ├─ training/
│  └─ web/
├─ tests/
├─ .gitignore
└─ README.md
```

2026-09-17 기준으로 `src/data/manifest.py`는 구현되어 있으나, `src/api`, `src/inference`, `src/web`, `scripts`는 아직 실행 코드가 없는 골격 상태다.

따라서 backend, inference, frontend, simulator의 실제 Dockerfile, 실행 명령, 포트와 healthcheck 경로는 각 담당자의 구현 완료 후 확정한다.

## 3. 서비스 구성

CQC는 Docker Compose에서 다음 5개 서비스를 관리한다.

- `simulator`
- `inference`
- `backend`
- `frontend`
- `mysql`

각 서비스의 역할은 다음과 같다.

| 서비스      | 역할                                                               |
| ----------- | ------------------------------------------------------------------ |
| `simulator` | 저장된 시험 사과 다각도 그룹을 자동 입력                           |
| `inference` | 다각도 이미지를 받아 품종·품질 예측 결과 반환                      |
| `backend`   | 입력 검증, inference 호출, 500ms·저신뢰 정책, bin 결정, MySQL 연동 |
| `frontend`  | 현재 검사 상태, 이력, 통계·분석 화면 제공                          |
| `mysql`     | 검사 이력과 통계용 데이터 저장                                     |

가상 제어 기능은 별도 Docker 서비스로 분리하지 않고 backend 내부 모듈과 API로 구성한다.

## 4. 서비스 통신

CQC는 Kafka를 사용하지 않는다.

서비스 간 통신은 HTTP 기반으로 구성한다.

기본 흐름은 다음과 같다.

```text
simulator
    ↓ HTTP
backend
    ↓ HTTP
inference

backend
    ↓
mysql

frontend
    ↓ HTTP
backend
```

frontend는 inference를 직접 호출하지 않고 backend API만 사용한다.

## 5. Docker Compose 구성 원칙

Compose는 프로젝트 루트의 `compose.yaml`을 기준 파일로 사용한다.

초기 서비스 골격은 다음과 같이 구성한다.

```yaml
services:
  mysql:
    # MySQL 서비스

  inference:
    # 모델 추론 서비스

  backend:
    # API 및 판정 서비스

  frontend:
    # 웹 서비스

  simulator:
    # 자동 입력 서비스
```

현재 각 서비스의 실제 실행 코드가 완성되지 않았으므로 image, build, command, port, healthcheck의 세부 값은 아직 확정하지 않는다.

## 6. 기동 순서와 의존성

정상 시작 시 서비스는 다음 순서를 기준으로 기동한다.

```text
MySQL + inference
        ↓
      backend
        ↓
simulator + frontend
```

- 정상 시작 시 MySQL과 inference 상태를 확인한 뒤 backend를 시작한다.
- backend를 시작하기 전에 필요한 MySQL 마이그레이션이 정상적으로 적용되어야 한다.
- backend가 정상 상태인 것을 확인한 뒤 simulator와 frontend를 시작한다.
- 실행 중 inference에 장애가 발생하면 backend가 이를 시스템 오류로 처리하고 재검사 흐름을 계속 유지한다.
- 실행 중 MySQL 장애가 발생해도 선별 처리는 계속한다. DB 저장 실패는 상태와 로그에 기록하며, 장애 중 저장하지 못한 검사 이력은 유실을 허용하고 재시작 후 복구하지 않는다.

기동 의존성은 Docker Compose의 `depends_on`과 healthcheck를 이용하여 구성한다.

## 7. Healthcheck 원칙

각 서비스는 단순히 컨테이너가 실행 중인지가 아니라 실제 사용할 수 있는 상태인지 확인한다.

예정된 상태 확인 기준은 다음과 같다.

| 서비스      | Healthcheck 기준                                   |
| ----------- | -------------------------------------------------- |
| `mysql`     | DB 연결 및 간단 조회가 정상적으로 가능한지 확인    |
| `inference` | 테스트 추론이 정상적으로 동작하는지 확인           |
| `backend`   | health API가 정상적으로 응답하는지 확인            |
| `frontend`  | 웹 페이지가 정상적으로 응답하는지 확인             |
| `simulator` | 최근 1초 내 입력이 정상적으로 생성되고 있는지 확인 |

실제 healthcheck 명령과 URL은 각 서비스의 실행 API가 확정된 후 작성한다.

## 8. Restart 정책

컨테이너 재시작 정책은 `unless-stopped`를 사용한다.

서비스가 비정상 종료된 경우 Docker가 자동으로 재시작하도록 구성하되, 사용자가 명시적으로 중지한 서비스는 자동으로 다시 시작하지 않도록 한다.

```yaml
restart: unless-stopped
```

## 9. Git 브랜치와 배포 기준

Git 브랜치는 다음 기준을 사용한다.

- `feat/*`: 개인 기능 개발
- `dev`: 팀 통합 및 자동 배포 기준
- `main`: 최종 발표 버전 표시

`feat/* → dev` 병합은 Pull Request와 최소 1명의 확인 후 진행한다.

자동 배포는 `dev` 브랜치만 대상으로 한다.

`main` 브랜치에는 자동 배포를 구성하지 않는다.

## 10. CI/CD 기본 흐름

CI/CD의 기본 흐름은 다음과 같이 구성한다.

```text
feat/*
   ↓ Pull Request
자동 검사
   ↓
dev 병합
   ↓
통합 검사
   ↓
검사 통과
   ↓
배포 환경 반영
```

CI에서 검사할 세부 항목은 각 파트의 실제 코드와 실행 명령이 정해진 후 확정한다.

현재 프로젝트 기준으로 다음 항목을 검사 대상으로 둔다.

- 데이터 검사
- 문법 및 단위 테스트
- API 계약
- 모델 로딩
- DB 마이그레이션
- Docker Compose 설정
- 핵심 통합 동작

API 요청·응답, 서비스 상태와 오류 코드 계약은 네 담당자가 합의한 문서를 기준으로 CI 검사에 연결한다.

CI/CD 제품과 실제 Workflow 파일은 아직 확정하지 않는다.

## 11. 배포 실패 정책

새로운 `dev` 버전의 검사 또는 배포가 실패할 경우 기존에 정상 실행 중인 버전을 유지한다.

CI 또는 배포가 실패한 경우 실패한 검사 단계와 원인을 확인할 수 있도록 결과를 남긴다.

새로운 버전 때문에 기존 정상 버전까지 중단되지 않도록 구성하는 것을 원칙으로 한다.

구체적인 배포·롤백 방식은 CI/CD 도구와 배포 방식을 확정한 뒤 추가한다.

## 12. 환경 변수와 비밀값

MySQL 비밀번호와 접속 정보 등 실제 비밀값은 Git 저장소에 저장하지 않는다.

다음 방식을 기준으로 한다.

```text
.env
→ 실제 개발·배포 환경 값
→ Git 제외

.env.example
→ 필요한 환경 변수 이름과 예시 형식
→ Git 포함 가능
```

`.env`는 `.gitignore`를 통해 저장소에서 제외한다.

원본 데이터, 모델 가중치·체크포인트와 대용량 생성 출력도 Git 저장소에서 제외한다.

각 서비스가 필요한 환경 변수 목록은 backend, inference, frontend의 실행 설정이 확정된 후 추가한다.

## 13. 모델 관리

모델 파일과 체크포인트는 Git 저장소에 커밋하지 않는다.

모델 담당자가 제공하는 다음 정보를 기준으로 배포 모델을 관리한다.

- 모델 파일
- 모델명
- 모델 버전
- 클래스 매핑
- 입력 크기
- 프레임 선택 규칙
- 전처리 설정
- 신뢰도 기준
- 모델 체크섬
- 평가 결과

inference 서비스가 배포된 모델을 정상적으로 로딩할 수 있는지 자동 검사 대상에 포함한다.

모델 담당자가 승인 기준과 시험 데이터 목록을 확정하면, 고정 시험 이미지 회귀 테스트와 최소 성능 기준 검사를 자동 배포 전 검사에 포함한다. 구체적인 성능 임계값은 모델 담당자의 최종 승인 기준을 따른다.

모델 파일이 누락되거나 정상적으로 로딩되지 않으면 inference 상태를 실패로 표시하고 원인을 로그에 기록한다.

배포된 모델 버전은 inference 응답의 `model_version`과 검사 이력에 기록되는 모델 버전이 서로 일치하는지 통합 시험에서 확인한다.

## 14. Docker Volume

컨테이너 재시작 또는 재생성 후에도 유지해야 하는 데이터는 Docker Volume을 사용한다.

현재 보존 대상은 다음과 같다.

- MySQL 데이터
- 장애 이미지
- 마지막 simulator 입력 위치
- 순환 로그

장애 이미지는 최대 100개까지만 유지하며, 100개를 초과하면 가장 오래된 이미지부터 삭제한다.

구체적인 Volume 이름과 마운트 경로는 각 서비스의 저장 경로가 확정된 후 작성한다.

## 15. 입력 위치 복구

Docker 재시작 후 simulator가 처음부터 다시 시작하지 않고 마지막으로 처리한 이미지의 다음 위치부터 이어서 입력할 수 있어야 한다.

마지막 처리 위치는 MySQL이 아닌 Docker Volume에 저장되는 작은 상태 파일을 사용한다.

예시:

```text
Docker 재시작 전
마지막 처리 위치 = 53

Docker 재시작 후
54번째 입력부터 재개
```

상태 파일의 실제 경로와 형식은 simulator·backend 구현 후 확정한다.

## 16. 로그 관리

프로그램 로그가 무한히 증가하여 디스크를 사용하는 것을 방지하기 위해 로그 순환 정책을 적용한다.

기본 원칙은 다음과 같다.

- 로그 크기 제한
- 오래된 로그부터 순차 삭제
- 장애 발생 시 필요한 로그는 확인 가능하도록 유지
- API·모델·DB 오류 원인을 구분할 수 있도록 기록
- 실제 DB 비밀번호, 비밀값과 민감한 경로는 로그에 기록하지 않음

구체적인 로그 파일 크기와 보존 개수는 통합 실행 후 실제 로그 발생량을 확인하여 결정한다.

## 17. CPU 성능 시험 환경

서비스 배포 환경은 GPU 없는 CPU Docker 환경이다.

배포 기준 사양은 다음과 같다.

```text
Intel Core i7-4790
RAM 16GB
CPU Docker 환경
```

모델 담당자가 4·8·12·16·40장 입력과 병렬 처리 수를 비교할 수 있도록 동일 Docker Compose 환경에서 반복 가능한 CPU 성능 시험 환경을 제공한다.

CPU 성능시험에서는 연속 요청 기준으로 처리시간의 평균·최대·p95와 처리량을 기록한다.

순차 처리와 병렬 처리를 비교하고, 동시 처리 수별 결과와 최종 선택 근거를 기록한다.

배포 환경에서는 초당 사과 그룹 2개 처리와 그룹당 모델 추론 500ms 이내를 목표로 검증한다.

MLOps는 시험 환경과 실행 절차를 관리하며, 모델 성능 지표와 최종 모델 선정은 데이터·모델 담당자가 수행한다.

## 18. 실행·배포·복구 명령

현재 실제 서비스 코드와 Dockerfile이 완성되지 않았으므로 아래 명령은 Docker Compose 공통 실행 기준만 먼저 기록한다.

전체 서비스 실행:

```powershell
docker compose up -d
```

실행 중인 서비스 확인:

```powershell
docker compose ps
```

로그 확인:

```powershell
docker compose logs
```

전체 서비스 종료:

```powershell
docker compose down
```

각 서비스의 build, restart, healthcheck, 복구 명령은 Dockerfile과 실제 서비스명이 확정된 후 추가한다.

백엔드 담당자가 MySQL 마이그레이션·초기화 방법을 제공하면 새 환경에서도 같은 순서로 재실행할 수 있도록 실행·복구 절차에 포함한다.

최종 운영 문서에는 공통 실행 방법, 배포 버전, 자동 검사 결과와 로그 위치를 기록하여 팀원이 같은 절차로 시연 환경을 재현할 수 있도록 한다.

## 19. 자동 실행 원칙

Docker Compose 서비스가 정상 기동되면 simulator의 입력과 검사 흐름을 자동으로 시작한다.

simulator는 저장된 시험 사과 그룹을 기본 500ms 간격, 즉 초당 사과 그룹 2개를 목표로 지속적으로 입력한다.

웹 페이지 접속 여부와 관계없이 백그라운드에서 입력과 검사가 계속 진행되어야 한다.

## 20. 장애 토글 재시작 정책

시연용 장애 토글은 메모리 상태로만 유지한다.

Docker 서비스가 재시작되면 다음 장애 토글을 모두 OFF 상태로 초기화한다.

- 추론 시간 초과
- 추론 서비스 오류
- DB 연결 오류
- 정상 bin 명령 거부
- 가상 제어 무응답

## 21. 최종 수용시험

최종 배포 전 다음 항목을 반복 가능한 방식으로 시험한다.

- 정상 검사 100건
- 동일 모델·입력·설정의 고정 시험 이미지에서 같은 예측이 재현되는지 확인
- 초당 사과 그룹 2개 처리
- 그룹당 모델 추론 500ms 목표와 가상 제어 응답 100ms 목표 측정
- 장애 시나리오 5종
- Docker 재시작 및 simulator 위치 복구
- healthcheck 확인
- DB 검사 이력이 86,400건에 도달하면 오래된 8,640건이 삭제되는지 확인
- 장애 이미지가 100개를 초과하면 가장 오래된 이미지부터 삭제되는지 확인
- CSV 결과가 필터 조건과 검사 이력 결과에 맞게 생성되는지 확인
- 로그 순환 확인
- 배포된 모델 버전과 inference 응답·검사 이력의 모델 버전 일치 확인
- 새 환경에서 문서화된 실행·마이그레이션 절차로 서비스가 재현되는지 확인

최종 시험을 통과한 버전만 발표용 배포 버전 후보로 사용한다.

## 22. 현재 미결정 사항

2026-09-17 기준 다음 내용은 아직 확정하지 않는다.

- CI/CD 제품 및 버전
- backend Dockerfile과 실행 명령
- inference Dockerfile과 실행 명령
- frontend Dockerfile과 빌드·실행 명령
- simulator Dockerfile과 실행 명령
- 서비스별 포트
- 실제 healthcheck URL과 명령
- Docker Volume 이름과 세부 마운트 경로
- 로그 최대 크기와 보존 개수
- 배포 실패 시 기존 버전 유지의 실제 구현 방식
- 모델 배포 경로와 파일 전달 방식

위 항목은 각 파트의 실행 코드와 계약이 확정되는 시점에 순차적으로 결정한다.

## 23. 선택 근거

Docker와 Docker Compose를 사용하는 이유는 다섯 개 서비스를 동일한 실행 환경에서 관리하고, 개발 PC와 시연 PC 사이의 환경 차이를 줄이기 위함이다.

프로젝트 기간이 1개월이므로 Kafka와 복잡한 분산 시스템을 추가하지 않고 HTTP 기반 서비스 구조를 사용한다.

MLOps 구성은 새로운 도구를 많이 추가하는 것보다 다음을 우선한다.

- 동일 환경에서 반복 실행 가능
- 서비스 상태 확인 가능
- 오류 발생 위치 추적 가능
- 재시작 후 필요한 상태 복구 가능
- 검증된 버전만 배포
- 발표 환경에서 안정적으로 재현 가능

## 24. 배포 버전 동결

2026-10-13 기능 동결 이후에는 치명적 오류를 제외한 기능 변경을 하지 않는다.

최종 수용시험을 통과한 버전을 발표용 배포 버전 후보로 지정한다.

최종 수용시험을 통과한 발표용 배포 버전에는 Git 태그 후보를 지정한다.

발표 리허설과 최종 확인이 끝난 버전은 `main`에 최종 발표 버전으로 표시하되, `main` 자동 배포는 사용하지 않는다.

발표용 배포 버전은 다음 항목과 실제 실행 환경이 일치하도록 관리한다.

- Docker Compose 구성
- 모델 버전
- 환경 변수 구성
- 실행 명령
- 복구 절차
- 상태 확인 절차
- 최종 수용시험 결과

최종 발표 전에는 실행·복구·상태 확인 문서와 실제 배포 버전이 일치하는지 다시 확인한다.

## 25. 파트별 인수인계 조건

MLOps는 각 파트의 최소 실행 명령과 테스트 기준이 준비되는 즉시 Compose와 CI에 연결한다.

통합을 위해 각 담당자로부터 다음 항목을 전달받는다.

| 제공자      | MLOps가 전달받을 항목                                                  | 확인 기준                                                             |
| ----------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 데이터·모델 | 모델 버전, 평가 지표, 승인 기준, 시험 데이터 목록                      | 자동 검사에서 모델 로딩과 확정된 최소 성능 기준을 확인할 수 있어야 함 |
| 백엔드·DB   | 실행 명령, 환경 변수, healthcheck 경로, MySQL 마이그레이션·초기화 방법 | 새 환경에서 MySQL과 backend를 실행하고 상태를 확인할 수 있어야 함     |
| 프론트엔드  | 빌드·실행 명령, backend 주소 설정, 정적 산출물                         | 통합 환경에서 backend 주소를 주입하여 frontend를 실행할 수 있어야 함  |

MLOps는 전체 팀에 공통 실행 방법, 자동 검사 결과, 배포 버전과 로그 위치를 제공한다.
